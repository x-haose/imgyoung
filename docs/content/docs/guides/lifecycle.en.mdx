## Lifetime (TTL)

Each image can have a lifetime, after which it is deleted automatically. There is no separate temporary folder or temporary upload type: to keep an image only for a while, give it a short lifetime.

The lifetime is resolved across three levels; the first one that is set wins:

| Level | Where it is set | Values |
|---|---|---|
| Per upload | The `ttl` form field, the `ttl` JSON field of a URL fetch, or **Expiry** in the console upload dialog | Seconds; `0` or `never` means forever |
| Per-user default | **Users** page → **Edit** → **Default TTL (hours)** | Empty follows the global default; `0` means forever; a positive number is hours |
| Global default | **Default lifetime** (`default_ttl_hours`) under **Settings → Runtime settings** | `0` means forever (the default); a positive number is hours |

- An explicit `0` or `never` on an upload overrides both the user and the global default, so that image never expires.
- S3 uploads cannot set a lifetime per request; they use the user default, then the global default.
- The expiry time is computed and stored at upload. Changing the user or global default later does not affect existing images.
- All three levels are capped at 876000 hours (100 years); larger values are rejected. Every other runtime setting that represents a duration (sweep intervals, the delete grace period, retention periods, timeouts and so on) is capped at 100 years as well, converted to its own unit.

### Changing an existing image's lifetime

Change it in the image details; both the image's owner and administrators can:

- **Change expiry** → enter a number of days → **Extend**: the image now expires N days from now, and that duration becomes its new lifetime, which later renewals use.
- **Make permanent**: removes the expiry.

## Renewal on access

**Renew on access** (`ttl_renew_on_access`) is on out of the box. With it on, every public access to an image that has a lifetime pushes its expiry back to "the time the access was recorded + its lifetime".

In effect, the lifetime becomes "expires after this long without a single access": images in use stay, and images nobody looks at get cleaned up. With it off, the expiry time stays fixed.

- Only public accesses through `/i/` and `/o/` count. Console thumbnails and previews and S3 GetObject do not; see [Browsing in the console is not counted](./access.mdx#console-browsing).
- Accesses are collected in memory and written to the database in batches every `activity_flush_seconds` (60 seconds out of the box); renewal happens at that write.
- An image that has already expired at the moment of the write is not renewed.
- Images without a lifetime are unaffected.

## Expiry cleanup

As soon as an image expires, its public links return 404 and access no longer renews it. On the **Images** page it shows as **Expired** and can still be deleted by hand. The cleanup sweep reclaims its record and file afterwards.

The cleanup sweep runs once when the process starts and then every `cleanup_sweep_seconds` (60 seconds out of the box). Each round, in order, it:

1. deletes expired images, at most 500 per round, leaving any backlog for the next round;
2. physically deletes files whose grace period has passed, see [The delete flow](#delete-flow);
3. tags cold images for cleanup, see [Cold images](#cold-images);
4. reclaims upload idempotency keys past their retention period;
5. reclaims old audit log entries if **Audit log retention** (`audit_retention_days`) is set. The default, 0, keeps them forever.

Images that expire while the service is down are deleted in the sweeps after it restarts.

## The delete flow [#delete-flow]

Expiry, deleting in the console (one image, or up to 100 at a time), deleting from the **Cleanup** page and S3 DeleteObject all take the same path:

<Steps>
<Step>

**Delete the record**: the image record and any idempotency keys pointing to it are deleted, and the reference count of its physical file goes down by one. The link returns 404 from then on.

If Cloudflare cache purging is configured, a CDN purge is queued for `/i/<short ID>` and every variant parameter combination generated for the image. `/o/` alias links are not included. See [CDN](../operations/cdn.mdx).

</Step>
<Step>

**Mark for deletion**: when the reference count reaches 0, the physical file is marked for deletion at now + the delete grace period. The grace period, `delete_grace_minutes`, is 0 out of the box, meaning the next sweep deletes the file.

</Step>
<Step>

**Delete physically**: the first sweep after that time removes the file's variant cache, deletes its database records, and queues a deletion of the object on every channel holding a replica. Channel deletions run asynchronously and are retried on failure; any object that still survives becomes an orphan, which reconciliation reclaims. See [Backup & restore](../operations/backup.mdx#reconciliation-gc).

</Step>
</Steps>

One physical file can be shared by several image records, as a result of deduplication merges. Deleting one record does not affect the others; the physical file enters the delete flow only once its last reference is gone. **References** in the image details shows the current reference count.

The delete confirmations in the console tell you roughly when the physical file will go, based on the current grace period.

A user can only be deleted after every image they own has been deleted.

## Cold images [#cold-images]

Images nobody has accessed for a long time are tagged for cleanup and wait on the **Cleanup** page for an administrator's decision. **They are never deleted automatically**: deletion cannot be undone, so a person decides.

- **Threshold**: **Cold image threshold** (`cold_cleanup_days`), 90 days out of the box; 0 stops tagging.
- **Tagging**: on each cleanup sweep, images whose last public access is older than the threshold and which are not exempt get tagged. Images that have never been accessed count from their upload time.
- **Untagging**: the tag is removed when any of these happens:
  - the image is publicly accessed; the tag goes at the next batch write of access counts;
  - an administrator sets or removes the image's cleanup exemption (deciding to **Keep** an image sets it). After the exemption is removed, the next sweep judges the image again;
  - the image is deleted.
- Raising the threshold or setting it to 0 does not remove existing tags.
- Cold tagging and lifetimes are independent: images with a lifetime can be tagged too, and exempt images still expire.

### Reviewing

The **Cleanup** page (administrators only) lists images from the longest-unaccessed down, and works on single images or selections:

- **Keep**: sets the cleanup exemption on the image, so it is never tagged as cold again. Its lifetime and renewal are unaffected. The exemption can be removed in the image details.
- **Delete**: runs the [delete flow](#delete-flow) above.

### Cleanup exemptions

Only administrators can set cleanup exemptions, so an image's owner cannot exempt their own images to dodge cleanup.

- The **Cleanup exempt** switch in the image details can be turned on before an image ever goes cold. Regular users see the state but cannot change it.
- The **Exempt only** filter on the **Images** page lists every exempt image.

## Deduplication

Deduplication never runs on the upload path, so it never slows uploads down. The background deduplication runs once at startup and then every `dedup_scan_seconds` (300 seconds out of the box). Each round merges exact duplicates first, then scans for near-duplicates:

| | Exact duplicates | Near-duplicates |
|---|---|---|
| Detected by | Identical stored bytes (same SHA-256) | Perceptual hashes that differ in no more bits than the threshold |
| Handling | Merged automatically | Listed on the **Duplicates** page for an administrator to decide |

### Exact duplicates: merged automatically

The bytes are identical, so every link serves the same content after a merge, and merging happens automatically:

- the oldest copy is kept, the image records of the others are pointed at it, and their reference counts are added to it;
- the extra files are marked for deletion and removed after the delete grace period;
- files of different users are merged as well. Every image record keeps its own short ID, owner, lifetime and access count, and every link keeps working;
- quotas count every reference in full, so merging does not reduce anyone's usage.

### Near-duplicates: reviewed by hand

Every physical file gets a 64-bit perceptual hash (pHash) at upload. When two files' hashes differ in no more bits (Hamming distance) than **Similarity threshold** (`dedup_phash_max_distance`, 10 out of the box), the pair becomes a candidate on the **Duplicates** page.

- A higher threshold is looser and produces more false positives; 0 turns similarity scanning off. The console notes that distances of 0–2 are nearly identical.
- Even a distance of 0 only makes a candidate and is never merged automatically: equal perceptual hashes do not mean equal bytes.
- Scanning is incremental: each round compares only new files against the existing ones. After a restart everything is rescanned once, and dismissed pairs do not come back.

### Deciding, and which image to keep

The **Duplicates** page (administrators only) shows each candidate pair side by side as Left and Right, with format, dimensions, size, reference count and distance, closest pairs first:

- **Keep this one** → confirm **Merge**: every reference of the other image now points to the kept one, the merged file is removed after the delete grace period, and any other candidates involving it are dropped. **This cannot be undone.**
- **Dismiss**: the pair is never shown again; several pairs can be dismissed at once.

After a merge, every link of the merged image (including other users' references) serves the kept image's content, which may differ in size, format and even picture. So keep the higher-resolution or better-format image, and choose **Dismiss** when the two are actually different pictures. Browsers and CDNs that already cached the old content keep showing it until their cache expires.

Merges and dismissals are recorded in the audit log, with the actions "Merge duplicates" and "Dismiss duplicates".

## Related settings

| Setting | Label in the console | Default |
|---|---|---|
| `default_ttl_hours` | Default lifetime | 0 (forever) |
| `ttl_renew_on_access` | Renew on access | On |
| `cold_cleanup_days` | Cold image threshold | 90 days |
| `delete_grace_minutes` | Delete grace period | 0 minutes |
| `cleanup_sweep_seconds` | Cleanup sweep interval | 60 seconds |
| `activity_flush_seconds` | Activity flush interval | 60 seconds |
| `idempotency_key_ttl_hours` | Idempotency key retention | 24 hours |
| `dedup_scan_seconds` | Dedup scan interval | 300 seconds |
| `dedup_phash_max_distance` | Similarity threshold | 10 |
| `audit_retention_days` | Audit log retention | 0 (forever) |

All of them are changed under **Settings → Runtime settings** and take effect on save; see [Configuration](../configuration.mdx).
