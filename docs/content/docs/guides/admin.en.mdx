## Signing in

The admin console lives at the site root, for example `https://img.example.com/`.

After the first start, sign in as the built-in administrator: username `admin`, and the initial password, that is, the one generated at the first start and printed in the log, or the value set with `IMGYOUNG_ADMIN_PASSWORD` at deployment. The console then takes you straight to **Set the admin password**.

<Callout type="warn" title="Change the initial password first">
The initial password is written in the log or the deployment settings, and anyone who can see them can sign in, so change it soon. Until you do, this account can only change the password, sign out and read the current account; every other console action (including console uploads, issuing tokens and managing channels) returns 403, whether the request comes from the console or a script.
</Callout>

Upload tokens cannot be provisioned through environment variables. On a headless deployment, too, sign in to the console, change the initial password, then issue an upload token.

If you forget the password, see [Password reset](../operations/password-reset.mdx).

## A tour of the pages

The sidebar has three groups, and regular users see only part of it:

| Group | Pages | Visible to |
|---|---|---|
| Content | Dashboard, Images, Upload tokens, Imports | Everyone |
| Site | Storage channels, Users, Duplicates, Cleanup, Audit log | Administrators |
| Other | Guide | Everyone |
| Other | Settings | Administrators |

The top bar has page search (⌘K / Ctrl+K opens the command palette), the language switch and the theme switch. The account menu at the bottom of the sidebar holds **Change password** and **Sign out**.

### Dashboard

Administrators see the whole site:

- **Stat cards**: Images, Storage used (original bytes in total, replicas not double counted), Users, Accesses (with an estimated traffic figure), Pending cleanup, Possible duplicates.
- **Storage channels**: the health and stored bytes of each channel.
- **Alerts**: alerts that are still open. Each resolves itself once its condition no longer holds. **History** opens the **Alert history** tab in Settings.
- **Top images**: the 10 most accessed images.

There are five alert kinds, and their descriptions follow the interface language:

| Alert | Description shows |
|---|---|
| Channel unhealthy | The failure reason, written as in the channel list |
| Replication failed | How many replicas failed |
| Channel over quota | The usage and the threshold |
| Channel drain failed | The failure reason, written as in the channel list |
| Backup failed | The backup error |

Alert kinds the page does not recognize show the Chinese description stored by the server.

<Callout type="warn" title="Your data only lives on this host">
This warning appears at the top of the dashboard when no channel is healthy, not draining and using a driver other than local; it also appears when there is no healthy channel at all. Image replicas and metadata snapshots then exist only on this host, so losing the host loses everything. Adding an object storage or cloud drive channel clears it; if you already have one, check on the **Storage channels** page why it is unhealthy.
</Callout>

Regular users see their own image count, space used and quota.

The **Quick start** card appears while there are no images yet:

- Administrators: while the site has no images, it shows three steps: check storage channels, issue an upload token, start uploading.
- Regular users: while they have not uploaded anything, it shows "You haven't uploaded any images yet. Two steps to get going" with two steps: issue an upload token, start uploading.

How accesses and the traffic estimate are counted is described in [Accessing images](./access.mdx).

### Images

A grid of images. Administrators see the whole site (**All images**); regular users see only their own (**My images**).

- **Search** by short ID or file name.
- **Filter** by **Upload token**, **Uploaded** time and **Exempt only**; administrators can also filter by **Owner**.
- **Select** lets you pick images and **Delete selected**, at most 100 at a time. If some deletions fail, the result shows how many were deleted and how many failed, with the reason for the first failure (for example, the image was already deleted elsewhere).
- **Upload** uploads straight from the console; see [Uploading](./upload.mdx#uploading-in-the-admin-console).

Clicking an image opens its details:

- **Share link**: the full link, with **Copy as** URL, Markdown, HTML or BBCode. Below it are the available resize widths; clicking one copies a link with `?w=`. When a public site address is set, links use its domain.
- **Metadata**: format, dimensions, size, owner, source token, references, upload time, last access, accesses, expiry (with **Change expiry**), cleanup exemption and SHA-256.
- **Replicas**: the replica state of this image on each channel (Pending / Uploading / Ready / Failed) and the attempt count. Replicas that have failed show **Last error**, written like a channel's failure reason; see [Failure reasons](#failure-reasons) below.
- **Delete**; administrators also get **Audit log**, which opens the audit entries targeting this image.

Lifetimes and cleanup exemptions are explained in [Lifecycle and deduplication](./lifecycle.mdx).

### Imports

Move images from an old image host or a blog into ImgYoung in bulk. Regular users see and manage only their own jobs; administrators see everyone's and can cancel or delete any job.

| Input | Use |
|---|---|
| Image URLs | One address per line, imported directly |
| Website | A sitemap, feed or web page; after scanning, confirm the domains to import |
| Text and files | Markdown or HTML text; after scanning, confirm the domains to import |

When a job ends you can download a mapping from old links to new ones. For the full walkthrough see [Bulk import](./import.mdx).

### Storage channels

Create, edit, probe and delete channels, and set their priority, encryption and 302 direct links. The **Replicas** column shows how many replicas on each channel are ready, pending and failed. Form fields and per-backend configuration are covered in [Storage channels](../channels/index.mdx); the points below matter when working in the console.

#### Configuration and authorization

- **Cloud drive authorization**: cloud drive templates have two fields above the authorization control, **App client ID** and **App client secret**, stored encrypted with the channel configuration. **One-click authorization** needs the client ID first. With **Paste a token**, fill in both fields too if the token was authorized with your own app, because a token can only be refreshed by the app that issued it.
- **Masked credentials**: when you edit a channel, credential-type parameters are masked; leave them unchanged to keep the stored values. Besides passwords, secrets and tokens, access key IDs, WebDAV usernames, client IDs and the like count as credentials, as decided by the server from the parameter attributes each backend declares. In custom mode the interface cannot tell which keys are credentials, so every value is shown in a masked input that you can reveal one at a time.
- **Save conflicts**: if two people edit the same channel at once, or the provider refreshes the token and writes it back to the channel while you are saving, the later save does not take effect and returns 409, saying the configuration changed while saving. Just save again.
- **Token refresh**: if the provider refreshes the authorization token during **Test connection**, the result says the form now holds the new token and the old one may no longer work, and the authorization field shows **Authorized**; just save. A failed save does not lose the token either: if the provider refreshed the submitted token while saving, the message says the form now holds the new token, so fix the problem and save again without authorizing again. When you edit a channel and a stored token you kept gets refreshed, it is written straight back to the channel.
- **Encryption and direct links**: with **Encrypt new channels by default** turned on in Settings, a new channel whose **Server-side encryption** stays at **Inherit the global default** is encrypted, and **Allow 302 direct links** is then unavailable. To use direct links, set **Server-side encryption** to **Force off**.

#### Failure reasons

The tooltips of the **Unhealthy** and **Draining** badges show the most recent failure as "explanation (raw cause)":

- The explanation follows the interface language, for example "Authentication failed (401): check the username, password or authorization token".
- The raw cause is the innermost error in the chain, usually the provider's or network library's own English message, with credentials removed and cut to at most 200 characters.
- When the failure cannot be classified, only the raw cause is shown.

A failed **Probe again** or **Test connection** reports the same text.

A channel that fails to load (its configuration cannot be decrypted, the driver cannot be built, building takes longer than 30 seconds and so on) shows as **Unhealthy** in the list, with "Load failed: " in front of the reason. A master key that differs from the one the configuration was written with is classified as "The channel settings cannot be decrypted".

Channels load in parallel, so one unreachable backend does not hold up startup or health checks. Every health check round retries loading, and **Probe again** retries loading first as well. A channel becomes healthy and serves reads and writes again only once it loads and passes the probe.

#### Exporting the rclone config

**Export rclone config** in a channel's row menu downloads the channel's rclone config file, `imgyoung-channel-<channel ID>.rclone.conf`; draining channels do not offer it. With this file, a stock rclone can read and write the channel's data without ImgYoung. An encrypted channel also gets a crypt remote, and reads through it come back as plaintext.

- The explanatory comments at the top of the file are in Chinese or English, following the interface language.
- Every download is recorded in the audit log.
- The dialog closes only after a successful download; on failure it stays open so you can retry. Closing it during a download aborts the download.

The file's contents and usage are covered in [Channel encryption](../channels/encryption.mdx) and [Storage channels](../channels/index.mdx).

<Callout type="warn" title="The config file contains credentials">
The file contains the channel's credentials and OAuth tokens, plus the decryption passwords for an encrypted channel. Keep it offline and safe, like the master key.
</Callout>

#### Deleting a channel

When you delete a channel, **Also delete what this service stored on the channel** is ticked by default:

| Choice | The channel | Data on the channel |
|---|---|---|
| Keep it ticked and click **Delete and purge** | Shows as **Draining** and is removed once its data is gone | Image replicas, metadata snapshots and leftover deep-check files are deleted one by one in the background |
| Untick it and click **Remove only** | Removed immediately | Image replicas and metadata snapshots are left as they are, for you to deal with at the provider if needed |

If this channel holds the only ready replica of some images, both kinds of deletion are refused with 409, and the message gives the number of such images; replicas on draining channels do not count. Add or fix another channel first and wait until those images have ready replicas on the other channels (no **pending** and no **failed** in their **Replicas** column), or delete those images, then delete the channel.

**Delete and purge** deletes only these objects: image replicas on record, objects under the system directory `_imgyoung/` (metadata snapshots included) and deep-check leftovers. Everything else in the channel is left alone: files written by other programs are untouched, and orphans left by failed uploads that reconciliation has not deleted yet also stay at the provider.

Once a channel is draining, editing, test connection, probing and re-authorizing are all refused (409), and the only action left is **Remove now**. **Remove now** removes the channel immediately and stops the purge: apart from the one object being deleted at that moment, the remaining remote objects (snapshots included) are left as they are.

#### When purging fails

A failed purge is retried automatically with backoff and never stops. If the channel was only temporarily unavailable, it finishes draining on its own once it recovers.

- Only when the same purge job still fails on its 4th attempt (with the built-in backoff, about 98 seconds after the first failure when each attempt fails quickly) is the reason written to the channel and shown in the **Draining** badge's tooltip, prefixed with an explanation of the purge failure, and a "Channel drain failed" alert opened. Until then the channel just shows **Draining**, so a single network hiccup does not raise an alert. A purge run interrupted by a shutdown, or one that times out after deleting some objects, counts neither as a failure nor as an attempt; a run that times out without deleting a single object counts as a failure.
- A draining channel that cannot be loaded cannot be purged either, so the load failure is shown right away and opens the "Channel drain failed" alert. As soon as the channel loads, that reason is cleared and the alert resolves; from then on only failures of the purge itself can open it again.
- The reason for a purge failure and its alert stay until the channel is purged or removed.

If the credentials are revoked or the bucket no longer exists, so that retrying cannot succeed, use **Remove now** on the channel. For a channel you already know cannot be purged, choose **Remove only** when deleting it.

### Users

Lists every account with its image count, usage / quota and default TTL. You can create accounts (**New user**), **Edit**, **Reset password** and **Delete**; see [Roles and permissions](#roles-and-permissions) and [Quotas and upload limits](#quotas-and-upload-limits) below.

### Duplicates and Cleanup

Two review queues listing images that need an administrator's decision, one item at a time:

- **Duplicates** compares pairs of images with close perceptual hashes side by side, so you can merge or dismiss them.
- **Cleanup** lists cold images nobody has accessed for a long time, so you can keep or delete them.

See [Lifecycle and deduplication](./lifecycle.mdx).

### Audit log

An append-only record of administrative actions. You can filter by **Action**, **Actor** (user ID), **Target** (image short ID, channel ID, token ID and so on, exact match) and **Time range**.

Creating, editing, exporting and deleting a channel all use the channel ID as the target, and creating and editing also record `name=` with the channel name in the details, so searching by channel ID finds every action on a channel. Channel IDs are never reused: a deleted channel's ID is never given to a new one.

Recorded actions:

| Object | Actions |
|---|---|
| Channels | Create channel, Edit channel, Delete channel, Export channel rclone config |
| Tokens | Issue token, Revoke token, Rotate token, Delete token |
| Users | Create user, Update user (including password changes and resets), Delete user |
| Images | Update image (lifetime, cleanup exemption), Delete image (including S3 DeleteObject) |
| Imports | Create import, Cancel import, Delete import |
| Reviews | Merge duplicates, Dismiss duplicates |
| Settings | Update settings, Add referer allowlist entry, Remove referer allowlist entry |
| Data | Export data, Create backup, Restore backup |

Uploads themselves and automatic expiry are not audited. Retention is set by **Audit log retention** (`audit_retention_days`); the default, 0, keeps entries forever.

### Guide

A built-in quick reference, visible to every user. Its curl, PicGo and S3 client examples are already filled in with the current site's address.

### Settings

Administrators only, with four tabs:

- **Runtime settings**: every runtime setting, grouped into access & links, upload limits, lifecycle, on-demand processing, deduplication, reliability & channels, CDN cache purge, and alerts & audit. Click **Save changes** and they apply immediately without a restart. If any value is invalid, nothing is saved, and the message names the setting key and the rule it breaks. See [Configuration](../configuration.mdx).
- **Hotlink protection**: the Referer allowlist and the **Allow empty referer** switch; see [Accessing images](./access.mdx#hotlink-protection).
- **Backups & export**: metadata snapshots are written to every healthy channel on the **Backup interval**, each channel keeping its own most recent copies. The snapshot table lists each snapshot with its size, time and **Stored on** (the channels holding it, in priority order), with **Back up now**, **Download** and **Restore**; **Export JSON** exports all metadata. For usage, working through a reverse proxy and error codes, see [Backup & restore](../operations/backup.mdx).
- **Alert history**: every alert's open and resolve record. For the alert webhook, see [Monitoring](../operations/monitoring.mdx).

Below **Runtime settings**, the **Bootstrap configuration** card shows the following read-only; changes to the environment variables take effect only after a process restart:

| Category | Contents |
|---|---|
| Environment variables | Listen address, data directory, trusted proxy networks, networks allowed on `/metrics` |
| Build | Server version, build commit, build time |
| Built-in policies | Login rate limit, replica reconciliation interval |

- The data directory is shown as the absolute path resolved at startup; a relative path is resolved against the working directory at startup.
- A network variable that is not set shows its default networks.
- A network variable explicitly set to an empty string shows "Empty: forwarded headers are never trusted" for **Trusted proxy networks** and "Empty: open to no one" for **Networks allowed on /metrics**.

Every download in the console (Export JSON, snapshot downloads, Export rclone config) fetches the whole file first and only then hands it to the browser to save. On failure or an interrupted transfer, a notification at the bottom right gives the reason; an error response or a partial file is never saved.

## Roles and permissions

Accounts are created only by administrators on the **Users** page; there is no sign-up. There are two roles:

| Capability | Administrator | User |
|---|---|---|
| Upload (token, console, S3) | Yes | Yes |
| View and delete images | Whole site | Own only |
| Change image lifetimes | Whole site | Own only |
| Set cleanup exemptions | Yes | No |
| Issue and rotate own tokens, view own tokens' S3 settings | Yes | Yes |
| View, revoke and delete other users' tokens | Yes | No |
| Storage channels, Users, Duplicates, Cleanup, Audit log, Settings | Yes | No |

Regular users cannot see each other's images or tokens, and opening someone else's image details returns 404. Image links themselves are public: anyone with a link can load it.

There can be several administrators. The built-in administrator (user ID `default`) is protected: it cannot be disabled, demoted or deleted, though it can be renamed. No administrator can delete their own account.

On the **Users** page:

- **New user**: username, initial password (at least 8 characters; usable right away), role, quota and default TTL.
- **Edit**: change the username, role, quota or default TTL, or tick **Disabled**. Disabling ends all of the user's sessions at once, and their tokens can no longer upload.
- **Reset password**: set a new password; all of the user's sessions end immediately.
- **Delete**: refused while the user still owns images, so delete those first. The user's tokens and sessions are deleted with the account; audit entries stay.

## Quotas and upload limits

- **Quota**: set per user when creating or editing the account, in MB or GB; empty or 0 means unlimited. An upload that would exceed the quota gets 403. Users see their space used and quota on the dashboard; administrators see the **Usage / quota** column on the **Users** page.
  Every reference counts in full: each image counts the complete size of its physical file, and deduplication merges do not reduce usage, so uploading the same images as someone else does not lower anyone's usage.
- **Upload rate limit**: `upload_rate_per_min` under **Settings → Runtime settings**, applied to every user alike; the default, 0, turns it off. Uploads by the same user through tokens, the console and the S3-compatible API share one allowance.
- **Concurrent uploads**: `max_concurrent_uploads`, shared by the whole site, 8 by default.

What happens when a limit is hit, and the status codes, are covered in [Uploading](./upload.mdx#formats-and-limits).

## Upload tokens [#upload-tokens]

Sent in an `Authorization: Bearer` header, an upload token can only call `/api/upload` and `/api/upload/url`. Each token also has a matching set of S3 credentials (see **S3 client settings** below), which can upload through the S3-compatible API and also read and delete the objects that user uploaded through S3. Neither can sign in to the console or call the console API. The console itself uses a session from signing in with a password; see [Sessions and security](#sessions-and-security).

If a token or its S3 credentials leak, the damage is limited to uploading as that user and to the objects that user uploaded through S3. Issue one token per client, so that a leaked one can be revoked on its own.

### Issuing

On the **Upload tokens** page, click **Issue token** and fill in:

- **Purpose**: for example `picgo` or `blog-script`, at most 64 characters. A user cannot have two active tokens with the same name; if the old token of that name has expired, issuing a new one revokes the expired record automatically.
- **Expiry**: Never, 7, 30, 90 or 365 days. An expired token stops working exactly as if it were revoked.

After issuing, a dialog shows the token secret (`imgy_` followed by 43 characters). **It is shown this one time only**; once the dialog is closed it can never be shown again. The database keeps only its SHA-256 and a 12-character identifying prefix.

Send it in the request header `Authorization: Bearer <token>`.

### List and status

The list shows name, prefix, status (Active / Expired / Revoked), expiry, last used and issue time. **Last used** is written in batches about once a minute.

Every image records the token it was uploaded with, and the **Images** page can filter by **Upload token**.

### Row actions

Open **More actions** at the end of a row:

| Action | Applies to | Effect |
|---|---|---|
| **S3 client settings** | Your own active tokens | Shows the S3 access key, secret and endpoint for this token; you can view them as often as you like. See [Upload clients](./clients.mdx) |
| **Rotate** | Your own active tokens | Issues a new token with the same name and revokes the old one in a single step. The new secret is also shown only once, and the old token and its S3 credential stop working immediately. A token that never expired still never expires; one with an expiry gets the same duration again, counted from now |
| **Revoke** | Active tokens | Stops working immediately: clients using it can no longer upload, and its S3 credential stops working too. The record stays |
| **Delete record** | Revoked or expired tokens | Removes it from the list; audit entries stay. Active tokens cannot be deleted; revoke them first |

### Administrators viewing other users' tokens

Administrators can use **View by user** to switch to any user's token list and **Revoke** or **Delete record** there.

**Rotate** and **S3 client settings** are only available for your own tokens. Both hand out working credentials, so using them on someone else's token would amount to taking over that user's upload access and the objects they uploaded through S3.

## Sessions and security

| Mechanism | How it works |
|---|---|
| Password storage | argon2id (64 MiB memory, 3 iterations, 1 lane) with a random salt per password. Passwords need at least 8 characters, counted as characters (Unicode code points), so one Chinese character counts as one |
| Login rate limit | Counted separately per client IP and per username: 5 attempts in a row each, then one more every 12 seconds; beyond that the response is 429. A successful sign-in resets the count. Behind a trusted reverse proxy, the client IP comes from `X-Forwarded-For` |
| Username enumeration | An unknown username and a wrong password return the same error and take about the same time to check |
| Sessions | Signing in issues a 256-bit random session ID in the cookie `imgyoung_session`, marked `HttpOnly` and `SameSite=Lax`, plus `Secure` when the client reaches the site over HTTPS. The server stores only a hash of the session ID, so a leaked database cannot be used to hijack sessions. Sessions last a fixed 30 days and are not extended by use |
| CSRF check | Each session is bound to a CSRF token that every state-changing request must send in the `X-CSRF-Token` header; the console does this automatically |
| Initial password | While the built-in administrator still uses the initial password, the server only allows changing the password, signing out and reading the current account; every other console API returns 403 |
| Changing passwords | **Change password** asks for the current password; afterwards every device of that user is signed out and must sign in again |
| Disabling and password resets | Disabling a user or resetting their password ends all of their sessions at once; a disabled user cannot sign in, and all of their tokens stop working |
| Page hardening | Every response carries `X-Frame-Options: DENY` and `X-Content-Type-Options: nosniff`. Console pages also carry a Content Security Policy that allows scripts and API calls only from this site and forbids embedding in other pages |

Both the HTTPS check and the client IP depend on forwarding headers from your reverse proxy, which are trusted only from the networks in `IMGYOUNG_TRUSTED_PROXIES`. See [Reverse proxy](../operations/reverse-proxy.mdx).

## Language and theme

- **Language**: the language button in the top bar switches between 简体中文 and English. On a first visit the browser language decides: Chinese browsers get Simplified Chinese, everything else English. After that, your choice is remembered for a year.
- **Theme**: the theme button in the top bar offers Light, Dark and System. Dark is the default, and the choice is remembered as well.

Both preferences are stored only in the current browser and do not follow your account.

All interface text follows the selected language, including what the server returns: errors, channel and replica failure reasons, and alert descriptions. The server sends only error codes, classifications and parameters, and the console renders the text in the current language. Only raw causes reported by providers or network libraries are shown as they are, usually in English.

## Error codes

Common error codes for console actions are listed below; the complete list is the `ErrorCode` schema in the [API reference](../api/index.mdx#error-format). Upload-related codes are listed in [Uploading](./upload.mdx#status-codes), and backup and restore codes in [Backup & restore](../operations/backup.mdx#error-codes).

| Action | Status | Error code | Meaning |
|---|---|---|---|
| Any console action other than changing the password, signing out and reading the current account | 403 | `must_change_password` | The built-in administrator still uses the initial password; change it first |
| Saving a channel | 409 | `channel_config_changed` | Another edit changed the configuration while saving, or the provider refreshed the authorization token; save again |
| Deleting a channel | 409 | `channel_sole_replicas` | This channel holds the only ready replica of some images; the message gives the number of images |
| Editing, test connection, probing, re-authorizing | 409 | `channel_deleting` | The channel is draining; the only action left is **Remove now** |
| Opening image details | 404 | `image_not_found` | The image does not exist, or a regular user opened someone else's image |
| Changing an image's expiry | 409 | `image_expired` | The image has expired, so its expiry can no longer be changed |
| Bulk import | 400, 404, 409 | `import_input_invalid`, `import_not_found`, `import_state_invalid` and others | See [Bulk import](./import.mdx#error-codes) |
