## Upload entry points

| Entry point | Authentication | Good for |
|---|---|---|
| `POST /api/upload` (multipart form) | Upload token | Scripts, PicGo / PicList custom uploaders |
| `POST /api/upload/url` (JSON) | Upload token | Having the server fetch an image from another address |
| **Upload** on the **Images** page of the admin console | Console session | Drag and drop, file picker, clipboard paste, fetch from URL |
| S3-compatible API `/s3/…` | S3 credential derived from an upload token | Clients that can upload to S3; see [Upload clients](./clients.mdx) |

All four go through the same processing steps: format check, pixel budget check, quota pre-check, EXIF handling, channel writes, then the metadata database record. They differ only in where the bytes come from and which options they accept: the S3-compatible API cannot set the lifetime per request, does no EXIF processing, and has no idempotency key.

Upload tokens are issued on the **Upload tokens** page of the console; see [Admin console](./admin.mdx#upload-tokens).

## Uploading through the API

The simplest upload:

```bash title="Terminal"
curl -H "Authorization: Bearer imgy_xxxxxxxx" \
  -F "file=@photo.jpg" \
  https://img.example.com/api/upload
```

With every optional parameter:

```bash title="Terminal"
curl -H "Authorization: Bearer imgy_xxxxxxxx" \
  -H "Idempotency-Key: 7d0c6a2e-photo-0001" \
  -F "file=@photo.jpg" \
  -F "ttl=604800" \
  -F "exif_policy=strip" \
  https://img.example.com/api/upload
```

| Form field | Required | Meaning |
|---|---|---|
| `file` | Yes | The image file. Only the first `file` part with a file name is used. The file name is metadata only (shown and searchable in the console); control characters are removed and it is truncated to 255 bytes |
| `ttl` | No | Lifetime in whole seconds (0 to 3153600000) or `never`; both `0` and `never` mean the image never expires. When omitted, the user's default applies, then the global default; see [Lifecycle and deduplication](./lifecycle.mdx) |
| `exif_policy` | No | `strip` or `passthrough`. When omitted, the global default applies (`passthrough` by default); see [EXIF handling](#exif-handling) below |

- `ttl` and `exif_policy` are read only from multipart form fields; putting them in the URL query string has no effect.
- Each of the two fields is at most 1 KiB; a longer one returns 400.
- Any other form fields are ignored.
- The `Idempotency-Key` request header is optional; see [Idempotency keys](#idempotency-keys).

A successful upload returns 200:

```json
{
  "id": "R0RjUyP1UW",
  "url": "https://img.example.com/i/R0RjUyP1UW"
}
```

- `id` is a 10-character short ID drawn from `0-9A-Za-z`.
- `url` is always absolute. If the **Public site address** (`base_url`) is set, it is used; otherwise the address is derived from the request: the scheme from whether the connection uses TLS, the host from the `Host` header.
- When the request arrives through a trusted reverse proxy, `X-Forwarded-Proto` and `X-Forwarded-Host` are used instead. Which proxies are trusted is set by the `IMGYOUNG_TRUSTED_PROXIES` environment variable.

<Callout type="warn" title="Set base_url behind a reverse proxy or CDN">
If the public domain of your reverse proxy or CDN differs from the host in the request, you must set `base_url`. See [Configuration](../configuration.mdx) and [Reverse proxy](../operations/reverse-proxy.mdx).
</Callout>

Failures return an error envelope, described in [Error responses](#error-responses) below. The full API definition is in [API reference: data plane](../api/data-plane.mdx).

### Error responses

The upload endpoints and every JSON API of the admin console return the same error envelope on failure. The exceptions are the image access endpoints, which return plain-text errors, and the S3-compatible API, which returns XML errors.

For example, uploading an oversized file with the default 50 MB per-image limit returns:

```json
{
  "code": "upload_too_large",
  "error": "文件超过大小上限(50 MB)",
  "params": { "max": "50" }
}
```

| Field | Meaning |
|---|---|
| `code` | Error code, a stable machine-readable identifier. The same failure always has the same code, however the message is worded |
| `error` | The Chinese message with the parameters filled in. Callers that do not go through the admin console (PicGo, ShareX, curl and so on) can show it to people as is |
| `params` | Values for the placeholders in the message, keyed by placeholder name, all strings; omitted for error codes without parameters |

- Scripts should branch on `code` (together with the HTTP status), not match the text of `error`.
- The admin console renders the message for `code` and `params` in the current interface language, so the English interface shows English.
- Upload-related codes are listed in [Status codes](#status-codes) below; the complete list is the `ErrorCode` schema in [API reference: data plane](../api/data-plane.mdx).

curl prints the body of a failed response by default (unless you pass `-f` / `--fail`), so the envelope shows up directly while debugging:

```bash title="Terminal"
curl -sS -H "Authorization: Bearer imgy_xxxxxxxx" \
  -F "file=@huge.png" \
  https://img.example.com/api/upload
# {"code":"upload_too_large","error":"文件超过大小上限(50 MB)","params":{"max":"50"}}
```

## Idempotency keys

On a flaky network a client may send the same upload twice. Sending an `Idempotency-Key` header keeps the retry from creating a second image:

- Within the retention period, a request from the same user with the same key returns the `id` and `url` of the first successful upload and writes nothing to the channels. The retention period is `idempotency_key_ttl_hours`, 24 hours by default, counted from that first success.
- A hit does not compare the request content: if you reuse a key with a different file, you still get the first image back. Use a different key for every distinct image.
- Only successful uploads record their key, so a failed request can safely be retried with the same key.
- Of several concurrent requests with the same key, only one is stored; the others return the same result, and the objects they already wrote to channels are deleted right away.
- Keys are scoped per user: two users can use the same key without affecting each other, so nobody can use an idempotency key to probe for or retrieve someone else's image.
- Once the retention period has passed, or the image the key points to has been deleted, the same key is treated as a new upload.

Both `/api/upload` and `/api/upload/url` honor idempotency keys; the S3-compatible API does not. A URL import that hits a key returns the first result right away without fetching the remote address again.

## Fetching from a URL

Give the server an image address and it downloads and stores the image for you, which is handy for pulling images back from other image hosts. The fetched bytes go through the same processing steps as a direct upload, so the format allowlist, pixel budget, EXIF handling and quota all apply; the server never copies a remote file straight into a channel.

```bash title="Terminal"
curl -H "Authorization: Bearer imgy_xxxxxxxx" \
  -H "Content-Type: application/json" \
  -d '{"url": "https://example.com/photo.png", "ttl": "never"}' \
  https://img.example.com/api/upload/url
```

The body is a JSON object of at most 8 KiB containing only the fields below; any other field returns 400:

| Field | Required | Meaning |
|---|---|---|
| `url` | Yes | Image address, `http` / `https` only |
| `file_name` | No | File name. Defaults to the last segment of the URL path, or `fetched` if there is none |
| `exif_policy` | No | Same as the form upload |
| `ttl` | No | Same as the form upload; the number `3600` and the strings `"3600"` and `"never"` are all accepted |

The response and the use of `Idempotency-Key` are the same as for the form upload. The format of the fetched bytes is determined from their content; the `Content-Type` declared by the remote server plays no part.

### Fetch restrictions

This entry point makes the server send an outbound request on the caller's behalf, so fetching is bound by a fixed set of rules that keep it from being used to probe your internal network:

| Rule | Detail | When violated |
|---|---|---|
| Scheme | Only `http` / `https`, checked again on every redirect hop | 400 |
| Destination | Public addresses only. The check runs right before each connection, against the IP actually resolved, so DNS rebinding and redirects into private networks are both caught | 400 |
| Redirects | Up to 5 are followed; a 6th redirect is an error | 502 |
| Size | Same as the per-image limit (`max_upload_mb`). A declared `Content-Length` over the limit is rejected up front; without one, reading stops once the limit is exceeded | 413 |
| Time | 30 seconds for the whole fetch; establishing the TCP connection, the TLS handshake and waiting for response headers are each capped at 10 seconds | 502 |
| Remote status | 2xx only | 502 |

Rejected address ranges:

- IPv4: `0.0.0.0/8`, `10.0.0.0/8`, `100.64.0.0/10`, `127.0.0.0/8`, `169.254.0.0/16` (including the cloud metadata address `169.254.169.254`), `172.16.0.0/12`, `192.0.0.0/24`, `192.168.0.0/16`, `198.18.0.0/15`, `224.0.0.0/4`, `240.0.0.0/4`.
- IPv6: `::/128`, `::1/128`, `::/96`, `64:ff9b::/96`, `64:ff9b:1::/48`, `2002::/16`, `fc00::/7`, `fe80::/10`, `ff00::/8`. IPv4-mapped addresses (such as `::ffff:127.0.0.1`) are judged by the IPv4 address they contain.

In addition:

- The server connects to the target directly and ignores proxy environment variables such as `HTTP_PROXY`.
- The request carries no `Referer`, not even when following redirects, so the submitted address never leaks to the redirect target. Its `User-Agent` is the Go standard library default. Sources with hotlink protection or bot blocking may refuse it, which shows up as a 502.
- A fetch occupies one upload concurrency slot while it runs; see [Formats and limits](#formats-and-limits).

## Uploading in the admin console

On the **Images** page, click **Upload**. The dialog has two tabs:

- **Local files**: click to pick files or drag images onto the dashed area; you can select several. While the dialog is open, Ctrl / ⌘ + V pastes images straight from the clipboard. At most two files upload at the same time; the rest wait in a queue.
- **Fetch from URL**: enter an image address and click **Fetch**; this works the same as [fetching from a URL](#fetching-from-a-url).

The **Expiry** (Default / Never / Custom hours) and **EXIF** (Default / Strip / Keep) options below apply to files added afterwards. **Default** means the field is not sent.

Closing the dialog does not interrupt uploads in progress. Each finished upload shows its link in the list, ready to copy.

Console uploads belong to the signed-in account and need no token; the image details show the source as "Console upload / token removed". They share the upload rate limit and the upload concurrency limit with token uploads.

## Formats and limits

Only JPEG, PNG, GIF and WebP are accepted. The format is determined from the file content (magic bytes) and cross-checked against what the decoder recognizes; file extensions and the type declared by the client are ignored.

- SVG is not accepted, because it can embed scripts.
- Animated GIFs can be uploaded; they are stored as is and always served as the original, so the animation is kept.
- Animated WebP is not supported; the upload returns 400.

| Limit | Setting | Default | When exceeded |
|---|---|---|---|
| Image size | `max_upload_mb` | 50 MB | 413 |
| Pixel budget | `max_pixels_mp` | 50 megapixels (width × height) | 422 |
| Concurrent uploads | `max_concurrent_uploads` | 8 | 429 with `Retry-After: 1` |
| Upload rate limit | `upload_rate_per_min` | 0 (off) | 429 with `Retry-After: 60` |
| Storage quota | Set per user | Unlimited | 403 |

- **Image size**: only the file itself counts, so a file exactly at the limit is accepted. The request body as a whole is capped separately at the limit + 64 KiB, and exceeding that also returns 413.
- **Pixel budget**: this guards decoded memory, which depends on resolution rather than file size: a 20-megapixel image decodes to about 80 MB of RGBA. The server judges it from the image header alone, so an oversized image never reaches the decoder.
- **Concurrent uploads**: a single limit for the whole site, shared by data API uploads, URL fetches, console uploads and every S3 request (including GET / HEAD / DELETE). It caps how many requests are processed at once. Uploads of any size are processed in memory and never written to temporary files, so this number bounds the peak memory of uploading. When every slot is taken, requests get 429 immediately instead of queueing.
- **Upload rate limit**: per user, and uploads by the same user through tokens, the console and S3 PutObject share one allowance. It is a token bucket: up to N uploads can go through back to back (N being the per-minute allowance), after which one more is allowed every 60/N seconds. The buckets live in process memory and reset on restart.
- **Storage quota**: every reference counts in full. Each image record counts the full size of its physical file against its owner, and background deduplication does not reduce usage. The pre-check uses the size of the uploaded bytes.

All of these are changed under **Settings → Runtime settings** and take effect on save; see [Configuration](../configuration.mdx). Per-user quotas are set on the **Users** page.

### Status codes

| Status | Error code | Meaning |
|---|---|---|
| 200 | — | Success; an idempotency key hit is also 200 |
| 400 | `upload_no_file` | Missing `file` field, or the body is not a valid multipart form |
| 400 | `upload_invalid_image` | Image content cannot be decoded, including animated WebP |
| 400 | `upload_ttl_invalid` | Invalid `ttl` |
| 400 | `upload_exif_policy` | Invalid `exif_policy` |
| 400 | `upload_field_too_long` | `ttl` or `exif_policy` longer than 1 KiB |
| 400 | `url_body_invalid` / `url_required` / `url_scheme` / `url_blocked` | URL fetch: invalid body, empty `url`, a scheme other than http/https, or a destination that is not a public address |
| 401 | `upload_token_invalid` | Token missing, invalid, revoked or expired, or its owner is disabled. Only ever a credential problem |
| 403 | `upload_token_scope` | Token lacks the upload scope |
| 403 | `upload_quota_exceeded` | Storage quota full |
| 413 | `upload_too_large` | The file is over the per-image size limit, or the request body is over the limit + 64 KiB |
| 413 | `url_too_large` | URL fetch: the remote content is over the per-image size limit |
| 415 | `upload_unsupported_type` | Not a supported image format |
| 422 | `upload_too_many_pixels` | Resolution exceeds the pixel budget |
| 429 | `upload_busy` | Every upload concurrency slot is taken; retry after `Retry-After` |
| 429 | `upload_rate_limited` | The user is uploading too fast; retry after `Retry-After` |
| 500 | `internal` | Internal server error, including a database read failure while checking the token; retry later |
| 502 | `url_too_many_redirects` / `url_bad_status` / `url_fetch_failed` | URL fetch: too many redirects, the remote server returned non-2xx, or it timed out or could not be reached |
| 503 | `upload_unavailable` | No healthy channel to write to, or fewer synchronous copies succeeded than **Minimum synced replicas** requires |

## EXIF handling

| Policy | Behavior |
|---|---|
| `passthrough` | Stored byte for byte; no metadata is touched. This is the global default |
| `strip` | Metadata is removed before storing, as listed below |

By default the original is left untouched: whether to strip metadata from what visitors with the link can see is the uploader's choice. Keeping image content from storage providers is the job of [channel encryption](../channels/encryption.mdx), independent of the EXIF policy.

The policy for an upload is the form (or JSON) field if given, otherwise the global default `exif_policy`. Uploads through the S3-compatible API skip EXIF processing and are stored byte for byte, because S3 clients check the upload by size and ETag, so the stored bytes must match what was sent.

`strip` works at the byte level: nothing is re-encoded and no pixel changes:

| Format | Removed | Kept |
|---|---|---|
| JPEG | Every APPn segment except APP0 (JFIF), APP2 (ICC color profile) and APP14 (Adobe), which covers EXIF (GPS, camera model, capture time and so on), XMP, IPTC and vendor segments; COM comment segments; any data after EOI (such as the video in a Motion Photo) | Entropy-coded data is kept untouched. If the original has a non-default orientation tag (Orientation), a minimal EXIF segment holding only the orientation is added back, so the photo still displays upright. Segments between the scans of a progressive JPEG are not inspected |
| PNG | `eXIf`, `tEXt`, `zTXt` and `iTXt` chunks; any data after IEND | `gAMA`, `iCCP` and other chunks that affect color rendering |
| WebP | `EXIF` and `XMP` chunks, clearing the matching flags in the VP8X header and fixing the RIFF length; any data beyond the declared RIFF length | Pixel chunks |
| GIF | Nothing | GIF has no standard container for EXIF / XMP |

An image's SHA-256 (the hash shown in the console and the basis of deduplication) is computed over the bytes actually stored, after stripping.

<Callout type="warn" title="passthrough exposes the original's metadata">
With `passthrough`, GPS and other metadata in the original can be read by anyone who has the link and fetches the original bytes. The variants produced by [on-demand processing](./access.mdx#on-demand-processing) are re-encoded and carry no metadata, but the original itself stays reachable.
</Callout>

### Why processing happens at upload time [#why-on-upload]

The EXIF policy takes effect at upload time, and the processed bytes are what the channels store. Changing the global policy later affects only new uploads; existing images are not reprocessed on access.

This is because an original's bytes never change after upload, and responses carry `Cache-Control: immutable`, so browsers and CDNs can safely cache them for a year. If EXIF were processed on access, changing the global policy would change the bytes served by the same original's link: the CDN cache would have to be purged wholesale, and old bytes already cached in visitors' browsers could not be invalidated at all.

A `/i/` link does not always serve the original: for a JPEG, PNG or WebP original requested without parameters, the format is negotiated from the request's `Accept` header, and variants are generated with the current **Target formats** and encoding quality; see [on-demand processing](./access.mdx#on-demand-processing). After you change these settings, output that is already cached does not update right away: CDN caches update once they expire or are purged manually, and browser caches once they expire (up to a year). See [CDN](../operations/cdn.mdx).

## Uploading the same image more than once

Uploads are not deduplicated on the way in: uploading the same file twice gives two short IDs, and two copies are written to the channels at first.

The background deduplication job (every 300 seconds by default, `dedup_scan_seconds`) merges physical files whose stored bytes are identical into one, and removes the extra copy after the delete grace period. After a merge:

- Each upload keeps its own short ID, lifetime, access count and owner, and every link keeps working.
- Quotas count every reference in full, so a merge does not reduce usage.

The same photo uploaded with different EXIF policies is stored as different bytes and is not merged automatically. Its perceptual hashes are close, so the pair lands in **Duplicates** for an administrator to decide. See [Lifecycle and deduplication](./lifecycle.mdx#deduplication).

Duplicates caused by client retries are best avoided at the source with [idempotency keys](#idempotency-keys).

## What a successful upload means

Before returning, an upload writes to healthy channels one after another in priority order until the number of successful writes reaches **Minimum synced replicas** (`min_success`, 1 by default):

1. If a write fails or times out (each write gets at most 10 minutes), the next healthy channel is tried. The first channel that succeeds is the primary channel for this image.
2. Once enough copies exist, the record is written to the metadata database and the upload returns. The remaining channels are marked as pending and filled by background replication, which does not slow the upload down.
3. If there are not enough healthy channels, or not enough writes succeed after trying them all, the upload returns 503.

With `min_success` above 1, an upload waits until several channels have the bytes before returning, in exchange for having multiple replicas from the start. If fewer channels are healthy than that number, every upload returns 503.

When an upload fails (too few copies, or the metadata database write fails), the objects it already wrote to channels are deleted right away. An object that occasionally cannot be deleted:

- on a channel that is not draining, is deleted as an orphan by the daily reconciliation once it was written more than 48 hours ago;
- on a channel marked as draining during the upload, stays at the provider, because reconciliation skips draining channels and purging deletes only objects on record.

If a target channel is marked as draining during the upload (an administrator chose **Delete and purge**), the copy written to it does not count. If the remaining copies fall short of `min_success`, the upload fails with 503 (`upload_unavailable`, the same as an unavailable channel), and the objects already written are deleted right away.

Channel priority, health checks and replication are covered in [Storage channels](../channels/index.mdx).
