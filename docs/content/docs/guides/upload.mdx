## 上传入口

| 入口 | 认证方式 | 适合 |
|---|---|---|
| `POST /api/upload`（multipart 表单）| 上传 Token | 脚本、PicGo / PicList 自定义图床 |
| `POST /api/upload/url`（JSON）| 上传 Token | 让服务端从别的地址抓取图片入库 |
| 管理后台「图片」页的「上传图片」 | 登录会话 | 拖拽、点选、粘贴剪贴板、链接转存 |
| S3 兼容接口 `/s3/…` | 由上传 Token 派生的 S3 凭证 | 支持 S3 上传的客户端，见[上传客户端](./clients.mdx) |

四个入口走同一条处理流程：格式校验、像素预算检查、配额预检、EXIF 处理、写入渠道、写入元数据库。它们的差别只在字节从哪里来、能带哪些选项：S3 兼容接口不能逐次指定有效期，不做 EXIF 处理，也不支持幂等键。

上传 Token 在后台「上传 Token」页签发，见[管理后台](./admin.mdx#upload-tokens)。

## 用接口上传

最简单的上传：

```bash title="终端"
curl -H "Authorization: Bearer imgy_xxxxxxxx" \
  -F "file=@photo.jpg" \
  https://img.example.com/api/upload
```

带上全部可选项：

```bash title="终端"
curl -H "Authorization: Bearer imgy_xxxxxxxx" \
  -H "Idempotency-Key: 7d0c6a2e-photo-0001" \
  -F "file=@photo.jpg" \
  -F "ttl=604800" \
  -F "exif_policy=strip" \
  https://img.example.com/api/upload
```

| 表单字段 | 必填 | 说明 |
|---|---|---|
| `file` | 是 | 图片文件。只取第一个带文件名的 `file` 段。文件名只作元数据（在后台显示和搜索），去掉控制字符后截断到 255 字节 |
| `ttl` | 否 | 有效期：整数秒（0 到 3153600000）或 `never`，`0` 和 `never` 都表示永久。省略时先取用户默认，没有再取全局默认，见[生命周期与查重](./lifecycle.mdx) |
| `exif_policy` | 否 | `strip` 或 `passthrough`。省略时用全局默认（默认为 `passthrough`），见下文 [EXIF 处理](#exif-处理) |

- `ttl` 和 `exif_policy` 只从 multipart 表单字段读取，写在 URL 查询参数里不生效。
- 这两个字段各自最长 1 KiB，超出返回 400。
- 表单里的其他字段会被忽略。
- 请求头 `Idempotency-Key` 可选，见[幂等键](#幂等键)。

成功时返回 200：

```json
{
  "id": "R0RjUyP1UW",
  "url": "https://img.example.com/i/R0RjUyP1UW"
}
```

- `id` 是 10 位短 ID，字符取自 `0-9A-Za-z`。
- `url` 总是绝对地址。设置了「对外站点地址」（`base_url`）时用它；没有设置时按本次请求推导：协议看连接是否为 TLS，域名取 `Host` 头。
- 请求经信任的反向代理转发时，改用 `X-Forwarded-Proto` 和 `X-Forwarded-Host` 推导。信任哪些代理由环境变量 `IMGYOUNG_TRUSTED_PROXIES` 决定。

<Callout type="warn" title="经反向代理或 CDN 时设置 base_url">
反向代理或 CDN 对外的域名与请求里的域名不一致时，必须设置 `base_url`。见[配置](../configuration.mdx)与[反向代理](../operations/reverse-proxy.mdx)。
</Callout>

失败时返回错误信封，见下节[错误响应](#错误响应)。完整的接口定义见[接口参考：数据面](../api/data-plane.mdx)。

### 错误响应

上传接口和管理后台的所有 JSON 接口失败时都返回同一种错误信封。例外是图片访问接口（返回纯文本错误）和 S3 兼容接口（返回 XML 错误）。

例如单图上限为默认的 50 MB 时上传超大文件，返回：

```json
{
  "code": "upload_too_large",
  "error": "文件超过大小上限(50 MB)",
  "params": { "max": "50" }
}
```

| 字段 | 说明 |
|---|---|
| `code` | 错误码，稳定的机器可读标识。同一种失败总是同一个错误码，不随文案措辞变化 |
| `error` | 填好参数的中文文案。不经过管理后台的调用方（PicGo、ShareX、curl 等）可以直接展示给用户 |
| `params` | 文案里占位符的取值，键为占位符名，值都是字符串；没有参数的错误码不带这个字段 |

- 脚本应按 `code`（配合 HTTP 状态码）判断失败种类，不要匹配 `error` 的文字。
- 管理后台按 `code` 和 `params` 生成当前界面语言的文案，英文界面看到的是英文。
- 上传相关的错误码见下文[状态码速查](#状态码速查)；完整列表见[接口参考：数据面](../api/data-plane.mdx)里的 `ErrorCode`。

curl 默认会输出失败响应的正文（加了 `-f` / `--fail` 时不输出），调试时可以直接看到错误信封：

```bash title="终端"
curl -sS -H "Authorization: Bearer imgy_xxxxxxxx" \
  -F "file=@huge.png" \
  https://img.example.com/api/upload
# {"code":"upload_too_large","error":"文件超过大小上限(50 MB)","params":{"max":"50"}}
```

## 幂等键

网络不稳定时，客户端可能重发同一次上传。请求带上 `Idempotency-Key` 头，重发就不会产生第二张图：

- 保留期内，同一用户带同一个键的请求直接返回第一次成功上传的 `id` 和 `url`，不再写入渠道。保留期由 `idempotency_key_ttl_hours` 决定，默认 24 小时，从第一次成功时算起。
- 命中时不比较请求内容：同一个键换了文件，返回的仍是第一次的那张图。每张不同的图要用不同的键。
- 只有成功的上传才会记下键，失败的请求可以带同一个键放心重试。
- 同时发出的多个同键请求只有一个会入库，其余返回同一结果，它们已经写进渠道的对象随即删除。
- 键按用户隔离：不同用户用同一个键互不影响，也就无法借幂等键探测或取到别人的图。
- 超过保留期，或者对应的图片已被删除或已到期，再用这个键会被当作新的上传。

`/api/upload` 和 `/api/upload/url` 都支持幂等键，S3 兼容接口不支持。URL 转存命中时直接返回第一次的结果，不会再去抓取远端。

## URL 转存

给出一个图片地址，服务端会替你下载并入库，常用来把散在其他图床的图片收回来。抓回的字节与直接上传走同一条处理流程，格式白名单、像素预算、EXIF 处理和配额照常生效；服务端不会把远端文件直接复制进渠道。

```bash title="终端"
curl -H "Authorization: Bearer imgy_xxxxxxxx" \
  -H "Content-Type: application/json" \
  -d '{"url": "https://example.com/photo.png", "ttl": "never"}' \
  https://img.example.com/api/upload/url
```

请求体是不超过 8 KiB 的 JSON 对象，只允许以下字段，出现其他字段返回 400：

| 字段 | 必填 | 说明 |
|---|---|---|
| `url` | 是 | 图片地址，仅限 `http` / `https` |
| `file_name` | 否 | 文件名。省略时取地址路径的最后一段，取不到时为 `fetched` |
| `exif_policy` | 否 | 同表单上传 |
| `ttl` | 否 | 同表单上传；数字 `3600` 与字符串 `"3600"`、`"never"` 都接受 |

返回体和 `Idempotency-Key` 的用法与表单上传相同。抓回的内容按字节判定格式，远端声明的 `Content-Type` 不参与判断。

### 抓取限制

这个入口会让服务端替调用方访问外部地址，所以抓取受一组固定规则约束，防止被用来探测你的内网：

| 规则 | 说明 | 不满足时 |
|---|---|---|
| 协议 | 只允许 `http` / `https`，重定向的每一跳都会检查 | 400 |
| 目标地址 | 只允许公网地址。每次建立连接前都按实际解析出的 IP 检查，所以 DNS 重绑定和重定向到内网都会被拦下 | 400 |
| 重定向 | 最多跟随 5 次，第 6 次重定向即报错 | 502 |
| 大小 | 与单图上限相同（`max_upload_mb`）。远端声明的 `Content-Length` 超限时直接拒绝；没有声明时，读到超限即停止 | 413 |
| 时长 | 整次抓取最长 30 秒；其中建立 TCP 连接、TLS 握手、等待响应头各不超过 10 秒 | 502 |
| 远端状态码 | 只接受 2xx | 502 |

被拒绝的地址段：

- IPv4：`0.0.0.0/8`、`10.0.0.0/8`、`100.64.0.0/10`、`127.0.0.0/8`、`169.254.0.0/16`（含云厂商元数据地址 `169.254.169.254`）、`172.16.0.0/12`、`192.0.0.0/24`、`192.168.0.0/16`、`198.18.0.0/15`、`224.0.0.0/4`、`240.0.0.0/4`。
- IPv6：`::/128`、`::1/128`、`::/96`、`64:ff9b::/96`、`64:ff9b:1::/48`、`2002::/16`、`fc00::/7`、`fe80::/10`、`ff00::/8`。IPv4 映射地址（如 `::ffff:127.0.0.1`）按其中的 IPv4 地址判定。

此外：

- 抓取直接连接目标，不使用 `HTTP_PROXY` 等代理环境变量。
- 请求不带 `Referer`，跟随重定向时也不带，提交的地址不会泄露给重定向目标。`User-Agent` 是 Go 标准库的默认值。开启了防盗链或屏蔽爬虫的源站可能拒绝请求，表现为 502。
- 抓取期间占用一个上传并发名额，见[格式与上限](#格式与上限)。

转存单张图片用这里；要成批搬迁旧图床或博客里的图片，用[批量导入](./import.mdx)。

## 在管理后台上传

在「图片」页点「上传图片」，对话框里有两个标签：

- 「本地文件」：点击选择，或把图片拖进虚线框，可以多选。对话框打开期间，按 Ctrl / ⌘ + V 可以直接粘贴剪贴板里的图片。每次最多同时上传两个文件，其余排队。
- 「链接转存」：填入图片地址后点「转存」，效果与 [URL 转存](#url-转存)相同。

对话框下方的「有效期」（默认 / 永久 / 自定义小时数）和「EXIF」（默认 / 剥离 / 保留）对之后加入的文件生效。选「默认」时不传这个字段。

关闭对话框不会中断进行中的上传。每张图上传成功后，列表里会显示它的链接，可以直接复制。

后台上传归属当前登录的账号，不需要 Token，图片详情里的「来源」显示为「后台上传 / 来源已删除」。后台上传与 Token 上传共用上传频率上限和上传并发上限。

## 格式与上限

只接受 JPEG、PNG、GIF 和 WebP。格式按文件内容（magic bytes）判定，并与解码器识别出的格式交叉核对，扩展名和客户端声明的类型一概不看。

- 不接受 SVG，因为它可以内嵌脚本。
- 动画 GIF 可以上传，原样保存；访问时始终输出原图，动画保留。
- 不支持动画 WebP，上传返回 400。

| 限制 | 配置键 | 默认值 | 超出时 |
|---|---|---|---|
| 单图大小 | `max_upload_mb` | 50 MB | 413 |
| 像素预算 | `max_pixels_mp` | 50 百万像素（宽 × 高）| 422 |
| 上传并发上限 | `max_concurrent_uploads` | 8 | 429，响应头 `Retry-After: 1` |
| 上传频率上限 | `upload_rate_per_min` | 0（不启用）| 429，响应头 `Retry-After: 60` |
| 存储配额 | 每个用户单独设置 | 不限 | 403 |

- **单图大小**：只算文件本身，大小恰好等于上限的文件可以上传。整个请求体另以「单图上限 + 64 KiB」为界，超出同样返回 413。
- **像素预算**：限制的是解码后占用的内存。它由分辨率决定，与文件大小无关：一张 2000 万像素的图解码成 RGBA 约 80 MB。服务端只读图片头就能判断，超限的图不会进入解码。
- **上传并发上限**：全站只有一个，数据接口上传、URL 转存、后台上传和所有 S3 请求（包括 GET / HEAD / DELETE）共用。它限制的是同时处理的请求数。上传内容无论大小都只在内存里处理、不写临时文件，所以这个值决定了上传的峰值内存。名额满时立即返回 429，不排队。
- **上传频率上限**：按用户计，同一用户经 Token、后台和 S3 PutObject 的上传共用一份额度。算法是令牌桶：可以连续上传 N 张（N 为每分钟额度），之后每 60/N 秒恢复一张。额度保存在进程内存里，重启后重置。
- **存储配额**：按引用计全额，每条图片记录都按其物理文件的完整大小计入归属用户，后台查重合并不会减少已用量。预检使用上传时的原始字节数。

以上配置都在「设置 → 运行配置」里修改，保存即生效，见[配置](../configuration.mdx)。用户配额在「用户」页设置。

### 状态码速查

| 状态码 | 错误码 | 含义 |
|---|---|---|
| 200 | — | 成功，幂等键命中时也是 200 |
| 400 | `upload_no_file` | 缺少 `file` 字段，或请求体不是合法的 multipart 表单 |
| 400 | `upload_invalid_image` | 图片内容无法解析，包括动画 WebP |
| 400 | `upload_ttl_invalid` | `ttl` 取值不合法 |
| 400 | `upload_exif_policy` | `exif_policy` 取值不合法 |
| 400 | `upload_field_too_long` | `ttl` 或 `exif_policy` 超过 1 KiB |
| 400 | `url_body_invalid` / `url_required` / `url_scheme` / `url_blocked` | URL 转存：请求体不合法、`url` 为空、协议不是 http/https、目标不是公网地址 |
| 401 | `upload_token_invalid` | Token 缺失、无效、已吊销、已过期，或所属用户已被禁用。只表示凭证本身有问题 |
| 403 | `upload_token_scope` | Token 没有上传权限 |
| 403 | `upload_quota_exceeded` | 存储配额已满 |
| 413 | `upload_too_large` | 文件超过单图大小上限，或请求体超过「单图上限 + 64 KiB」|
| 413 | `url_too_large` | URL 转存：远端内容超过单图大小上限 |
| 415 | `upload_unsupported_type` | 不是支持的图片格式 |
| 422 | `upload_too_many_pixels` | 分辨率超过像素预算 |
| 429 | `upload_busy` | 上传并发名额已满，按 `Retry-After` 稍后重试 |
| 429 | `upload_rate_limited` | 该用户上传过于频繁，按 `Retry-After` 稍后重试 |
| 500 | `internal` | 服务内部错误，包括校验 Token 时读取数据库失败；可以稍后重试 |
| 502 | `url_too_many_redirects` / `url_bad_status` / `url_fetch_failed` | URL 转存：重定向过多、远端返回非 2xx、超时或连接失败 |
| 503 | `upload_unavailable` | 没有健康渠道可写，或同步写入的份数达不到「最少同步副本」 |

## EXIF 处理

| 档位 | 行为 |
|---|---|
| `passthrough` | 原样保存，不改动任何元数据。这是全局默认档位 |
| `strip` | 剥离元数据后保存，范围见下表 |

默认不改动原图：是否对拿到链接的访客隐去元数据，由上传者自己选择。不让存储商看到图片内容，由[渠道存储加密](../channels/encryption.mdx)负责，与 EXIF 档位无关。

每次上传的档位以表单字段（或 JSON 字段）为准，没有时用全局默认 `exif_policy`。S3 兼容接口的上传不做 EXIF 处理，一律按原字节保存，因为 S3 客户端按大小和 ETag 核对上传结果，保存的字节必须与上传的一致。

`strip` 在字节层面操作，不重新编码，也不改动任何像素：

| 格式 | 剥离 | 保留 |
|---|---|---|
| JPEG | 除 APP0（JFIF）、APP2（ICC 色彩配置）、APP14（Adobe）之外的全部 APPn 段，包括 EXIF（GPS、机型、拍摄时间等）、XMP、IPTC 与相机私有段；COM 注释段；EOI 之后的附加数据（如 Motion Photo 里的视频）| 熵编码数据原样保留。原图带非默认的方向标记（Orientation）时，补回一个只含方向的最小 EXIF 段，照片仍按正确方向显示。渐进式 JPEG 各次扫描之间的段不检查 |
| PNG | `eXIf`、`tEXt`、`zTXt`、`iTXt` 块；IEND 之后的附加数据 | `gAMA`、`iCCP` 等影响颜色渲染的块 |
| WebP | `EXIF` 与 `XMP` chunk，并同步清除 VP8X 头里对应的标志位、修正 RIFF 长度；RIFF 声明长度之外的附加数据 | 像素 chunk |
| GIF | 不处理 | GIF 没有承载 EXIF / XMP 的标准容器 |

图片的 SHA-256（后台显示的哈希，也是查重的依据）按剥离后实际保存的字节计算。

<Callout type="warn" title="passthrough 会公开原图里的元数据">
用 `passthrough` 保存的原图里如果有 GPS 等信息，任何拿到链接的人都能取到原始字节并读出来。[按需处理](./access.mdx#on-demand-processing)输出的衍生图经过重新编码，不带元数据，但原图本身仍然可以访问。
</Callout>

### 为什么在上传时处理 [#why-on-upload]

EXIF 档位在上传时生效，渠道里保存的就是处理后的字节。之后修改全局档位只影响新的上传，访问已有图片时不会按新设置重新处理。

这是因为原图的字节在上传后不再改变，响应带 `Cache-Control: immutable`，浏览器和 CDN 可以放心缓存一年。如果在访问时处理 EXIF，修改全局档位后，同一张原图的链接就会输出不同的字节：CDN 上的缓存要整体清除，访客浏览器里已经缓存的旧内容也无法失效。

`/i/` 链接输出的不一定是原图：JPEG、PNG 原图不带参数访问时，按请求的 `Accept` 协商格式，转出的衍生图按当前的「目标格式」和编码质量生成，见[按需处理](./access.mdx#on-demand-processing)。修改这些设置后，已经缓存的输出不会立即更新：CDN 上的缓存要等过期或手动清除，浏览器里的要等过期（最长一年）。见 [CDN](../operations/cdn.mdx)。

## 同一张图多次上传

上传时不查重：同一个文件上传两次，会得到两个短 ID，渠道里也会先写入两份。

后台查重任务（默认每 300 秒一轮，`dedup_scan_seconds`）会把保存字节完全相同的物理文件自动合并为一份，多余的那份在删除宽限期后清理。合并后：

- 每次上传仍有自己的短 ID、有效期、访问计数和归属用户，所有链接继续可用。
- 配额按引用计全额，合并不会减少已用量。

用不同 EXIF 档位上传的同一张照片，保存的字节不同，不会自动合并；它们的感知哈希相近，会进入「疑似重复」，由管理员裁决。见[生命周期与查重](./lifecycle.mdx#deduplication)。

客户端重试造成的重复，用[幂等键](#幂等键)从源头避免。

## 写入语义

一次上传在返回之前，按优先级从高到低依次写入健康渠道，直到写成功的份数达到「最少同步副本」（`min_success`，默认 1）：

1. 某个渠道写入失败或超时（每次写入最长 10 分钟），就换下一个健康渠道。第一个写成功的渠道就是这张图的主渠道。
2. 份数够了之后写入元数据库并返回。其余渠道记为待补齐，由后台异步复制，不拖慢这次上传。
3. 健康渠道不够，或者全部试过后份数仍不够，返回 503。

`min_success` 大于 1 时，上传要等多个渠道都写完才返回，换来的是返回时就已有多份副本。健康渠道少于这个数时，上传一律返回 503。

上传失败时（份数不够，或写入元数据库失败），这次已经写进渠道的对象会随即删除。个别没能删掉的对象：

- 在不处于清理中的渠道上，由每日对账在写入 48 小时后作为无主对象删除。
- 在上传期间被标为「清理中」的渠道上，会留在存储商处，因为对账不检查清理中的渠道，清理也只删除有记录的对象。

上传过程中，如果某个目标渠道被标为「清理中」（管理员选了「删除并清理」），写到它上面的副本不计入成功份数。剩下的副本不足 `min_success` 时，上传失败并返回 503（`upload_unavailable`，与渠道不可用时相同），已经写下的对象随即删除。

渠道的优先级、健康探测与补齐见[存储渠道](../channels/index.mdx)。
