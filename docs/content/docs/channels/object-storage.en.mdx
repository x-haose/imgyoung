## Choosing a storage type

After **New channel** on the Storage channels page, you first pick a type:

- **Object storage**: **Amazon S3**, **Cloudflare R2**, **Tencent Cloud COS**, **Alibaba Cloud OSS**, **Backblaze B2**, **MinIO / self-hosted** and **S3-compatible (generic)**. All of them use rclone's `s3` backend and differ only in the preset `provider`, endpoint and region.
- **Cloud drives**: WebDAV (later on this page) and the drives that need authorization (see [Cloud drives and OAuth](./cloud-drives.mdx)).
- **Advanced**: **Custom**, where you enter an rclone backend name and raw parameters.

Templates expose only the fields that matter and preset the rest. Saving merges them into the full backend parameters; editing reverses the merge to refill the form, including fields that were folded into the endpoint (account ID, region).

## Object storage templates

| Template | Fields to fill | Set by the template |
|---|---|---|
| Amazon S3 | Access key ID, Secret access key, Region (list), Bucket | `provider=AWS`; the endpoint follows from the region |
| Cloudflare R2 | Access key ID, Secret access key, Account ID, Bucket | `provider=Cloudflare`, `region=auto`, `endpoint=https://<account ID>.r2.cloudflarestorage.com` |
| Tencent Cloud COS | SecretId, SecretKey, Region (list), Bucket | `provider=TencentCOS`, `endpoint=cos.<region>.myqcloud.com` |
| Alibaba Cloud OSS | Access key ID, Secret access key, Region (list), Bucket | `provider=Alibaba`, `endpoint=<region>.aliyuncs.com` |
| Backblaze B2 | Key ID, Application key, Region (typed), Bucket | `provider=Other`, `endpoint=https://s3.<region>.backblazeb2.com` |
| MinIO / self-hosted | Access key ID, Secret access key, Endpoint, Bucket | `provider=Minio` |
| S3-compatible (generic) | Access key ID, Secret access key, S3 API endpoint, Bucket | `provider=Other` |

Every object storage template also has an optional **Public URL**, described below. The fields:

| Key | Label | Meaning |
|---|---|---|
| `access_key_id`, `secret_access_key` | Access key ID / Secret access key (COS: SecretId / SecretKey; B2: Key ID / Application key) | Credentials |
| `region` | Region | Region. Lists show the region name followed by its code, such as US East (Ohio) `us-east-2`. AWS, COS and OSS offer a list of common regions; Alibaba values carry the `oss-` prefix (such as `oss-cn-hangzhou`). If your region is missing, use the S3-compatible template with an explicit endpoint. B2 takes free text (such as `us-west-004`) matching the endpoint shown in the B2 console |
| `account_id` | Account ID | Cloudflare account ID, used to build the R2 endpoint |
| `endpoint` | Endpoint / S3 API endpoint | Full URL, such as `https://minio.example.com` |
| `bucket` | Bucket | Bucket name, optionally followed by `/prefix` to confine the channel to a folder: `my-bucket` or `my-bucket/imgyoung`. This value is the channel's storage path. COS bucket names must include the APPID suffix, such as `mybucket-1250000000` |
| `public_base_url` | Public URL | Optional public URL prefix, see below |

## Create the bucket first

ImgYoung adds `no_check_bucket=true` to every `s3` channel, so rclone neither checks for nor creates the bucket before uploading.

The reason: by default rclone attempts to create the bucket before uploading. Scoped credentials, common with R2 and MinIO, can read and write one bucket but not create buckets; when the bucket already exists that attempt returns 403 and the write fails, while the read-only light check keeps passing. The channel looks healthy yet uploads fail. Buckets are expected to exist already, so the attempt is skipped by default.

So:

- **Create the bucket in your provider's console first**, then create the channel.
- If your credentials can create buckets and you want ImgYoung to do it, turn on **Create the bucket automatically** in the create form. ImgYoung then tries to create the bucket once (an existing bucket is fine); if that fails the whole creation is aborted with 400 and error code `channel_bucket_failed` ("Creating the bucket failed (check that the key may create buckets, or create the bucket in the console and turn this option off): " followed by the root cause). The switch only exists at creation, and **Test connection** never creates a bucket.
- In custom mode, setting `no_check_bucket=false` explicitly restores rclone's check-and-create-if-missing before uploads.

## Public URL and 302 direct links

**Public URL** (`public_base_url`) is optional: the URL prefix under which the bucket (or a CDN in front of it) serves objects publicly, such as `https://cdn.example.com`. A channel can only issue 302 direct links once it is set.

A direct link is `<public URL>/<object key>`, and the object key is relative to the channel's storage path. If the **Bucket** field includes a prefix, the public URL must point at that prefix too: with `my-bucket/imgyoung` in **Bucket** and a CDN serving the whole bucket, the public URL is `https://cdn.example.com/imgyoung`. A trailing `/` is stripped.

An image is redirected only when all of these hold:

1. **Settings → Runtime settings → Access & links → Access mode** is `redirect · 302 to direct links`;
2. the channel has **Allow 302 direct links** on and is not encrypted;
3. the channel has a public URL;
4. the channel is healthy, holds a ready replica of the image, and is the highest-priority channel meeting the conditions above;
5. the request does not produce a variant: one with `w`, with an explicit `format` other than the original's, or negotiated to WebP through `Accept` (the default for browsers opening a JPEG / PNG) is converted and proxied.

Otherwise the image is proxied. With **Allow 302 direct links** on but no public URL, the form warns "public_base_url is not set, so direct links will not take effect and access falls back to proxying".

The 302 response carries `Cache-Control: no-store`, so neither browsers nor CDNs cache the redirect, and switching channels, retiring one or an image expiring takes effect immediately. Objects are written with a `Content-Type` sniffed from their content, so even though object keys have no extension, a browser opening a direct link displays the image.

Public read access on the bucket has to be enabled at the provider; ImgYoung does not check it. Public read also means anyone holding a direct link can fetch the object without going through ImgYoung, so hotlink protection only applies to requests that do. See [Access and links](../guides/access.mdx) for the full picture of access modes.

## Custom mode

**Advanced → Custom** takes an rclone backend name and its parameters directly. Use it for backends the templates do not cover — any rclone backend works, such as `sftp`, `ftp`, `azureblob`, or `local` on another disk.

- **rclone backend**: the backend name, i.e. the `type` value in `rclone.conf`, such as `s3`, `sftp` or `local`.
- **Backend parameters**: key–value pairs whose keys are the backend's option names, written as in `rclone.conf`; only letters, digits and underscores are allowed. Copying from the output of `rclone config show` works (put the `type` line into **rclone backend**).
- Two reserved keys are not passed to rclone: `path` is the storage path inside the backend (bucket and prefix, or a folder), and `public_base_url` is the public URL. The `path` of a `local` backend must be absolute (a relative path is rejected with 400 and error code `channel_local_path_relative`); without `path` it uses `<data dir>/blobs`.
- Parameter values are always shown as masked inputs (each can be revealed): the console cannot tell which custom keys are credentials.

rclone stores password-type options (options rclone flags as passwords, such as `pass` for `sftp`, `ftp` and `webdav`) in an encoded form. ImgYoung handles this: plain values are encoded, and values that already are encoded (for example copied from `rclone.conf`) are kept as they are. In rare cases a plain password happens to look like an encoded value and is passed through unencoded, which shows up as an authentication failure; run `rclone obscure <password>` and enter its output instead.

```text title="Example: an SFTP channel"
rclone backend       sftp
Backend parameters   host = files.example.com
                     user = imgyoung
                     pass = <password>
                     path = /srv/imgyoung
```

## WebDAV

The generic WebDAV template sits in the **Cloud drives** group of the type picker and covers Nutstore, Nextcloud / ownCloud, Synology, Alist and the like. They all use rclone's `webdav` backend and differ only in the server URL and the server type, so there is one template for all of them.

| Key | Label | Meaning |
|---|---|---|
| `url` | Server URL | WebDAV root URL. Nutstore `https://dav.jianguoyun.com/dav/`; Nextcloud / ownCloud `https://domain/remote.php/dav/files/username/`; Alist `https://domain/dav/`; Synology `https://domain:5006/` |
| `vendor` | Server type | A wrong choice breaks folder listing or chunked uploads; if unsure, choose **Other (Nutstore, Alist, Synology, …)** |
| `user` | Username | WebDAV user name |
| `pass` | Password | Nutstore requires an **app password** generated in its security settings, not the login password |
| `path` | Folder | Folder for the images, `imgyoung` suggested; empty means the root |

Server type options and the rclone `vendor` value each maps to:

| Option | `vendor` |
|---|---|
| Nextcloud | `nextcloud` |
| ownCloud 10 | `owncloud` |
| ownCloud Infinite Scale | `infinitescale` |
| SharePoint Online | `sharepoint` |
| SharePoint (self-hosted, NTLM) | `sharepoint-ntlm` |
| Fastmail Files | `fastmail` |
| rclone serve webdav | `rclone` |
| Other (Nutstore, Alist, Synology, …) | `other` |

WebDAV channels have no public URL, and the form hides **Allow 302 direct links** and **Create the bucket automatically**; reads are always proxied. Chinese cloud drives such as Aliyun Drive and Baidu Netdisk are also connected over WebDAV, see [Cloud drives and OAuth](./cloud-drives.mdx).

## Common errors

### Failure reasons

The failure reason from **Test connection**, the reason shown when hovering **Unhealthy** in the Status column, and a replica's sync failure in the image details are all the same kind of conclusion: the underlying error is classified by its text (case-insensitive, first match from the top), and the root cause follows the classification in parentheses. The root cause is the innermost error of the error chain, usually the provider's or network library's own English text, with credentials scrubbed (the values of parameters rclone flags as passwords or sensitive) and at most 200 characters (a longer one is cut to 199 characters followed by "…"). If nothing matches, only the root cause is shown.

In the API this conclusion is `{reason, detail}` (a channel's conclusion also carries the stage, see [Channels and failover](./index.mdx)). The classifications, with the text the console shows in English:

| Classification (`reason`) | Console text | Underlying error contains | What to check |
|---|---|---|---|
| `s3_auth` | "Authentication failed (403): check the Access Key / Secret Key and their permissions" | `InvalidAccessKeyId`, `SignatureDoesNotMatch`, `StatusCode: 403` (S3-type backends only) | Mistyped or revoked keys, or missing read, write or delete permission on the bucket. Read-only keys fail at the write step of the deep check |
| `app_credentials` | "Invalid app credentials: check that the Client ID / Client Secret belong to the app that issued the token" | `invalid_client`, `unauthorized_client` | A drive channel's app client ID or secret is wrong, or belongs to a different app than the one that issued the token |
| `grant_revoked` | "Authorization expired: the refresh token was rejected. Authorize again" | `invalid_grant` | The token was revoked or has lapsed; use **Authorize again** in the edit form |
| `auth` | "Authentication failed (401): check the username, password or authorization token" | `401 Unauthorized`, `unauthenticated`, `InvalidAuthenticationToken` | The WebDAV user name or password (Nutstore needs an app password), or a drive's authorization token |
| `forbidden` | "Access denied (403): check the account’s permissions on the storage location" | `AccessDenied`, `access denied`, `403 Forbidden` | On non-S3 backends, the account lacks read, write or delete permission on the folder |
| `bucket_missing` | "The bucket does not exist or is not accessible: check the bucket name and credential permissions" | `NoSuchBucket`, `no such bucket`, `BucketRegionError` | The bucket name (COS needs the APPID suffix); whether the bucket exists |
| `region_mismatch` | "Region mismatch: check that the selected region matches the bucket’s region" | `PermanentRedirect`, `AuthorizationHeaderMalformed` | The region or endpoint does not match the bucket's actual region |
| `dns` | "Cannot resolve the endpoint host: check the endpoint setting" | `no such host`, `server misbehaving` | A typo in the endpoint, or DNS on the server |
| `connect` | "Cannot connect to the endpoint: check its address and port" | `connection refused`, `connection reset` | Port, scheme or firewall |
| `tls` | "TLS certificate verification failed: check the endpoint certificate or use the right protocol" | `certificate`, `x509`, `tls handshake` (except `TLS handshake timeout`, which counts as `timeout`) | A self-signed certificate, or `https` used for an `http` service |
| `timeout` | "Connection timed out: check the endpoint address and network connectivity" | Timeouts, including `TLS handshake timeout`, the check's own 10 s / 20 s limits and the 30 s load limit (root cause `context deadline exceeded`) | Network reachability or a very slow service |
| `permission` | "No write permission on the storage path: check the directory permissions" | `permission denied`, `read-only file system` | Folder permissions of a `local` channel; in the container image the process runs as uid 65532, so mounted folders must be writable by it |
| `probe_mismatch` | "The probe object read back differently: the storage rewrote or truncated it" | The deep check read back something other than what it wrote | The storage service silently rewrites or truncates objects; check its settings or use another service |
| `config_unreadable` | "The channel settings cannot be decrypted: the master key differs from the one they were written with" | The channel configuration cannot be decrypted while loading | Switch back to the master key the configuration was written with |
| `no_source` | "No readable source replica" | No readable source replica while syncing | Replicas only: every channel holding a ready replica is unhealthy or failed to read |
| `channel_unavailable` | "The target channel is not loaded" | The sync target channel is not loaded | Replicas only: fix the channel's load failure first |
| `object_missing` | "Reconciliation found the object missing from the channel" | The daily reconciliation found a replica marked ready missing from the channel | Replicas only: the replica went back to pending and is copied again |
| `unclassified` | Root cause only | Nothing above matches | Read the root cause |

### Rejections when saving the form

These errors come back with 400 as soon as you submit, and no channel is created (a duplicate name, a draining channel and a concurrent change get 409). Error responses are `{code, error, params}`: `code` is a stable error code, `error` the server's Chinese message, and `params` fills the placeholders in it; the console shows the message for the code and parameters in its own language.

| Error code | Console text | Cause |
|---|---|---|
| `channel_field_required` | "Invalid channel settings: field `{field}` is required" | A required template field is empty; the field is named by its key, such as `bucket` |
| `channel_name_exists` | "A channel with this name already exists" | The channel name is taken (409) |
| `channel_backend_failed` | "Invalid channel settings: the backend failed to initialize: `{detail}`" | Building the backend from these parameters failed, or selecting the drive for a newly authorized OneDrive channel failed when querying the provider; `params` also carries the classification `reason`, and `detail` is the root cause |
| `channel_unknown_backend` | "Invalid channel settings: unknown backend `{driver}`" | A misspelt backend name in custom mode |
| `channel_local_path_relative` | "Invalid channel settings: the path of a local channel must be absolute, got `{path}`" | A relative `path` for a `local` channel |
| `channel_config_key_invalid` | "Invalid channel settings: parameter key `{key}` is invalid (only letters, digits and underscores)" | A custom parameter key contains other characters (such as `-`) |
| `channel_bucket_failed` | "Creating the bucket failed (check that the key may create buckets, or create the bucket in the console and turn this option off): `{detail}`" | **Create the bucket automatically** is on but the key cannot create buckets |
| `channel_keep_not_secret` | "Invalid channel settings: field `{field}` is not a credential, so its stored value cannot be kept" | The mask value `__imgyoung_secret_keep__` was put on a parameter that is not a credential |
| `channel_keep_no_value` | "Invalid channel settings: field `{field}` has no stored value to keep. Fill it in again" | The mask value was submitted for a parameter that has no stored value |
| `channel_deleting` | "The channel is being cleaned up and cannot be changed or probed" | The channel is **Draining** (409) |
| `channel_config_changed` | "The channel configuration changed while saving (another edit, or the provider refreshed the authorization token). Save again" | Another edit or a token write-back changed the channel configuration while this edit was being saved (409); just save again |

Once a channel exists but shows **Unhealthy**, fix its configuration and use **Probe again** in the row menu: it runs a deep check right away and refreshes the status. The probe and status rules are in [Channels and failover](./index.mdx).
