## What a channel is

A channel is where images are actually stored. Each channel is one rclone backend instance: a backend type (`s3`, `webdav`, `local` and so on) plus its parameters, plus a few ImgYoung attributes:

| Attribute | Meaning |
|---|---|
| Channel name | Unique, up to 64 bytes; used in the UI, logs, metrics and alerts |
| Priority | Integer, higher wins; the admin console accepts 0–1000 and defaults to 100 |
| Server-side encryption | Whether data is stored through rclone crypt; cannot be changed after creation, see [Channel encryption](./encryption.mdx) |
| Allow 302 direct links | Whether reads may be redirected to the channel's public URL, see [Object storage and WebDAV](./object-storage.mdx) |

Channels are created and managed on the **Storage channels** page of the admin console, which only admins can see; the API is under [admin channels](../api/admin-channels.mdx). Backend parameters are handed to rclone directly, never through `rclone.conf`, and the whole parameter set is stored in the metadata database encrypted with the master key (AES-256-GCM).

Channel objects in the API and in the metadata export carry `created_at`, the channel's creation time (UTC). Together with the channel ID it feeds the key derivation for encrypted channels, and it never changes. Channel IDs are never reused: a channel created after deleting another gets a new ID.

**Every channel ends up holding a replica of every image.** Channels mirror each other in full; nothing is sharded. Size each channel for the whole library.

<Callout type="error" title="Two instances must not share a channel path">
The daily reconciliation deletes objects that ImgYoung wrote but the metadata database has no record of (orphans). If two ImgYoung instances use the same storage path, objects written by the other instance are orphans to this one and are deleted after 48 hours. Give each instance its own bucket or path. Files other programs write to the same path are only counted, never deleted. The exact rules are under [Reconciliation GC](../operations/backup.mdx#reconciliation-gc).
</Callout>

## The built-in local channel

On first start with a fresh metadata database, ImgYoung creates a channel named `local`: backend `local`, priority 100, stored under `<data dir>/blobs`. Uploads work with no configuration at all.

- The channel is created only this once, on a fresh metadata database. Once you delete or rename it, restarts do not bring it back, even if you delete every channel.
- The `path` of a `local` channel must be absolute; leaving it empty uses `<data dir>/blobs`.

<Callout type="warn" title="When the local disk is the only channel">
The built-in local channel lives on the same machine as the metadata database and the master key, so losing the host loses everything. While it is the only channel, the Storage channels page shows **Only the local disk is configured**. Add an off-site channel and existing images are replicated to it automatically; from the next backup on, the new channel holds metadata snapshots too.
</Callout>

## Creating a channel

On the Storage channels page click **New channel**, choose a storage type, then fill in the form:

<Steps>
<Step>
Choose a type: **Object storage** and **Cloud drives** hold the built-in templates, **Advanced** holds **Custom** (an rclone backend name plus raw parameters). Template fields are described in [Object storage and WebDAV](./object-storage.mdx) and [Cloud drives and OAuth](./cloud-drives.mdx).
</Step>
<Step>
Fill in the channel name, the template fields and the priority, and choose **Server-side encryption**. Object storage also offers **Allow 302 direct links** and **Create the bucket automatically**.
</Step>
<Step>
Click **Test connection**, and once it passes, **Create**.
</Step>
</Steps>

ImgYoung first builds the backend once from the parameters you entered and rejects invalid ones outright. Templates that need authorization first fill in what the authorization implies, such as the OneDrive drive.

Once the channel is stored, a deep check runs immediately (see [Health checks](#health-checks)). A failed deep check does not undo the creation: the channel stays, marked **Unhealthy**, with the notice "Channel created, but the probe failed:" plus the reason. Fix the configuration and click **Probe again**.

After the channel is created, every existing image is replicated to it automatically; see [Asynchronous replication](#asynchronous-replication).

## Test connection

**Test connection** at the bottom of the create and edit forms runs a deep check with the current form contents, **without saving or creating anything**.

- Success shows "Connection OK (write, read and delete probes passed)". Failure shows "Connection failed:" followed by the failure reason, written the same way as in the Status column (see [Failure reasons](#failure-reasons)), with credentials scrubbed.
- It never creates a bucket and never applies encryption: it only verifies connectivity and write, read and delete permissions on the backend.
- When editing, masked credentials are replaced with the stored values before the check runs.
- The API responds with `{ok, failure}`, where `failure` is `{reason, detail}` on failure.

The provider may refresh a cloud drive's authorization token during a connection test or a save. The new token is never lost; where it goes is described in [Cloud drives and OAuth](./cloud-drives.mdx#token-refreshes-during-tests-and-saves).

## Primary and backup channels

There is no separate "primary" switch; priority alone decides which channel is primary:

- **Primary channel**: the highest-priority channel that is healthy and not draining. The list marks it **Primary**.
- **Backup channels**: all the others. Normally uploads do not write to them directly, and asynchronous replication copies the replicas over. Uploads write to them synchronously only when a higher-priority channel fails to accept the write, or when **Minimum synced replicas** is above 1.
- On equal priority, the channel created first wins.

When the primary turns unhealthy, the next healthy channel takes over with no manual step. Once the original primary recovers, it is primary again.

## Upload writes

Each upload walks the currently healthy channels from highest to lowest priority and writes synchronously until **Minimum synced replicas** (`min_success`) copies have succeeded:

1. If a write fails (including the 10-minute per-write timeout), the next healthy channel is tried.
2. As soon as enough copies exist, the upload succeeds. The first channel that accepted the write holds the image's first replica.
3. Every other channel, including temporarily unhealthy ones, gets a pending replica for asynchronous replication.

**Minimum synced replicas** lives under **Settings → Runtime settings → Access & links → Minimum synced replicas** (default 1, minimum 1).

The upload fails with 503 (error code `upload_unavailable`), and no metadata is recorded, when:

- there are not enough healthy channels, or every write fails;
- a channel the upload already wrote to turns **Draining** in the meantime, so its copy no longer counts, and the remaining copies fall short of **Minimum synced replicas**.

Whichever step an upload fails at, the objects it wrote to channels are deleted right away. Anything that could not be deleted is reclaimed as an orphan by the daily reconciliation.

<Callout type="info">
If **Minimum synced replicas** exceeds the number of healthy channels, every upload fails. Setting it to 2 means an upload only succeeds once two channels hold it, at the cost of higher write latency and a dependency on several channels being up at once.
</Callout>

## Asynchronous replication

Channels the upload did not write to synchronously receive their replicas from a background job; this is called replication. Each image has a replica state on each channel:

| Replica state | Meaning |
|---|---|
| `pending` | Waiting to be replicated |
| `uploading` | Replication in progress |
| `done` | Ready to serve reads |
| `failed` | Still failing after all retries |

The replica table in the metadata database is the source of truth for replica states; the job queue (River, in the same SQLite database) only triggers the work.

- **Copying**: the replica is read from the highest-priority healthy channel that already holds a ready one and streamed into the target channel. The queue runs at most 4 jobs at a time (shared by replication, deletion and draining), and one replication job may run for at most 15 minutes.
- **Retries**: a failed replica goes back to `pending` and is retried with exponential backoff, roughly n⁴ seconds after the n-th failure (1 s, 16 s, 81 s…), up to 25 attempts spanning about 20 days. If the last attempt fails, the replica becomes `failed`.
- **Periodic reconciliation**: at startup and every 10 minutes after, ImgYoung adds missing replica records for every channel that is not draining, sets `failed` replicas on healthy channels back to `pending`, and queues every unfinished replica again. The "Replica reconciliation every … s" line under **Settings → Runtime settings → Bootstrap configuration** shows this interval.
- **Restarts**: jobs and replica states live in SQLite, so restarts lose nothing. A graceful shutdown cancels in-flight replication jobs, and the periodic reconciliation queues them again at the next startup; jobs that were running when the process was killed run again after about 16 minutes.
- **New channels**: creating a channel registers a pending replica for every existing image, and copying starts right away. If an upload running at the same moment missed the new channel, the periodic reconciliation fills the gap.
- **Daily reconciliation GC**: every 24 hours the objects on each healthy channel are checked. Orphans written more than 48 hours ago are deleted; replicas the metadata database marks ready but the channel no longer has go back to `pending` and are replicated again. See [Reconciliation GC](../operations/backup.mdx#reconciliation-gc).

## Read failover

To serve an image, the candidate channels are those that are **healthy, not draining, and hold a ready replica of that image**, ordered by priority. A channel the replica has not reached yet is not a candidate.

- **Proxy mode** (`access_mode = proxy`, the default): candidates are read in order; if one fails, the next is tried, invisibly to the visitor. With no candidates, or when all of them fail, the response is 503 `渠道暂不可用` ("channel temporarily unavailable").
- **Redirect mode** (`access_mode = redirect`): the first candidate that allows 302 direct links, is not encrypted and has a public URL gets a 302; if there is none, the image is proxied.

In redirect mode, requests that need a variant are always proxied: those with `w`, with an explicit `format` other than the original's, or negotiated to WebP through `Accept`. Since browsers all announce WebP support, browser requests for JPEG / PNG are proxied and converted by default. Requests that end up serving the original are still redirected.

Access modes and caching are covered in [Accessing images](../guides/access.mdx).

## Health checks

Health decides whether a channel takes uploads and reads. There are two kinds of check:

| | Light check | Deep check |
|---|---|---|
| What it does | Looks up an object that never exists, `.imgyoung-health-probe` (never written); either a result or "not found" counts as reachable | Writes a small object under a random key `.imgyoung-probe-<random hex>`, reads it back and compares, then deletes it |
| Cost | Read-only, no writes or deletes | One write, read and delete |
| Timeout | 10 s | 20 s for the write and read, plus 10 s for the delete |
| When | Periodic loop every `health_check_seconds` (default 60 s) | After creating a channel, after saving an edit, on **Probe again** or **Test connection**; and in the periodic loop when an unhealthy channel passes its light check |

In the periodic loop, **a light check can mark a channel unhealthy but never healthy again**:

- Healthy channels get only a light check each round; a failure marks them unhealthy.
- Unhealthy channels get a light check first; if it passes, a deep check follows, and only a full write–read–delete pass marks them healthy again.
- Read-only credentials, for example, pass the light check but cannot write. Such a channel is not marked healthy again just because light checks pass.

The periodic loop uses only the read-only light check so that pay-per-request storage is not billed for a write and a delete every minute. Problems on the write path are caught by deep checks.

Channels are checked in parallel with independent timeouts, so one slow channel never slows the others down. Draining channels are not checked.

Results are shown in the **Status** column of the Storage channels page: **Healthy**, **Unhealthy** or **Draining**. The small text below shows when the last check ran, or **Not probed yet**.

### Failure reasons

Hovering **Unhealthy** shows the failure reason as "classification (root cause)", for example "Authentication failed (403): check the Access Key / Secret Key and their permissions (…)". If the failure cannot be classified, only the root cause is shown. The classification follows the console language; the root cause is quoted verbatim and is usually the provider's or network library's own English text. Failures while loading or draining get a stage prefix in front; see [When a channel cannot be loaded](#when-a-channel-cannot-be-loaded) and [When draining fails](#when-draining-fails).

In the channel objects returned by the API, the failure reason is the `failure` field: `null` means the last check succeeded or nothing has failed yet; otherwise it is `{stage, reason, detail}`:

| Field | Meaning |
|---|---|
| `stage` | Where it failed: `probe` health check; `load` building the driver from the configuration; `drain` deleting objects of a draining channel |
| `reason` | Classification, such as `s3_auth`, `bucket_missing` or `timeout`; `unclassified` when none applies. All values and what to check are under [Failure reasons](./object-storage.mdx#failure-reasons) in Object storage and WebDAV |
| `detail` | Root cause: the innermost error of the error chain, with credentials scrubbed; at most 200 characters, a longer one is cut to 199 characters followed by "…" |

### When a channel cannot be loaded

If a channel's configuration cannot be decrypted or its backend fails to initialize, that channel is skipped and the rest keep serving.

- The list shows it as **Unhealthy**; the failure stage is `load` and the reason is prefixed with "Load failed:".
- A configuration that cannot be decrypted is classified as `config_unreadable`, which usually means the current master key differs from the one the configuration was written with.
- Channels load in parallel, and building each channel's driver may take at most 30 seconds, so an unreachable backend never holds up startup, reloads or health checks. A build that has not finished by then (an unreachable backend, or one such as `ftp` that ignores cancellation while being built) is recorded as a load failure classified as `timeout`; the root cause shown in the console and in alerts is `context deadline exceeded`. Building the backend during Test connection, creation and editing has the same 30-second limit.
- After a timeout the build carries on in the background until the backend's own timeout ends it. Until then, loading or testing the same configuration (same backend name, parameters and path) fails with a timeout straight away.
- Every health check round retries loading first, and **Probe again** also tries to load first. Once loaded, the channel still has to pass a deep check before it is healthy again.
- If no channel at all can be loaded at startup, startup fails.

The related log lines are listed under [Logs](#logs) at the end of this page.

## Replica counts

The **Replicas** column shows how many of the channel's replicas are in each state: ready, pending (including in progress) and failed.

A pending count that never drops, or any failures, means writes to that channel are failing: check the reason in the Status column, then run **Probe again**. Once the channel is healthy again, failed replicas are retried at the next periodic reconciliation.

## Editing a channel

**Edit** in the row menu opens the same form as creation. You can change the channel name, the template fields (or custom parameters), the priority and **Allow 302 direct links**. These cannot be changed:

- **Server-side encryption**: the form only shows **Encrypted** or **Not encrypted**, and the API rejects changes; see [Channel encryption](./encryption.mdx#fixed-at-creation).
- The storage type: an edit keeps the template the channel was created with. Custom channels and the built-in local channel open in the custom form.
- **Create the bucket automatically**: only exists at creation.

Saving replaces the configuration as a whole, without merging. Only this channel's driver is rebuilt, so in-flight reads and writes on other channels are unaffected. A deep check follows immediately, and a failure shows "Channel saved, but the probe failed:" plus the reason.

### Masked credentials

Credentials are never sent back to the edit form; the fixed placeholder `__imgyoung_secret_keep__` stands in for them:

- Submitting the placeholder unchanged keeps the stored value; typing a new value replaces it.
- What counts as a credential follows the rclone backend's option metadata: every parameter rclone flags as a password or as sensitive is masked. Besides passwords, keys and authorization tokens, that includes access key IDs (Access Key, SecretId, Key ID), the WebDAV user name, the app client ID, OneDrive's `drive_id` and so on.
- Template forms use the same metadata to decide which fields are masked inputs. Custom parameter values are always masked inputs (each can be revealed), because the console cannot tell which custom keys are credentials.
- Putting the placeholder on a parameter that is not a credential is rejected (400).

### Save conflicts

Saving checks that the channel configuration is still the one read when the save started. If another edit was saved first, or the provider refreshed a token that was written back to the channel during the save, this save does not take effect and the API answers 409 (error code `channel_config_changed`); just save again.

### Binding time

The **binding time** is when the channel started using its current storage location. The daily reconciliation only deletes orphans written no earlier than the binding time.

- For a new channel, the binding time is its creation time.
- Any change to the backend name or to any configuration parameter (the public URL included) resets the binding time to the moment of saving. Re-entering the same password counts as a change, because rclone encodes passwords with a random IV.
- Changing only the name, the priority or **Allow 302 direct links** does not reset it, and neither do token refresh write-backs.
- After a reset, objects in this service's key format at the new location that predate it are only counted, never deleted.

Restoring a snapshot resets the binding time of every channel as well; the full rules are under [Reconciliation GC](../operations/backup.mdx#reconciliation-gc).

<Callout type="warn" title="Do not move storage by editing">
Editing never triggers replication. After changing the bucket, prefix or endpoint, the channel's existing replicas are still recorded as ready; reads from it fail and fall through to other channels until the daily reconciliation notices the missing objects and replicates them again. To move storage, create a new channel, wait until the **Pending** count in its **Replicas** column reaches zero, then delete the old one.
</Callout>

## Deleting a channel

**Delete** in the row menu opens a confirmation dialog. The checkbox "Also delete what this service stored on the channel" picks the path:

| | Delete and purge (checked, default) | Remove only (unchecked) |
|---|---|---|
| Immediately | The channel turns **Draining** and leaves upload routing, replication and health checks | The channel and its replica records are deleted |
| Remote objects | Objects this service has on record are deleted one by one by a background drain job, then the channel is removed; nothing else in the channel is scanned or deleted | Image replicas and metadata snapshots are left as they are; clean them up at the provider if needed |
| Use it when | Retiring a channel normally | Credentials are revoked, the bucket is gone, or draining is stuck |

**Only-replica protection**: if any image has no ready replica on another channel (draining channels do not count), both kinds of delete are refused with 409 (error code `channel_sole_replicas`). Replicas still pending on other channels do not count; wait until they are ready. The check also holds when you delete two channels one after the other, so no image ever loses its last copy.

### How draining works

With **Delete and purge**, the drain job deletes objects in this order:

1. Image objects, batch by batch according to the replica records, removing each record as it goes. Progress is kept in the metadata database, so an interrupted drain resumes where it stopped.
2. Everything under `_imgyoung/` (including the metadata snapshots under `_imgyoung/backup/`) and the probe leftovers `.imgyoung-probe-*` in the root.
3. The channel record.

Files other programs wrote are left alone. Also:

- Once the channel turns **Draining**, new writes are refused immediately. The drain waits for writes already in progress to finish before it starts, so nothing this service wrote is missed.
- The drain deletes only these recorded objects, and the daily reconciliation does not scan draining channels. Orphans left by failed uploads that are less than 48 hours old stay at the provider after the purge.
- One drain run lasts at most an hour. After a timeout or a shutdown, the next run continues with what is left; neither counts as a failure.
- A draining channel cannot be edited, tested, probed again or re-authorized, even one that failed to load. Its row menu offers only **Remove now**, and the API answers 409 (error code `channel_deleting`).

### When draining fails

Failed deletions are retried with backoff until the drain completes, and it finishes on its own once the channel is reachable again.

- Only when the 4th attempt of the same drain job still fails (about 98 seconds after the first failure with the default backoff) does the Status column show the reason and a **Channel drain failed** alert open. Until then the column just shows **Draining**, so a brief network glitch leaves neither a reason nor an alert.
- The failure stage of a drain failure is `drain`, and the console prefixes the classification with "Deleting the channel’s objects failed; this is retried automatically. If the credentials no longer work or the bucket is gone, remove the channel directly (remote objects are kept):".
- If a draining channel fails to load (stage `load`), the reason shows right away and a **Channel drain failed** alert opens, because a channel that cannot be loaded cannot be drained. As soon as the channel loads, that reason is cleared and the alert resolves; whether it opens again depends on the drain's own failures.
- When a channel turns **Draining**, its previous failure reason is cleared. From then on the reason in the Status column comes only from drain failures and load failures.
- A drain failure reason and its alert stay until draining completes. Choosing **Delete and purge** again for a channel that is already draining changes nothing.

### Remove now

If the credentials are revoked or the bucket is gone, use **Remove now** to remove the channel at once. A drain in progress stops: apart from the one object being deleted at that moment, the remaining remote objects (the snapshots under `_imgyoung/backup/` included) stay as they are.

## Exporting the rclone config

**Export rclone config** in the row menu downloads the channel's rclone config file `imgyoung-channel-<channel ID>.rclone.conf`; draining channels do not offer it. With this file, a stock rclone can read and write the channel's data without ImgYoung. The file contains:

- Remote `imgyoung-<channel ID>`: the channel's backend, with exactly the parameters ImgYoung hands to the backend, access credentials and OAuth tokens included.
- Remote `imgyoung-<channel ID>-crypt`: encrypted channels only; a crypt layer pointing at the channel's storage path, so reads and writes through it are plaintext.
- Comments at the top: what each remote is, with example commands. They come in Chinese and English; a download from the console follows the console language.

The file holds the channel's credentials, plus the decryption passwords for an encrypted channel. The dialog warns "Keep it offline and safe, just like the master key: anyone who has it can read and write all of this channel's data."

After **Download config file**, the file is saved only once it has been fetched completely. If the download fails (for example 422, 404 or a broken transfer), the reason appears in a notification at the bottom right and the dialog stays open for another try; closing the dialog cancels the download. Every download is recorded in the audit log as "Export channel rclone config".

How to use the file, and what to watch out for, is covered in [Channel encryption](./encryption.mdx#reading-a-channel-with-stock-rclone).

## Usage and alerts

Channel usage is the **total size of the images whose replicas on that channel are ready**. It is a logical figure: it excludes metadata snapshots and orphans, and it is not your provider's bill.

- It is refreshed every `usage_report_seconds` (default 300 s) into the metric `imgyoung_channel_storage_bytes{channel="…"}`. The **Storage channels** card on the **Dashboard** shows each channel's stored bytes and share.
- The alert threshold is **Settings → Runtime settings → Reliability & channels → Channel usage alert threshold** (`channel_quota_gb`, in GB of 2³⁰ bytes); 0 reports without alerting. Exceeding it opens a **Channel over quota** alert.

Four alerts concern channels. They are evaluated on the health check cadence, recorded under **Settings → Alert history**, and delivered to the alert webhook when one is configured:

| Alert | Opens when | Resolves when |
|---|---|---|
| Channel unhealthy | A channel that is not draining is marked unhealthy | It passes its health check again |
| Replication failed | The channel has `failed` replicas | It has none left. On a healthy channel, the periodic reconciliation sets them back to pending for another try |
| Channel over quota | Usage exceeds the threshold | Usage drops or the threshold is raised |
| Channel drain failed | The 4th attempt of the same drain job on a draining channel still fails, or a draining channel fails to load | The channel is removed (after draining or with **Remove now**); when opened by a load failure, also once the channel loads |

Alert descriptions follow the console language. Alert objects and webhook payloads carry structured values in `params`, such as `stage`, `reason` and `detail` for channel failures. Scraping metrics and delivering alerts are covered in [Monitoring & alerts](../operations/monitoring.mdx).

Other relevant metrics:

| Metric | Meaning |
|---|---|
| `imgyoung_channels_healthy_total` | Healthy channels |
| `imgyoung_channels_total` | Loaded channels that are not draining, unhealthy ones included |
| `imgyoung_channel_puts_total{channel, result}` | Object writes to a channel, `result` being `ok` or `error`; counts both upload writes and replication |

## Reference

### Error codes

| Action | Status | Error code | Meaning |
|---|---|---|---|
| Upload | 503 | `upload_unavailable` | Not enough healthy channels, or every write failed; uploads through the S3-compatible API get 503 `ServiceUnavailable` |
| Image access | 503 | — | No candidate channel, or every read failed; the response body is `渠道暂不可用` |
| Create, edit | 400 | `channel_local_path_relative` | The `path` of a `local` channel is not absolute |
| Edit | 409 | `channel_encrypted_immutable` | An attempt to change **Server-side encryption** |
| Edit | 409 | `channel_config_changed` | Another edit or a token write-back changed the channel configuration during the save; just save again |
| Delete | 409 | `channel_sole_replicas` | The channel holds the only replica of some images; the `count` parameter is how many |
| Edit, test connection, probe again, re-authorize | 409 | `channel_deleting` | The channel is draining |
| Export rclone config | 422 | `channel_unrepresentable` | A parameter value cannot be written into an rclone config file; see [Channel encryption](./encryption.mdx#with-an-exported-config-file) |

Other error codes returned when saving the form are listed under [Error codes when saving](./object-storage.mdx#error-codes-when-saving).

### Logs

| Log line | Meaning |
|---|---|
| `渠道装载失败,本渠道跳过,健康检查时重试` | The channel could not be loaded and was skipped |
| `构造后端未在时限内完成: context deadline exceeded` | Building the backend took longer than 30 seconds |
| `构造后端未在时限内完成(同一配置上一次构造仍未结束): context deadline exceeded` | An earlier build of the same configuration that timed out is still running in the background, so no new build was started |
| `渠道已清理完毕并删除` | Draining finished and the channel was removed; the field `objects` is the number of image replicas deleted, `system_objects` the number of system objects deleted |
