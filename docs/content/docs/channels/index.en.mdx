## What a channel is

A channel is one rclone backend instance: a backend type (`s3`, `webdav`, `local`…) plus its parameters, plus a few ImgYoung attributes:

| Attribute | Meaning |
|---|---|
| Channel name | Unique, up to 64 bytes; used in the UI, logs, metrics and alerts |
| Priority | Integer, higher wins; the admin console accepts 0–1000 and defaults to 100 |
| Server-side encryption | Whether data is stored through rclone crypt; fixed at creation, see [Channel encryption](./encryption.mdx) |
| Allow 302 direct links | Whether reads may be redirected to the channel's public URL, see [Object storage and WebDAV](./object-storage.mdx) |

Backend parameters are handed to rclone as a map, never through `rclone.conf`; the whole parameter set is encrypted with the master key (AES-256-GCM) and stored in the metadata database. Channels are managed on the **Storage channels** page of the admin console, which only admins can see; the API is under [admin channels](../api/admin-channels.mdx). Channel objects returned by the API (the list, the responses to create, edit and probe again, and `channels` in the metadata export) carry `created_at`: when the channel was created (UTC). It is part of the key derivation for encrypted channels and never changes. Channel IDs are never reused: a channel created after deleting another gets a new ID.

**Every channel ends up holding a replica of every image.** Channels mirror each other in full; nothing is sharded. Size each channel for the whole library.

<Callout type="warn" title="Two instances must not share a channel path">
The daily reconciliation only removes orphans this service wrote, meaning objects that meet all of these: the key has this service's object key format `<short ID>_<first 8 hex digits of SHA-256>`; the metadata database has no replica record of any state for it on this channel; it was modified no earlier than the channel's bind time; and it is older than 48 hours. Deep-check leftovers `.imgyoung-probe-*` are removed once written more than 48 hours ago, regardless of the bind time. Files other programs put under the same path are only counted (the `foreign` field of the reconciliation log), never deleted. Two ImgYoung instances must not share a channel path: objects written by the other instance look like orphans to this one and get deleted.

The bind time is when the channel record started pointing at its current storage location: it equals the creation time for a new channel and is reset when [editing](#editing-a-channel) changes the configuration; restoring a snapshot (from the admin console, or by placing it as `<data dir>/imgyoung.db.restore` and starting) resets it for every channel. The full rules are under "Reconciliation GC" in [Metadata backups](../operations/backup.mdx).
</Callout>

## The built-in local channel

On first start with a fresh metadata database, ImgYoung creates a channel named `local`: backend `local`, priority 100, stored under `<data dir>/blobs`. Uploads work with no configuration at all.

- It is seeded only this once, on a fresh metadata database. Once you delete or rename it, restarts do not bring it back, and neither does emptying the channels table.
- The `path` of a `local` channel must be absolute; a relative path is rejected with 400 and error code `channel_local_path_relative` (message `渠道参数非法: local 渠道的路径须为绝对路径,收到 {path}`). Leaving it empty uses `<data dir>/blobs`.
- It lives on the same machine as the metadata database and the master key, so losing the host loses everything. While it is the only channel, the Storage channels page shows "Only the local disk is configured". Add an off-site channel and existing images are replicated to it automatically; metadata snapshots are written to every healthy channel on each round, so the new channel holds snapshots from the next backup on.

## Priority: primary and backup channels

There is no separate "primary" switch; priority alone expresses primary and backup:

- **Primary channel**: the highest-priority channel that is healthy and not draining. The list marks it **Primary**.
- **Backup channels**: everything else. Normally uploads do not write to them directly and asynchronous replication copies replicas over; they are written synchronously only when a higher channel fails mid-upload or when `min_success` is above 1.
- On equal priority, the channel created first wins.

When the primary turns unhealthy, the next healthy channel takes over with no manual step; once the original recovers, it is primary again.

## Upload writes

Each upload walks the currently healthy channels from highest to lowest priority and writes synchronously until `min_success` copies have succeeded:

1. If a write fails (including the 10-minute per-write timeout), the next healthy channel is tried.
2. As soon as enough copies exist, the upload succeeds. The first channel that accepted the write holds the image's first replica.
3. Every other channel, including temporarily unhealthy ones, gets a pending replica for asynchronous replication.

`min_success` lives under **Settings → Runtime settings → Access & links → Minimum synced replicas** (default 1, minimum 1). When there are not enough healthy channels or every write fails, the upload returns 503 with error code `upload_unavailable` (message `存储渠道暂不可用,请稍后重试`, "storage channels temporarily unavailable, retry later"; S3 uploads get 503 `ServiceUnavailable`) and no metadata is recorded; copies that did get written become orphans and are removed by the daily reconciliation.

If a channel the upload already wrote to turns **Draining** in the meantime, the copy on it does not count towards the required number; when the remaining in-service copies fall short of `min_success`, the upload fails the same way (503 `upload_unavailable`) and the objects it wrote are deleted right away.

<Callout type="info">
If `min_success` exceeds the number of healthy channels, every upload fails. Setting it to 2 means an upload only succeeds once two channels hold it, at the cost of write latency and a dependency on several channels being up.
</Callout>

## Asynchronous replication

Replica state lives in a replica table in the metadata database, and that table is the single source of truth. The job queue (River, in the same SQLite database) only triggers work, and at most one job per image and channel is in flight.

| Replica state | Meaning |
|---|---|
| `pending` | Waiting to be replicated |
| `uploading` | Replication in progress |
| `done` | Ready to serve reads |
| `failed` | Still failing after all retries |

- **Copying**: the replica is read from the highest-priority healthy channel that already has it and streamed into the target channel. The queue runs 4 jobs at a time (shared with delete and drain jobs); one replication job may run for at most 15 minutes.
- **Retries**: a failed job goes back to `pending` and River retries it with exponential backoff, roughly n⁴ seconds after the n-th failure (1 s, 16 s, 81 s…), up to 25 attempts spanning about 20 days. If the last attempt fails, the replica becomes `failed`.
- **Periodic reconciliation**: at startup and every 10 minutes after, ImgYoung adds missing replica rows for every channel in service, resets `failed` replicas on healthy channels to `pending`, and re-queues every unfinished replica (jobs already queued are de-duplicated). The "Replica reconciliation every … s" line under **Settings → Runtime settings → Bootstrap configuration** shows this interval.
- **Survives restarts**: jobs and replica states are in SQLite. A graceful shutdown cancels in-flight replication jobs; their replica states stay in the table and the next startup reconciliation re-queues them. Jobs that were running when the process was killed are rescheduled by River after about 16 minutes.
- **Backfilling a new channel**: creating a channel registers a pending replica for every existing image in the same transaction, and replication starts right away. If an upload racing with the creation missed the new channel, the periodic reconciliation fills the gap.
- **Daily reconciliation GC**: every 24 hours each healthy channel is compared with the database in both directions. Objects this service wrote that have no replica record are deleted once older than 48 hours (orphans, as defined at the top of this page); replicas the database marks ready but the channel no longer has go back to `pending` and are replicated again (phantoms).

## Read failover

To serve an image, the candidate channels are those that are **healthy, not draining, and hold a ready replica of that image**, ordered by priority.

- **Proxy mode** (`access_mode = proxy`, the default): candidates are read in order; if one fails, the next is tried, invisibly to the visitor. With no candidates, or when all of them fail, the response is 503 with `渠道暂不可用` ("channel temporarily unavailable").
- **Redirect mode** (`access_mode = redirect`): the first candidate that allows 302 direct links, is not encrypted and has a public URL gets a 302; if there is none, the image is proxied. Requests that actually produce a variant (with `w`, with an explicit `format` other than the original's, or negotiated to WebP through `Accept`) are always proxied; since browsers all announce WebP support, browser requests for JPEG / PNG are proxied and converted by default. Requests that resolve to the original are still redirected.

A channel the replica has not reached yet is not a candidate for that image. Access modes and caching are covered in [Access and links](../guides/access.mdx).

## Health checks

Health decides whether a channel takes uploads and reads. There are two kinds of check:

| | Light check | Deep check |
|---|---|---|
| What it does | Stats an object that never exists, `.imgyoung-health-probe` (never written); either a result or "not found" counts as reachable | Writes a small object under a random key `.imgyoung-probe-<random hex>`, reads it back and compares, then deletes it |
| Cost | Read-only, no writes or deletes | One write, read and delete |
| Timeout | 10 s | 20 s for the write and read, plus 10 s for the delete |
| When | Periodic loop every `health_check_seconds` (default 60 s) | After creating a channel, after saving an edit, on **Probe again**, on **Test connection**; and in the periodic loop when an unhealthy channel passes its light check |

The periodic loop follows one rule: **a light check can only mark a channel down, never up.**

- Healthy channels get only a light check each round; a failure marks them unhealthy.
- Unhealthy channels get a light check first; if it passes, a deep check follows, and only a full write–read–delete pass restores them.
- A read-only success never overrides a failed deep check. Read-only credentials, for example, pass the light check but cannot write; such a channel is not revived by light checks.

The periodic loop uses only the read-only light check because, on pay-per-request storage, writing and deleting a probe object every minute is a pointless expense; problems on the write path are caught by the event-driven deep checks and the confirmation before recovery.

Channels are checked in parallel with independent timeouts, so one slow channel never drags the others down. Draining channels are not checked. A round in progress at shutdown is discarded rather than recorded.

Results are written back to the database and shown in the **Status** column of the Storage channels page: **Healthy**, **Unhealthy** or **Draining**; the small text below shows when the last check ran, or **Not probed yet**.

Hovering **Unhealthy** shows the failure reason as "classification (root cause)", for example "Authentication failed (403): check the Access Key / Secret Key and their permissions (…)"; if the failure cannot be classified, only the root cause is shown. Failures during loading or draining get a stage prefix in front (see below). The classification follows the console language; the root cause is quoted verbatim and is usually the provider's or network library's own English text.

In the channel objects returned by the API this conclusion is the `failure` field: `null` means the last check succeeded or nothing has failed yet; otherwise it is `{stage, reason, detail}`:

| Field | Meaning |
|---|---|
| `stage` | Where it failed: `probe` health check; `load` building the driver from the configuration; `drain` deleting objects of a draining channel |
| `reason` | Classification, such as `s3_auth`, `bucket_missing` or `timeout`; `unclassified` when none applies. All values and what to check are under "Common errors" in [Object storage and WebDAV](./object-storage.mdx) |
| `detail` | Root cause: the innermost error of the error chain, with credentials scrubbed; at most 200 characters, a longer one is cut to 199 characters followed by "…" |

Probe results are only written to channels in service. When a channel turns draining, its previous failure is cleared, and from then on only drain failures and load failures write this field; see [Deleting a channel](#deleting-a-channel).

<Callout type="info" title="When a channel cannot be loaded">
If a channel's configuration cannot be decrypted or its backend fails to initialize, that channel is skipped (log line `渠道装载失败,本渠道跳过,健康检查时重试`) and the rest keep serving. Channels load in parallel, and building each channel's driver may take at most 30 seconds: an unreachable backend is recorded as a load failure (timeout) when time is up, without holding up startup, reloads or health checks. The trial build during Test connection, creating and editing has the same 30-second limit. The list shows it as **Unhealthy**; the failure stage is `load` and the reason is prefixed with "Load failed:". A configuration that cannot be decrypted is classified as `config_unreadable`, which usually means the current master key differs from the one the configuration was written with. Every health check round retries loading it first, and **Probe again** also tries to load it first; once loaded, it still has to pass a deep check before it is healthy and takes part in routing. If no channel at all can be loaded at startup, startup fails.
</Callout>

## Replica watermark

The **Replicas** column shows the channel's replica counts: ready, pending (including in progress) and failed. A pending count that never drops, or any failures, means writes to that channel are failing: check the reason in the Status column and run **Probe again**. Once the channel is healthy, failed replicas are retried at the next periodic reconciliation.

## Test connection

**Test connection** at the bottom of the create and edit forms runs a deep check with the current form contents, **without saving or creating anything**:

- Success shows "Connection OK (write, read and delete probes passed)"; failure shows "Connection failed:" followed by the failure reason, written the same way as in the Status column (classification plus root cause), with credentials scrubbed from the root cause. The API responds with `{ok, failure}`, where `failure` is `{reason, detail}` on failure.
- It never creates a bucket and never applies encryption: it verifies connectivity and write, read and delete permissions on the backend.
- When editing, masked credentials are restored from the stored values before the check runs; if a stored token gets refreshed during the test, the new token is written straight back to the channel.
- If the provider refreshes a token submitted in this form during the test (which can happen even when the test fails), the new token is handed back to the form: below the result the form notes "The provider refreshed the authorization token during the test. The form now holds the new token and will save it; the old one may no longer work.", the authorization field shows **Authorized**, and saving submits the new token. See [Cloud drives and OAuth](./cloud-drives.mdx).

## Creating a channel

On the Storage channels page click **New channel**, choose a storage type, then fill in the form:

<Steps>
<Step>
Choose a type: **Object storage** and **Cloud drives** hold the built-in templates, **Advanced** holds **Custom** (an rclone backend name plus raw parameters). Template fields are described in [Object storage and WebDAV](./object-storage.mdx) and [Cloud drives and OAuth](./cloud-drives.mdx).
</Step>
<Step>
Fill in the channel name, the template fields and the priority, and choose **Server-side encryption**; object storage also offers **Allow 302 direct links** and **Create the bucket automatically**.
</Step>
<Step>
Click **Test connection**, and once it passes, **Create**.
</Step>
</Steps>

Creation first builds the backend once from the parameters (templates that need authorization first fill in what the authorization implies, such as the OneDrive drive) and rejects invalid ones outright; after the channel is stored, a deep check runs immediately. A failed deep check does not undo the creation: the channel stays, marked **Unhealthy**, with the notice "Channel created, but the probe failed:" plus the reason. Fix the configuration and click **Probe again**.

If saving a new or edited channel fails after the provider refreshed the authorization token during the save, the new token is not lost: a token submitted in the form comes back with the error response (the `token` field) and replaces the one in the form, with the notice "Saving failed, but the provider refreshed the authorization token meanwhile. The form now holds the new token; fix the problem and save again, no need to authorize again."; a stored token kept while editing is written straight back to the channel. See [Cloud drives and OAuth](./cloud-drives.mdx).

## Editing a channel

**Edit** in the row menu opens the same form as creation. You can change the channel name, the template fields (or custom parameters), the priority and **Allow 302 direct links**.

- **Fixed**: server-side encryption (the form only shows **Encrypted** or **Not encrypted**; the API rejects changes with 409); the storage type (an edit keeps the template the channel was created with; custom channels and the built-in local channel open in the custom form); **Create the bucket automatically** only exists at creation.
- **Masked credentials**: credentials are never sent back to the form; they are replaced with the fixed placeholder `__imgyoung_secret_keep__`. Which values are replaced by the placeholder follows the rclone backend's option metadata: every parameter rclone flags as a password or as sensitive. Besides passwords, keys and authorization tokens, that includes access key IDs (Access Key, SecretId, Key ID), the WebDAV user name, the app client ID, OneDrive's `drive_id` and so on. Template forms use the same metadata to decide which fields are masked inputs; custom parameter values are always masked inputs (each can be revealed), because the console cannot tell which custom keys are credentials. Submitting the placeholder unchanged keeps the stored value and typing a new value replaces it; putting the placeholder on a parameter that is not a credential is rejected (400).
- The configuration is replaced as a whole, not merged. Saving rebuilds only this channel's driver, so in-flight reads and writes on other channels are unaffected; a deep check follows immediately, and a failure shows "Channel saved, but the probe failed:" plus the reason.
- **Concurrent edits**: saving checks that the channel configuration is still the one read when the save started. If another edit was stored, or the provider refreshed a token that was written back to the channel, during the save, this edit is not stored and the API answers 409 with error code `channel_config_changed` (message `渠道配置在保存期间已被改动(另一次编辑,或服务商刷新了授权令牌),请重新保存`); just save again.
- **Bind time reset**: any change to the backend name or to any configuration parameter (the public URL included) resets the channel's bind time to the moment of saving. Re-entering the same password counts as a change, because rclone encodes passwords with a random IV. Changing only the name, the priority or **Allow 302 direct links** does not reset it, and neither do token refresh write-backs. After a reset, objects in this service's key format that predate it at the new location are only counted, never removed; see "Reconciliation GC" in [Metadata backups](../operations/backup.mdx).

<Callout type="warn" title="Do not move storage by editing">
Editing never triggers a backfill. After changing the bucket, prefix or endpoint, the channel's existing replicas are still recorded as ready; reads from it fail and fall through to other channels until the daily reconciliation notices the missing objects and replicates them again. To move storage, create a new channel, wait until its pending replica count reaches zero, then delete the old one.
</Callout>

## Deleting a channel

**Delete** in the row menu opens a confirmation dialog; the checkbox "Also delete what this service stored on the channel" picks the path:

| | Delete and purge (checked, default) | Remove only (unchecked) |
|---|---|---|
| Immediately | The channel turns **Draining** and leaves upload routing, replication and health checks | The channel and its replica records are deleted |
| Remote objects | Objects this service has on record (the images in the replica records, system objects under `_imgyoung/`, deep-check leftovers) are deleted one by one by a background drain job, then the channel is removed; nothing else in the channel is scanned or deleted | Image replicas and metadata snapshots are left as they are; clean them up at the provider if needed |
| Use it when | Retiring a channel normally | Credentials are revoked, the bucket is gone, or draining is stuck |

Both paths are protected against deleting **the only replica**: if any image has no ready replica on another channel (draining channels do not count), the delete is refused with 409 and error code `channel_sole_replicas` (message `该渠道持有 {count} 张图片的唯一副本,删除会丢数据;请先迁移或删除相关图片`, where `count` is the number of such images). The check and the delete run in one transaction, so deleting two channels one after the other can never remove every copy of an image. Replicas still pending on other channels do not count; wait until they are ready.

Draining in detail:

- The drain job first deletes image objects batch by batch according to the replica records and removes each record as it goes. Progress is kept in the database, so an interrupted drain resumes where it stopped.
- Once the image replicas are gone, it deletes everything under `_imgyoung/` (including the metadata snapshots under `_imgyoung/backup/`) and the deep-check leftovers `.imgyoung-probe-*` in the root, and only then removes the channel record. Files other programs wrote are left alone. The completion log `渠道已清理完毕并删除` carries the fields `objects` (image replicas) and `system_objects` (system objects).
- Uploads, replication, metadata snapshots and deep checks all write their objects and records under the channel's write lease. Once the channel turns **Draining**, new writes are refused; before listing objects and records, the drain waits for writes already in flight to finish. So a draining channel never keeps an object this service wrote that the drain cannot see.
- The drain deletes only these recorded objects, and the reconciliation GC does not scan draining channels. Orphans left by failed uploads that are still within their 48-hour grace period, not yet reclaimed by reconciliation, stay at the provider after **Delete and purge**.
- One drain run may last up to an hour; after a timeout the next run continues with what is left.
- Marking the channel as draining clears its previous failure. From then on the reason in the Status column comes from only two sources: drain failures and load failures.
- Failed deletions are retried by River with backoff. Only when the 4th attempt of the same drain job still fails (about 98 seconds after the first failure with River's default backoff) is the reason written to the Status column and a **Channel drain failed** alert opened; until then the column just shows **Draining**, so a brief network glitch leaves neither a reason nor an alert. The failure stage is `drain`, and the console prefixes the classification with "Deleting the channel’s objects failed; this is retried automatically. If the credentials no longer work or the bucket is gone, remove the channel directly (remote objects are kept):".
- If a draining channel fails to load (stage `load`), the reason shows right away and a **Channel drain failed** alert opens: a channel that cannot be loaded cannot be drained.
- Draining keeps retrying and never gives up, so it finishes on its own once the channel is reachable again. When a job runs out of attempts, reconciliation queues a new one that counts from attempt 1, and the recorded reason and alert stay until draining completes. A drain run's own timeout or a shutdown does not count as a failure.
- A draining channel cannot be edited, tested, probed again or re-authorized, even one that failed to load: its row menu offers only **Remove now**, and the API answers 409 with error code `channel_deleting`.
- If the credentials are revoked or the bucket is gone, use **Remove now** to remove the channel at once. The drain checks that the channel is still draining before each batch of replicas and before each system object, so a drain job in flight stops and deletes no further remote objects (the snapshots under `_imgyoung/backup/` included); whatever has not been deleted stays as it is.

## Exporting the rclone config

**Export rclone config** in the row menu (not offered for draining channels) downloads the channel's rclone config file `imgyoung-channel-<channel ID>.rclone.conf`. With it, a stock rclone can read and write this channel's data without ImgYoung:

- Remote `imgyoung-<channel ID>`: the channel's backend, with exactly the parameters ImgYoung hands to the backend, access credentials and OAuth tokens included.
- Remote `imgyoung-<channel ID>-crypt`: encrypted channels only; a crypt layer pointing at the channel's storage path, so reads and writes through it are plaintext.
- Comments at the top of the file describe each remote and show example commands. They come in Chinese and English; a download from the console follows the console language.

The file holds the channel's credentials (and, for encrypted channels, the decryption passwords); the dialog warns "Keep it offline and safe, just like the master key: anyone who has it can read and write all of this channel's data." After **Download config file**, the console first fetches the whole file and only hands it to the browser to save, closing the dialog, once that succeeds; on failure (such as 422, 404 or a broken transfer) the dialog shows the reason and no error response or partial file is saved. Every download is recorded in the audit log as "Export channel rclone config". How to use the file, and what to watch out for, is under "Self-rescue" in [Channel encryption](./encryption.mdx).

## Usage monitoring and alerts

Channel usage is the total size of the images whose replicas on that channel are ready. It is a logical figure: it excludes metadata snapshots and orphans, and it is not your provider's bill.

- It is refreshed every `usage_report_seconds` (default 300 s) into the metric `imgyoung_channel_storage_bytes{channel="…"}`; the **Storage channels** card on the **Dashboard** shows bytes per channel and each channel's share.
- The alert threshold is **Settings → Runtime settings → Reliability & channels → Channel usage alert threshold** (`channel_quota_gb`, in GB of 2³⁰ bytes); 0 reports without alerting. Exceeding it opens a **Channel over quota** alert.

Four alert kinds concern channels. They are evaluated on the health check cadence, recorded under **Settings → Alert history**, and delivered to the alert webhook when one is configured. The console shows alert descriptions in its own language; the alert objects and webhook payloads carry structured values in `params` (for channel failures `stage`, `reason` and `detail`), see [Monitoring and alerts](../operations/monitoring.mdx):

| Alert | Opens when | Resolves when |
|---|---|---|
| Channel unhealthy | A channel in service is marked unhealthy | It passes its health check again |
| Replication failed | The channel has `failed` replicas | It has none left (on a healthy channel, the periodic reconciliation resets them for another try) |
| Channel over quota | Usage exceeds the threshold | Usage drops or the threshold is raised |
| Channel drain failed | The 4th attempt of the same drain job on a draining channel still fails, or a draining channel fails to load | The channel is removed (drained or removed now) |

Other relevant metrics: `imgyoung_channels_healthy_total` (healthy channels), `imgyoung_channels_total` (loaded channels that are not draining, unhealthy ones included) and `imgyoung_channel_puts_total{channel, result}` (object writes to a channel, `result` being `ok` or `error`, counting both upload writes and replication). Scraping and alert delivery are covered in [Monitoring and alerts](../operations/monitoring.mdx).
