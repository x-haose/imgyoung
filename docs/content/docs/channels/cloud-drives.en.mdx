## Supported drives

In the type picker of **New channel**, the **Cloud drives** group holds the generic [WebDAV](./object-storage.mdx) template plus six templates that need OAuth authorization:

| Template | rclone backend | Backend-specific field |
|---|---|---|
| OneDrive | `onedrive` | Region |
| Google Drive | `drive` | — |
| Dropbox | `dropbox` | — |
| pCloud | `pcloud` | Data region |
| Box | `box` | — |
| Yandex Disk | `yandex` | — |

After the backend-specific field, all six templates have **App client ID**, **App client secret**, **Authorization** and **Folder**, in that order:

- **Region** (OneDrive): **Global**, **Microsoft Cloud for US Government**, **Microsoft Cloud Germany** or **China (operated by 21Vianet)**. It selects the authorization and API endpoints and must match the account's region.
- **Data region** (pCloud): **United States** or **Europe**. It must match the region chosen when the account was registered, or the token exchange fails.
- **App client ID / App client secret**: the identity and secret of an OAuth app you registered on the provider's developer platform. One-click authorization requires the client ID. When pasting a token, fill in both if the token was obtained with your own app; leave them empty for tokens from rclone's built-in app. Token renewal uses these two values, so they must belong to the app that issued the token. Both are stored encrypted with the channel and shown masked when editing.
- **Authorization**: the token, filled in by one of the two authorization paths below; the form cannot be saved without it.
- **Folder**: the folder on the drive that holds the images, `imgyoung` suggested; empty means the root.

The endpoints, scopes and rclone's built-in app identity needed for authorization all come from the rclone backend's own registration; ImgYoung has no per-provider code.

**OneDrive drives**: when a new authorization comes in, saving or testing the connection runs the rest of rclone's own configuration flow after the authorization step, taking the default answer at every question: it selects the account's default drive and writes `drive_id` and `drive_type`, the same choice `rclone config` makes when you accept every default. If the query to the provider fails, saving returns 400 and Test connection shows the reason. Editing with the stored authorization keeps the existing choice. For a SharePoint document library or another drive, see [Other OneDrive drives](#other-onedrive-drives).

**pCloud tokens**: pCloud tokens never expire (their expiry is the zero time) and carry no refresh token; they save normally.

## Option 1: paste a token

Get a token with rclone on any computer that has a browser, then paste it into the form. The ImgYoung server needs no public domain, which makes this the only option for deployments without one.

<Steps>
<Step>
On a computer with a browser, install rclone and run the command shown in the form (Google Drive as an example):

```bash title="Terminal"
rclone authorize "drive"
```

A browser opens the provider's sign-in and consent page; complete it.
</Step>
<Step>
The terminal prints something like:

```text
Paste the following into your remote machine --->
{"access_token":"…","token_type":"Bearer","refresh_token":"…","expiry":"…"}
<---End paste
```

Copy everything between the two marker lines.
</Step>
<Step>
In the **Authorization** field switch to **Paste a token**, paste it, fill in the remaining fields, run **Test connection** and save.
</Step>
</Steps>

- Both a plain token JSON and rclone's encoded config blob (what `rclone authorize` prints when given a config blob argument) are accepted; ImgYoung extracts the token.
- A token that expires must include a refresh token, otherwise it cannot be renewed once the access token expires; saving then fails with 400 and error code `oauth_no_refresh_token` ("Invalid channel settings: the authorization token has no refresh token, so it cannot be renewed once the access token expires"). Tokens that never expire (such as pCloud's) need none. Content that cannot be parsed fails with error code `oauth_token_invalid` ("Invalid channel settings: the authorization token is malformed").
- A token from `rclone authorize "<backend>"` is issued to rclone's built-in app: leave the app client ID and secret empty, and rclone renews it with the built-in app as well.
- To use your own app, run `rclone authorize "<backend>" <client ID> <client secret>` (the app must register rclone's local callback URL `http://127.0.0.1:53682/`), then enter the same app's client ID and secret in the form.

## Option 2: one-click authorization in the admin console

This runs the whole OAuth authorization-code flow inside the admin console. It requires an app of your own, because OAuth callback URLs must be registered with the provider in advance, and rclone's built-in apps only register a local loopback address that a browser cannot use to reach a remote server.

<Steps>
<Step>
Set **Settings → Runtime settings → Access & links → Public site address** to ImgYoung's public address, such as `https://img.example.com`. Without it, starting authorization fails with 400 and error code `oauth_base_url_required` ("One-click authorization needs the public site address in Settings first; or paste a token instead").
</Step>
<Step>
Create an app on the provider's developer platform and register this callback URL — the public site address plus a fixed path:

```text
https://img.example.com/api/admin/channel-oauth/callback
```

The two must match character for character (scheme, host, port and path).
</Step>
<Step>
Enter your app's credentials in the **App client ID** and **App client secret** fields above the **Authorization** field, then click **Authorize with …** under **One-click authorization**. The button stays disabled until a client ID is filled in. A new browser tab opens the provider's consent page.
</Step>
<Step>
When it finishes, the callback page reads `Authorization complete. Go back to the admin console to continue.`, the **Authorization** field turns **Authorized**, and you can save. The callback page is in English or Chinese according to the browser's `Accept-Language`.
</Step>
</Steps>

- The callback requires an admin session, so finish the authorization **in the same browser you are signed in to the console with**.
- An authorization session is valid for 10 minutes and the form waits for at most about 11 minutes; after that it shows "Timed out waiting for authorization, please start again".
- The token is never written into the callback page; the form collects it with a one-time identifier, and it can be collected only once.
- A failed token exchange shows "Exchanging the token failed. Check the app credentials and the callback address" in the form (error code `oauth_exchange_failed`); refusing or cancelling on the provider's page shows "Authorization was denied or canceled:" plus the reason the provider returned (error code `oauth_denied`).
- When re-authorizing an existing channel, leaving the two app credential fields masked keeps the stored values. A draining channel cannot be re-authorized: starting authorization answers 409 with error code `channel_deleting`.
- The client ID and secret are stored with the channel, so rclone renews the token with the same app once it expires.

## Token renewal and persistence

- Backend parameters are handed to rclone as a map with a write-back hook. When the access token nears expiry, rclone refreshes it itself and writes the new token back through the hook; ImgYoung immediately encrypts it with the master key and stores it in the channel configuration. Any other parameter rclone writes back at runtime takes the same path.
- Storing a write-back checks only the parameter being written back: it is stored only if the database still holds the value this driver last confirmed for it. If an edit changed that parameter (re-authorizing with a new token, for example), the write-back is dropped, so a write-back from an old driver never overwrites a token an edit just saved. If an edit changed only other parameters (priority, folder and so on) and left the token masked, the write-back is merged into the edited configuration as usual. Conversely, a write-back during an edit's save makes that edit answer 409 `channel_config_changed`; just save again, see [Editing a channel](./index.mdx).
- If storing fails, only a log line is written (`后端写回参数无法落库`): the driver keeps using the new token without being rebuilt, and the next write-back stores it; a restart before that falls back to the old token in the database.
- If a backend built temporarily while saving a channel refreshes the token, the new token is stored with the configuration when the save succeeds. When the save fails, the new token is not lost either:
  - A token submitted in the form (for a new channel, or newly authorized or pasted while editing) comes back in the `token` field of the error response and replaces the one in the form, with the notice "Saving failed, but the provider refreshed the authorization token meanwhile. The form now holds the new token; fix the problem and save again, no need to authorize again."
  - A stored token kept while editing is written straight back to the channel, which is then reloaded; it is not returned with the error.
- When a token gets refreshed during **Test connection**, there are two cases:
  - A stored token being kept (the **Authorization** field left at **Authorized · using the stored token** while editing) is written straight back to the channel.
  - A token submitted in this form (refreshed even if the test fails) is handed back to the form: below the result the form notes "The provider refreshed the authorization token during the test. The form now holds the new token and will save it; the old one may no longer work.", the **Authorization** field shows **Authorized**, and saving submits the new token. In custom mode the new token goes into the `token` row of the backend parameters.
- **There is exactly one refresher.** ImgYoung runs no refresh loop of its own: some providers invalidate the old refresh token on every refresh, so two refreshers would keep invalidating each other. The read-only requests of the periodic light check (every 60 s by default) are enough for rclone to refresh on time.
- When editing a drive channel, the **Authorization** field shows **Authorized · using the stored token**; leave it to keep the token, or click **Authorize again** to replace it.
- An [exported rclone config file](./encryption.mdx) carries the token too. Do not use that file while ImgYoung is still using the channel: with providers such as Box, whose refresh tokens are single-use, the two would keep invalidating each other's tokens. Once ImgYoung refreshes the token, the copy in the file is stale and you need to export again.

## Other OneDrive drives

The template only ever selects the account's default drive. For a SharePoint document library or another drive, enter `drive_id` and `drive_type` yourself under **New channel → Advanced → Custom**.

On a computer with a browser, create a OneDrive remote interactively with `rclone config`, pick the target drive when it asks, then show the parameters it wrote:

```bash title="Terminal"
rclone config
rclone config show onedrive-tmp
```

Copy the values into the custom form:

| Key | Value |
|---|---|
| rclone backend | `onedrive` |
| `token` | `token` from the `rclone config show` output |
| `drive_id` | Same source |
| `drive_type` | Same source (`personal`, `business` or `documentLibrary`) |
| `region` | Only outside the global cloud: `us`, `de` or `cn` |
| `client_id`, `client_secret` | Only if you used your own app in rclone |
| `path` | Folder for the images, such as `imgyoung` |

Custom mode stores the token as given; to re-authorize, replace the value of `token`. After saving, delete the temporary remote on your computer so that two places do not refresh the same token:

```bash title="Terminal"
rclone config delete onedrive-tmp
```

## Chinese cloud drives: WebDAV through a self-hosted aggregator

rclone has no backends for Aliyun Drive, Baidu Netdisk, 115, Quark and similar Chinese cloud drives. The open-source aggregators that do support them (Alist and the like) are licensed AGPL-3.0: porting their code into ImgYoung would force the whole project onto the AGPL, and would leave ImgYoung chasing these drives' API and anti-abuse changes indefinitely.

So ImgYoung does not port them. You deploy such an aggregator yourself and have it serve WebDAV, and ImgYoung connects with the generic WebDAV template. The two are separate processes that only talk over a network protocol, so the license does not carry over, and maintaining the drive integrations stays upstream.

<Steps>
<Step>
Deploy the aggregator following its own documentation, mount the drive you want, and enable WebDAV.
</Step>
<Step>
Create a dedicated account for ImgYoung with read, write and delete permissions. Deep checks, the daily reconciliation and channel draining all delete objects; without delete permission a channel cannot pass a deep check.
</Step>
<Step>
Create a WebDAV channel in ImgYoung: set **Server URL** to the aggregator's WebDAV address (for Alist, `https://domain/dav/`), choose **Other (Nutstore, Alist, Synology, …)** as **Server type**, enter the account and password, and set **Folder** to a dedicated folder under the drive's mount path in the aggregator.
</Step>
<Step>
Run **Test connection** to confirm write, read and delete all pass, give the channel a priority below your object storage channels, and save.
</Step>
</Steps>

## Limits of drive channels

- **Always proxied**: drives rarely offer stable public direct links, so drive templates have no public URL, and the form hides **Allow 302 direct links** and **Create the bucket automatically**. Even in `redirect` access mode, images on a drive are served through ImgYoung.
- **Rate and traffic limits**: drives limit request rates and traffic far more tightly than object storage, so heavy image traffic easily triggers throttling or anti-abuse measures. The periodic light check sends one read-only request per channel per round.
- **Full mirror**: like any channel, a drive channel ends up storing every image in the library.

That makes drives best suited as **low-priority backup channels**: give them a priority below your object storage channels so that normally they only receive asynchronous replication, and reads move to them only when the channels above are down. This trade-off is expressed entirely through priority, see [Channels and failover](./index.mdx).
