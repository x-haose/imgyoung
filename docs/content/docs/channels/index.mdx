## 渠道是什么

渠道是图片实际存放的地方。一个渠道对应一个 rclone 后端实例：一种后端（`s3`、`webdav`、`local` 等）加一组后端参数，再加上 ImgYoung 自己的几项属性：

| 属性 | 含义 |
|---|---|
| 渠道名 | 唯一，最长 64 字节，用于界面、日志、指标与告警 |
| 优先级 | 整数，越大越优先；后台表单接受 0–1000，新建默认 100 |
| 服务端加密 | 是否经 rclone crypt 加密存储，创建后不能修改，见[渠道存储加密](./encryption.mdx) |
| 允许 302 直链 | 访问时能否 302 跳转到渠道的公开地址，见[对象存储与 WebDAV](./object-storage.mdx) |

渠道在管理后台的「存储渠道」页创建和管理，只有管理员可见；对应的接口见[渠道管理接口](../api/admin-channels.mdx)。后端参数直接交给 rclone，不经过 `rclone.conf`，整体用主密钥加密（AES-256-GCM）后存在元数据库里。

接口与元数据导出里的渠道对象带 `created_at`，即渠道的创建时刻（UTC）。它和渠道 ID 一起参与加密渠道的密钥派生，创建后不变。渠道 ID 不会复用：删除渠道后再新建，拿到的是新的 ID。

**每个渠道最终都持有全部图片的副本。** 多个渠道之间是全量镜像，不是分片。规划容量时，每个渠道都要放得下全站的图片。

<Callout type="error" title="两个实例不能共用同一个渠道路径">
每日对账会删除 ImgYoung 写出、但元数据库里没有记录的对象（无主对象）。两个 ImgYoung 实例接入同一个存储路径时，对方写出的对象在本实例看来就是无主对象，48 小时后会被删除。每个实例要用各自的桶或路径。别的程序写进同一路径的文件只计数，不会删除。判定规则见[备份与恢复](../operations/backup.mdx#对账-gc)。
</Callout>

## 内置 local 渠道

全新的元数据库首次启动时，ImgYoung 会自动创建一个名为 `local` 的渠道：后端 `local`，优先级 100，存储位置 `<数据目录>/blobs`。所以不做任何配置也能上传。

- 这个渠道只在全新的元数据库上创建一次。删除或改名之后，重启不会让它重新出现，删光所有渠道也一样。
- `local` 渠道的 `path` 必须是绝对路径，留空即用 `<数据目录>/blobs`。

<Callout type="warn" title="只有本机磁盘一个渠道时">
内置 local 渠道和元数据库、主密钥在同一台机器上，主机损坏就会全部丢失。只有这一个渠道时，「存储渠道」页会提示「只有本机磁盘一个渠道」。接入一个异地渠道后，已有图片会自动补齐到新渠道；从下一次备份起，新渠道上也会有元数据库快照。
</Callout>

## 新建渠道

在「存储渠道」页点「新建渠道」，先选存储类型，再填表单：

<Steps>
<Step>
选类型：「对象存储」和「网盘」下是内置模板，「高级」下是「自定义」（直接填 rclone 后端名与参数）。各模板的字段见[对象存储与 WebDAV](./object-storage.mdx)与[网盘与 OAuth](./cloud-drives.mdx)。
</Step>
<Step>
填写渠道名、模板字段和优先级，选择「服务端加密」。对象存储还可以打开「允许 302 直链」与「自动创建存储桶」。
</Step>
<Step>
点「测试连接」，通过后点「创建」。
</Step>
</Steps>

创建时，ImgYoung 先用填写的参数构造一次后端，参数非法直接拒绝。需要授权的模板会先补齐授权带出的参数，如 OneDrive 的驱动器。

渠道保存后立即做一次深探测（见[健康探测](#健康探测)）。深探测失败不会撤销创建：渠道保留，状态为「异常」，并提示「渠道已创建，但探测失败：」加原因。改好配置后点「重新探测」即可。

新渠道创建后，全部存量图片都会自动补齐到它上面，见[异步补齐](#异步补齐)。

## 测试连接

新建与编辑表单底部的「测试连接」用表单当前的内容做一次深探测，**不保存，也不创建渠道**。

- 通过时显示「连接正常（写入、读取、删除均通过）」。失败时显示「连接失败：」加失败原因，写法与「状态」列相同（见[失败原因](#失败原因)），其中的凭证已抹掉。
- 不会创建存储桶，也不套加密层，只验证后端的连通性和写、读、删权限。
- 编辑时，保持掩码的凭证会先换回已保存的值再探测。
- 接口响应是 `{ok, failure}`，失败时 `failure` 为 `{reason, detail}`。

网盘渠道在测试连接或保存时，服务商可能刷新授权令牌。新令牌不会丢失，去向见[网盘与 OAuth](./cloud-drives.mdx#测试连接与保存时的令牌刷新)。

## 主渠道与备份渠道

ImgYoung 没有单独的「主渠道」开关，主备完全由优先级决定：

- **主渠道**：健康且不在清理中的渠道里，优先级最高的那个。列表里标为「主渠道」。
- **备份渠道**：其余渠道。正常情况下，上传不直接写它们，由异步补齐把副本复制过去。只有更高优先级的渠道写入失败，或「最少同步副本」大于 1 时，上传才会同步写入它们。
- 优先级相同时，先创建的渠道排在前面。

主渠道变为异常时，下一个健康渠道自动接替，不需要人工切换。原来的主渠道恢复健康后，重新成为主渠道。

## 上传写入

每次上传按优先级从高到低，依次同步写入当前健康的渠道，直到成功的份数达到「最少同步副本」（`min_success`）：

1. 写入某个渠道失败（包括单次 10 分钟的写入超时），就换下一个健康渠道。
2. 份数凑够即返回成功。第一个写成功的渠道持有这张图的首个副本。
3. 其余渠道（包括暂时异常的渠道）各记一条待补齐的副本，由异步补齐完成。

「最少同步副本」在「设置 → 运行配置 → 访问与链接 → 最少同步副本」，默认 1，最小 1。

以下情况上传失败，返回 503（错误码 `upload_unavailable`），不记录任何元数据：

- 健康渠道不足，或全部写入失败；
- 上传期间某个已写入的渠道转为「清理中」，它上面的副本不再计数，剩下的副本不足「最少同步副本」。

上传无论在哪一步失败，本次写进渠道的对象都会随即删除。删除失败或进程中途退出而没删掉的：在役渠道上的由每日对账作为无主对象回收；上传期间转为「清理中」的渠道上的会留在存储商处，见[删除渠道](#删除渠道)。

<Callout type="info">
「最少同步副本」大于当前健康渠道数时，所有上传都会失败。设为 2 表示至少两个渠道同时写成功才算上传成功，代价是写入时延更长，并且依赖多个渠道同时可用。
</Callout>

## 异步补齐

上传时没有同步写到的渠道，由后台任务把副本复制过去，这个过程叫补齐。每张图在每个渠道上的副本都有一个状态：

| 副本状态 | 含义 |
|---|---|
| `pending` | 待补齐 |
| `uploading` | 补齐中 |
| `done` | 就绪，可用于访问 |
| `failed` | 重试用尽仍失败，或目标渠道未装载 |

副本状态以元数据库里的副本表为准，任务队列（River，与元数据库在同一个 SQLite 库里）只负责触发补齐。

- **复制**：从优先级最高、健康且已有就绪副本的其他渠道读出，流式写入目标渠道。任务队列分两条：默认队列最多同时执行 4 个任务（上传时的补齐、删除、排空与 CDN 缓存清理共用），补课队列最多同时执行 3 个补齐任务，见下文「补课队列」。单个补齐任务最长 15 分钟。
- **重试**：失败后改回 `pending`，按指数退避重试：第 n 次失败后约等 n⁴ 秒（1 秒、16 秒、81 秒……），最多 25 次，前后约 20 天。最后一次仍失败，记为 `failed`。
- **周期对账**：启动时和之后每 10 分钟各做一次：为每个不在清理中的渠道补上缺失的副本记录，把健康渠道上的 `failed` 副本改回 `pending`，把所有未完成的副本重新排队。「设置 → 运行配置 → 引导配置」里的「副本对账间隔」就是这个间隔。
- **重启**：任务和副本状态都存在 SQLite 里，重启不会丢失。正常停机时，进行中的补齐任务被取消，下次启动由周期对账重新排队；进程被强制终止时，正在执行的任务约 16 分钟后重新执行。
- **新渠道**：创建渠道时，全部存量图片都登记为待补齐，随即开始复制。与创建同时进行的上传如果漏掉了新渠道，周期对账会补上。
- **补课队列**：新渠道的存量补齐，以及周期对账和启动对账重新排队的补齐，走独立的补课队列，与上传时的补齐、删除、排空所在的默认队列互不占用 worker。所以迁移期间新上传的图片仍会很快补齐到各渠道，不会排在整批存量补齐之后。需要限制补课占用的带宽时，见 `replicate_limit_mbps`（[配置](../configuration.mdx#可靠性与渠道)），它只作用于补课队列。
- **每日对账 GC**：每 24 小时核对一次健康渠道上的对象。写入超过 48 小时的无主对象会被删除；元数据库记为就绪、渠道上却没有的副本，改回 `pending` 重新补齐。见[备份与恢复](../operations/backup.mdx#对账-gc)。

## 访问容灾

访问一张图时，候选渠道是**健康、不在清理中、并且这张图的副本已就绪**的渠道，按优先级排序。副本还没补齐到的渠道不是候选。

- **代理模式**（`access_mode = proxy`，默认）：按顺序读取，一个渠道读失败就换下一个，访问者感知不到。没有候选或全部读失败时，返回 503 `渠道暂不可用`。
- **302 模式**（`access_mode = redirect`）：候选中第一个允许 302 直链、未加密、并配置了公开访问地址的渠道，直接 302 跳转；没有这样的渠道就走代理。

302 模式下，需要生成衍生图的请求始终走代理：带 `w`、显式指定与原图不同的 `format`，或按 `Accept` 协商为 WebP。浏览器都声明支持 WebP，所以浏览器访问 JPEG / PNG 默认也走代理转码。最终返回原图的请求照常 302。

访问模式与缓存的细节见[访问图片](../guides/access.mdx)。

## 健康探测

健康状态决定一个渠道能否承接上传与访问。探测分两种：

| | 轻探测 | 深探测 |
|---|---|---|
| 做什么 | 查询一个不存在的对象 `.imgyoung-health-probe`（从不写入），查到或得到「不存在」都算可达 | 写入一个随机键名的小对象 `.imgyoung-probe-<随机十六进制>`，读回核对内容，再删除 |
| 成本 | 只读，不写不删 | 一次写、读、删 |
| 超时 | 10 秒 | 写与读共 20 秒，删除另有 10 秒 |
| 何时运行 | 周期循环，每隔 `health_check_seconds`（默认 60 秒）| 创建渠道后、编辑保存后、点「重新探测」或「测试连接」时；周期循环里异常渠道的轻探测通过时 |

周期循环里，**轻探测只能把渠道标为异常，不能让它恢复健康**：

- 健康渠道每轮只做轻探测，失败即标为异常。
- 异常渠道先做轻探测；通过后再做一次深探测，写、读、删全部通过才恢复健康。
- 例如只读凭证能通过轻探测，但写不进去。这样的渠道不会因为轻探测通过而恢复健康。

周期循环只用只读的轻探测，是为了不让按量计费的存储每分钟都产生写入和删除的费用。写入方面的问题由深探测发现。

各渠道并行探测、各自计时，一个慢渠道不会拖慢其他渠道。清理中的渠道不做探测。

探测结果显示在「存储渠道」页的「状态」列：「健康」「异常」或「清理中」。下方小字是最近一次探测的时间，从未探测过时显示「未探测」。

### 失败原因

鼠标悬停在「异常」上会显示失败原因，写法是「归类说明（根因原文）」，例如「认证失败（403）：检查 Access Key / Secret Key 及其权限（…）」。无法归类时只显示根因原文。归类说明跟随界面语言；根因原文照抄，多为服务商或网络库的英文原文。装载或清理时的失败，原因前面还有一段环节说明，见[渠道无法装载](#渠道无法装载)与[清理失败](#清理失败)。

接口返回的渠道对象里，失败原因在 `failure` 字段：`null` 表示最近一次探测成功或从未出错，否则是 `{stage, reason, detail}`：

| 字段 | 含义 |
|---|---|
| `stage` | 失败环节：`probe` 健康探测；`load` 按配置装载驱动；`drain` 清理中的渠道删除对象 |
| `reason` | 归类，如 `s3_auth`、`bucket_missing`、`timeout`；无法归类时为 `unclassified`。全部取值与排查方法见[对象存储与 WebDAV](./object-storage.mdx#失败原因) |
| `detail` | 根因原文：错误链最内层的错误，已抹除凭证；最长 200 个字符，超长时截到 199 个字符再加「…」 |

### 渠道无法装载

渠道的配置无法解密，或后端初始化失败时，这个渠道会被跳过，其余渠道照常服务。

- 列表里显示为「异常」，失败环节是 `load`，原因前面加「装载失败：」。
- 配置无法解密时归类为 `config_unreadable`，多半是当前的主密钥与写入配置时用的不同。
- 各渠道并行装载，每个渠道构造驱动最多等 30 秒，所以一个不可达的后端不会拖住启动、重载或健康检查。到点仍未完成的（如后端不可达，或 `ftp` 这类构造时不响应取消的后端），按装载失败归类为 `timeout`，界面与告警里的根因原文是 `context deadline exceeded`。测试连接、新建和编辑时构造后端也有同样的 30 秒上限。
- 超时之后，这次构造仍在后台继续，直到后端自身超时才结束。在此之前，用同一份配置（后端名、参数、路径都相同）再次装载或测试连接，会立即以超时失败。
- 每一轮健康检查都会先重试装载，点「重新探测」也会先尝试装载。装上之后，还要通过一次深探测才恢复健康。
- 启动时全部渠道都无法装载，则启动失败。

相关日志见页末的[日志](#日志)。

## 副本统计

「副本」列显示该渠道上各状态的副本数：就绪、待补（含补齐中）、失败，以及完成百分比，即就绪数除以就绪、待补、失败三者之和；三者都为 0 时不显示百分比。

「待补」和「失败」的数字可以点开，进入该渠道的「副本清单」，列出对应状态的副本：图片短 ID、引用张数、状态、尝试次数、最近失败的原因、大小、类型和更新时间，最近有变化的在前。清单里的「重试失败的副本」把该渠道上失败的副本全部改回待补并重新排队，不必等下一次周期对账；渠道在清理中时不能重试（`channel_deleting`），渠道此刻不健康时副本会再次失败。每次重试记入审计日志。完整的迁移步骤见[迁移存储渠道](../operations/migrate-channel.mdx)。

待补长期不降，或出现失败，说明写入这个渠道有问题：先看「状态」列的失败原因，再点「重新探测」确认。渠道恢复健康后，失败的副本会在下一次周期对账时重新补齐。

## 编辑渠道

行菜单「编辑」打开与新建相同的表单。可以修改渠道名、模板字段（或自定义参数）、优先级和「允许 302 直链」。以下几项不能修改：

- 「服务端加密」：表单只显示「已加密」或「未加密」，接口拒绝修改，见[渠道存储加密](./encryption.mdx#创建后不可变)。
- 存储类型：编辑沿用创建时的模板。自定义渠道和内置 local 渠道以自定义表单打开。
- 「自动创建存储桶」：只在创建时出现。

保存时配置整体替换，不做增量合并。保存后只重建这一个渠道的驱动，其他渠道正在进行的读写不受影响。随后立即做一次深探测，失败时提示「渠道已保存，但探测失败：」加原因。

### 凭证掩码

编辑表单不回传凭证，而是以固定的掩码值 `__imgyoung_secret_keep__` 代替：

- 保持掩码值原样提交，就沿用已保存的值；输入新值即替换。
- 哪些参数算凭证，以 rclone 后端的选项元数据为准：rclone 标为密码或敏感信息的参数都会掩码。除了密码、密钥和授权令牌，还包括访问密钥 ID（Access Key、SecretId、Key ID）、WebDAV 用户名、应用 Client ID、OneDrive 的 `drive_id` 等。
- 模板表单按同一份元数据决定哪些栏用掩码输入框。自定义参数的值一律用掩码输入框（可以逐栏点开查看），因为界面无法判断自定义的键是不是凭证。
- 把掩码值填在不是凭证的参数上，保存会被拒绝（400）。

### 保存冲突

保存时，ImgYoung 核对渠道配置是否还是开始保存时读到的那份。如果保存期间另有一次编辑先保存了，或者服务商刷新令牌后写回了渠道，这次保存不生效，返回 409（错误码 `channel_config_changed`），重新保存即可。

### 绑定时刻

**绑定时刻**是渠道开始使用当前存储位置的时刻。每日对账只删除写入时间不早于绑定时刻的无主对象。

- 新建渠道时，绑定时刻等于创建时刻。
- 后端名或任一配置参数（包括公开访问地址）有改动，绑定时刻重置为保存时刻。重新输入相同的密码也算改动，因为 rclone 编码密码时带随机 IV。
- 只改渠道名、优先级或「允许 302 直链」不重置，令牌刷新后的写回也不重置。
- 重置之后，新位置上早于这一刻的、符合本服务键名格式的对象只计数，不删除。

从快照恢复时，全部渠道的绑定时刻也会重置，完整规则见[备份与恢复](../operations/backup.mdx#对账-gc)。

<Callout type="warn" title="不要用编辑来迁移存储位置">
编辑不会触发补齐。改了桶、前缀或服务端点之后，这个渠道上原有的副本仍记为就绪，读取会失败并切到其他渠道，直到每日对账发现对象缺失、重新补齐。要换存储位置，应新建一个渠道，等它「副本」列的「待补」归零、也没有「失败」后，再删除旧渠道，见[迁移存储渠道](../operations/migrate-channel.mdx)。
</Callout>

## 删除渠道

行菜单「删除」打开确认框。勾选项「同时删除本服务写在该渠道上的数据」决定走哪条路径：

| | 删除并清理（默认勾选）| 仅移除（取消勾选）|
|---|---|---|
| 立即效果 | 渠道转为「清理中」，立刻退出上传、补齐与探测 | 渠道和它的副本记录立即删除 |
| 远端对象 | 本服务记录在案的对象由后台的排空任务逐个删除，删完自动移除渠道；渠道里的其他对象不删除 | 图片副本和元数据库快照原样保留，需要时自行到存储商处处理 |
| 适用 | 正常下线一个渠道 | 凭证已失效、桶已不存在，或清理卡住 |

**唯一副本保护**：如果某张图在其他渠道上没有就绪的副本（清理中的渠道不算），两种删除都会被拒绝，返回 409（错误码 `channel_sole_replicas`）。其他渠道上待补或失败的副本不算，等它们就绪后再删。先后删除两个渠道时，这项检查同样生效，不会删光一张图的全部副本。

### 清理过程

选「删除并清理」后，排空任务按以下顺序删除对象：

1. 按副本记录分批删除图片对象，同时删掉对应的副本记录。进度保存在元数据库里，中断后从剩余部分继续。
2. 删除 `_imgyoung/` 下的全部对象（包括 `_imgyoung/backup/` 下的元数据库快照）和根目录下的探测残留 `.imgyoung-probe-*`。这一步只列举 `_imgyoung/` 和根目录这一层，不遍历其他子目录。
3. 删除渠道记录。

别的程序写的文件不动。此外：

- 渠道转为「清理中」后，新的写入立即被拒绝。排空会等正在进行的写入结束后再开始，本服务写下且已有记录的对象都会被删除。
- 排空只删除上面这些记录在案的对象，每日对账也不扫描清理中的渠道。上传失败后没能删掉、也还没被对账回收的无主对象，清理后会留在存储商处。
- 单次排空最长 1 小时。遇到停机，或超时前已删掉部分对象时，下一次从剩余部分继续，不算失败，也不计入尝试次数；一个对象也没删掉就超时，按失败计。
- 清理中的渠道（即使装载失败）不能编辑、测试连接、重新探测或重新授权。行菜单里只有「直接移除」，接口返回 409（错误码 `channel_deleting`）。

### 清理失败

删除对象失败时自动退避重试，一直重试到清完为止。渠道恢复可用后，清理会自行完成。

- 同一个排空任务第 4 次尝试仍失败时（按默认退避，各次尝试都很快失败时约在首次失败 98 秒后），「状态」列才显示原因，并开启「渠道排空失败」告警。在此之前只显示「清理中」，一次网络抖动不会留下原因或告警。
- 排空失败的环节是 `drain`，界面在归类说明前加上「清理渠道对象失败，会自动重试；凭证已失效或存储桶已不存在时可直接移除（远端对象保留）：」。
- 清理中的渠道装载失败（环节 `load`）时，原因立即显示，并开启「渠道排空失败」告警，因为装不上就无法排空。渠道一装上，这条原因随即清除，告警恢复；之后是否再告警，取决于排空本身的失败。
- 转为「清理中」时，渠道此前的失败原因会清空。此后「状态」列的原因只来自排空失败和装载失败。
- 已显示的排空失败原因和告警会保留到清理完成。对已在清理中的渠道再次「删除并清理」，不会改变任何状态。

### 直接移除

凭证已失效或桶已不存在时，用「直接移除」立即移除渠道。正在进行的排空随之停止：除了正在删除的那一个对象，剩下的远端对象（包括 `_imgyoung/backup/` 下的快照）原样保留。

## 导出 rclone 配置

行菜单「导出 rclone 配置」下载渠道的 rclone 配置文件 `imgyoung-channel-<渠道 ID>.rclone.conf`，清理中的渠道没有这一项。凭这个文件，标准 rclone 不经过 ImgYoung 也能读写这个渠道上的数据。文件里有：

- 远端 `imgyoung-<渠道 ID>`：渠道的后端，参数与 ImgYoung 交给后端的完全一致，包括访问凭证和授权令牌。
- 远端 `imgyoung-<渠道 ID>-crypt`：只有加密渠道才有，是指向渠道存储路径的加密层，经它读写的就是明文。
- 文件开头的注释：说明各远端的含义并给出用法示例，有中文和英文两种，从后台下载时跟随界面语言。

文件里有渠道凭证，加密渠道还有解密密码。弹窗会提示「和主密钥一样离线妥善保存：拿到它的人可以直接读写这个渠道上的全部数据。」

点「下载配置文件」后，文件完整取回才保存到本地。下载失败时（如 422、404 或传输中断），原因显示在页面右下角的提示里，弹窗保持打开，可以重试；关闭弹窗即取消下载。每次下载都记一条审计日志「导出渠道 rclone 配置」。

文件的用法与注意事项见[渠道存储加密](./encryption.mdx#用标准-rclone-读出渠道数据)。

## 用量与告警

渠道用量是该渠道上**已就绪副本的图片大小之和**，属于逻辑用量：不含元数据库快照和无主对象，也不等于存储商的账单。

- 每隔 `usage_report_seconds`（默认 300 秒）刷新一次，写入指标 `imgyoung_channel_storage_bytes{channel="…"}`。「总览」页的「存储渠道」卡片显示各渠道的已存字节和占比。
- 告警阈值在「设置 → 运行配置 → 可靠性与渠道 → 渠道用量告警阈值」（`channel_quota_gb`，单位 GB，按 2³⁰ 字节计），0 表示只上报、不告警。超过阈值时开启「渠道用量超阈值」告警。

与渠道相关的告警有四种，和健康探测按同一节奏评估，记录在「设置 → 告警历史」，配置了告警 Webhook 时同时外发：

| 告警 | 开启条件 | 恢复条件 |
|---|---|---|
| 渠道不健康 | 不在清理中的渠道被标为异常 | 探测恢复健康 |
| 副本补齐失败 | 渠道上有 `failed` 副本 | 渠道上不再有 `failed` 副本。渠道健康时，周期对账会把它们改回待补齐重试 |
| 渠道用量超阈值 | 用量大于阈值 | 用量回落或阈值调高 |
| 渠道排空失败 | 清理中渠道的同一个排空任务第 4 次尝试仍失败，或清理中的渠道装载失败 | 渠道被移除（清完后自动移除，或直接移除）；因装载失败开启的，渠道装上即恢复 |

告警描述跟随界面语言。告警对象和 Webhook 请求体的 `params` 带有结构化的取值，如渠道失败的 `stage`、`reason`、`detail`。指标与告警的接入见[监控与告警](../operations/monitoring.mdx)。

其他相关指标：

| 指标 | 含义 |
|---|---|
| `imgyoung_channels_healthy_total` | 健康渠道数 |
| `imgyoung_channels_total` | 已装载且不在清理中的渠道数，含异常渠道 |
| `imgyoung_channel_puts_total{channel, result}` | 向渠道写对象的次数，`result` 为 `ok` 或 `error`；含上传时的同步写入与异步补齐 |

## 参考

### 错误码

| 操作 | 状态码 | 错误码 | 含义 |
|---|---|---|---|
| 上传 | 503 | `upload_unavailable` | 健康渠道不足，或全部写入失败；S3 兼容接口的上传返回 503 `ServiceUnavailable` |
| 访问图片 | 503 | — | 没有候选渠道，或全部读取失败；响应正文为 `渠道暂不可用` |
| 新建、编辑 | 400 | `channel_local_path_relative` | `local` 渠道的 `path` 不是绝对路径 |
| 新建、编辑 | 400 | `channel_encrypted_direct_link` | 同时要求加密与 302 直链 |
| 编辑 | 409 | `channel_encrypted_immutable` | 试图修改「服务端加密」 |
| 编辑 | 409 | `channel_config_changed` | 保存期间渠道配置被另一次编辑或令牌写回改动，重新保存即可 |
| 删除 | 409 | `channel_sole_replicas` | 渠道持有部分图片的唯一副本，参数 `count` 为这类图片的张数 |
| 编辑、测试连接、重新探测、重新授权 | 409 | `channel_deleting` | 渠道在清理中 |
| 导出 rclone 配置 | 422 | `channel_unrepresentable` | 有参数值无法写进 rclone 配置文件，见[渠道存储加密](./encryption.mdx#用导出的配置文件) |

保存表单时的其他错误码见[对象存储与 WebDAV](./object-storage.mdx#保存时的错误码)。

### 日志

| 日志 | 含义 |
|---|---|
| `渠道装载失败,本渠道跳过,健康检查时重试` | 渠道无法装载，已跳过；字段 `err` 为失败原因。构造后端超过 30 秒时为 `构造后端未在时限内完成: context deadline exceeded`；同一配置上一次超时的构造仍在后台运行、这次没有再构造时为 `构造后端未在时限内完成(同一配置上一次构造仍未结束): context deadline exceeded` |
| `渠道已清理完毕并删除` | 排空完成，渠道已移除；字段 `objects` 为最后一次排空执行中删除的图片副本数，`system_objects` 为删除的系统对象数 |
