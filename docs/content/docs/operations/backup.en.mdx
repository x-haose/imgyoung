## What to back up

Images are stored in your channels under their content hash; which short link points to which image, and which user owns it, is recorded in the metadata database. As a result:

- if you lose the metadata database, the images in your channels can no longer be matched to their links;
- if you lose the master key, the instance cannot start, and channel credentials and encrypted channel data can no longer be decrypted.

| What | Where | How |
|---|---|---|
| Master key | `<data dir>/master.key`, or the `IMGYOUNG_MASTER_KEY` variable | Copy it offline right after the first start and keep it apart from the snapshots. See [Configuration](../configuration.mdx#master-key) |
| Metadata database | `<data dir>/imgyoung.db` | Automatic snapshots are written to every healthy channel; also download a copy regularly and keep it elsewhere |
| Images | Your channels | Configure two or more channels so each image has several replicas. The built-in local channel stores its data in `<data dir>/blobs/` |
| rclone config of encrypted channels | **Export rclone config** on the **Storage channels** page | Export one per encrypted channel and keep it offline like the master key. See [Channel encryption](../channels/encryption.mdx) |
| Deployment configuration | Environment variables, systemd drop-ins, `compose.yaml`, reverse proxy configuration | Your own configuration management |

`<data dir>/variants/` caches resized and converted images; it is regenerated on demand and needs no backup.

Do not copy `imgyoung.db` while the service is running: recent writes may still be in `imgyoung.db-wal`, so the copy would be incomplete. For a complete copy, download a snapshot from the admin console, or stop the service first.

## Automatic metadata snapshots

ImgYoung takes snapshots of the metadata database on a schedule and writes the same snapshot to every healthy channel.

- **Schedule**: one snapshot every **Backup interval** (`backup_interval_hours`, 24 hours by default), counted from service start; changing the interval restarts the countdown. At startup, if any healthy channel lacks a snapshot from within the last interval, a backup runs immediately.
- **Location**: `_imgyoung/backup/` under the channel's path, with names like `imgyoung-20261015-083000.123.db` (UTC). On the built-in local channel that is `<data dir>/blobs/_imgyoung/backup/`. Snapshots on encrypted channels are encrypted too.
- **Retention**: each channel keeps only its newest **Backups to keep** (`backup_keep`, 7 by default) snapshots; older ones are deleted automatically.
- **Disk space**: the snapshot is first written to a temporary file `backup-snapshot.tmp` in the data directory, which needs free space of roughly the database size.
- **Failure**: if the snapshot cannot be taken, there is no healthy channel, a channel was not written, or a channel could not prune old snapshots down to the retention count, the backup counts as failed and opens a `backup_failed` alert, which resolves after the next success. Channels that were written keep the snapshot. See [Monitoring & alerts](./monitoring.mdx).

When you delete a channel, **Delete and purge** deletes the snapshots on it as well; **Remove only** leaves them in place.

<Callout type="warn" title="Your data only lives on this host">
If there is no healthy channel besides the built-in local channel, images and snapshots exist only on this host's disk and are lost if the host fails. The dashboard then shows **Your data only lives on this host**. Once you add an object storage or cloud drive channel, snapshots are written there as well.
</Callout>

<Callout type="warn" title="Snapshots on encrypted channels">
The keys that decrypt a snapshot on an encrypted channel are derived from the master key together with the channel details recorded in the metadata database. Once the metadata database is lost, the only way to read those snapshots is with the config file saved beforehand through **Export rclone config**. So keep snapshots on at least one unencrypted channel, or export the rclone config of every encrypted channel and keep it offline. See [Channel encryption](../channels/encryption.mdx).
</Callout>

## Managing snapshots in the admin console

**Settings → Backups & export → Metadata snapshots** lists the snapshots on all healthy channels, newest first; **Stored on** shows which channels hold each snapshot. Snapshots on unhealthy or draining channels are not listed.

- **Back up now**: take a snapshot right away, write it to every healthy channel, and prune old snapshots down to the retention count. Clicking again while a backup is running schedules one more backup after the current one — just one, however many times you click — so every click gets a snapshot taken after it.
- **Download**: download the snapshot file, which is itself an SQLite database. It is read from the channels holding it in priority order, moving on to the next channel if a read fails, and is saved only once fetched completely.
- **Restore**: replace the current metadata database with this snapshot; see the next section.

Backups run on the server, so closing the page or a reverse proxy timeout does not interrupt them. If the reverse proxy times out first (Nginx returns 504, Cloudflare returns 524), the backup still completes on the server: refresh the list later, and click again only if no new snapshot appears.

For status and error codes, see [Error codes](#error-codes) at the end of this page.

## Restoring from a snapshot

A restore takes all metadata back to the time of the snapshot.

<Steps>
<Step>

**Start the restore**: click **Restore** on the snapshot's row and confirm with **Restore and restart**. The service downloads the snapshot to `imgyoung.db.restore` in the data directory, checks that it is complete, and then stops.

</Step>
<Step>

**Restart**: a process manager starts the service again: `--restart unless-stopped` for Docker, `restart: unless-stopped` for Compose, `Restart=always` for systemd; the examples in `deploy/` are already set up this way. A binary run directly in a terminal simply exits, and the restore completes the next time you start it.

</Step>
<Step>

**Swap in the snapshot**: at startup the service replaces the current database with the snapshot and upgrades it to the current schema. The previous database is renamed to `imgyoung.db.pre-restore-<UTC time>` and kept in the data directory; delete it by hand once you are satisfied with the restore.

</Step>
<Step>

**Sign in again**: the admin console reloads once the service is back. Accounts and passwords are back to snapshot time too, so sign in with the password you had then.

</Step>
</Steps>

If the snapshot is incomplete or is not an ImgYoung metadata database, the restore is refused and the service keeps running; pick another snapshot. If the service was killed (for example `kill -9` or a power loss), a half-written snapshot may be left on the local channel; it shows up in the list but cannot be used to restore.

### After a restore

Changes made after the snapshot are lost, and the objects in your channels no longer match the metadata:

- **Images uploaded after the snapshot** are not in the metadata and can no longer be reached through ImgYoung. Their objects stay on the channels and are never deleted automatically.
- **Images deleted after the snapshot** reappear in the metadata, but their objects are gone, so they fail to load and raise **Replication failed** alerts. Delete them in the admin console.
- **Everything else** — channels, users and tokens created after the snapshot, changed runtime settings and hotlink rules — goes back to snapshot time.

### Restoring behind a reverse proxy

The restore request waits until the snapshot has been downloaded and checked. If the request is cut off before then (the page is closed, the reverse proxy times out), the restore is cancelled: the service keeps running and nothing changes. The reverse proxy's read timeout must therefore be longer than it takes to download the snapshot from the channel:

- **Nginx**: `proxy_read_timeout` defaults to 60 seconds; the `deploy/nginx.conf` example sets it to 600 seconds. On a timeout (504) the restore has been cancelled and nothing changed.
- **Cloudflare**: the read timeout is fixed at 125 seconds and only Enterprise plans can change it. On a timeout (524) it is unknown whether the restore completed: if Cloudflare kept its connection to the origin open, the restore completes there and the service restarts on its own. For snapshots that take longer than 125 seconds to download, open the admin console on the origin directly, or put the snapshot in place by hand as described in [disaster recovery](#disaster-recovery-after-losing-the-host) below.

See [Reverse proxy & HTTPS](./reverse-proxy.mdx).

## Disaster recovery after losing the host

Before you start, you need:

- the original instance's master key: a backup of `master.key`, or the value of `IMGYOUNG_MASTER_KEY`;
- a snapshot file, from one of:
  - a snapshot you downloaded;
  - any **unencrypted** channel: download the newest `imgyoung-*.db` under `_imgyoung/backup/` in the channel's path with the provider's console or rclone;
  - an encrypted channel: read it with the rclone config you exported beforehand; see [Channel encryption](../channels/encryption.mdx).

<Steps>
<Step>

**Install**: install the same or a newer version on the new machine; see [Installation](../install/index.mdx). It does not matter if it has already started once, but the `master.key` it generated on first start must be replaced with the original in the next step.

</Step>
<Step>

**Stop the service and put the master key and snapshot in place**: put the original master key in the data directory as `master.key`, and the snapshot file in the data directory as `imgyoung.db.restore`.

Do not overwrite `imgyoung.db` with the snapshot. A snapshot put in place as `imgyoung.db.restore` is handled as a restore, which keeps the objects written to the channels after the snapshot; if you overwrite the database directly, those objects are treated as orphans: reconciliation GC first runs 24 hours after the service starts and then every 24 hours, and each run deletes the orphans written more than 48 hours earlier.

A snapshot put in place by hand skips the integrity check that restores from the admin console get, so you may want to check it yourself: `sqlite3 imgyoung-20261015-083000.123.db 'PRAGMA quick_check;'` should print `ok`, and the output of `sqlite3 imgyoung-20261015-083000.123.db '.tables'` should include `schema_revisions`.

<Tabs items={['Binary', 'Docker', 'Compose', 'systemd']}>
<Tab value="Binary">

```bash title="Terminal"
mkdir -p data
cp imgyoung-master.key data/master.key && chmod 600 data/master.key
cp imgyoung-20261015-083000.123.db data/imgyoung.db.restore
```

</Tab>
<Tab value="Docker">

The image runs as uid 65532 and has no shell, so use a throwaway container to write into the volume and fix ownership:

```bash title="Terminal"
# If the container is running, docker stop imgyoung first; if there is none yet, create it with your usual options (without starting it)
docker create --name imgyoung --restart unless-stopped -p 8721:8721 \
  -v imgyoung-data:/data ghcr.io/x-haose/imgyoung:latest
docker run --rm --volumes-from imgyoung -v "$PWD":/in:ro alpine:3.24 sh -c '
  cp /in/imgyoung-master.key /data/master.key &&
  cp /in/imgyoung-20261015-083000.123.db /data/imgyoung.db.restore &&
  chmod 600 /data/master.key &&
  chown 65532:65532 /data /data/master.key /data/imgyoung.db.restore'
docker start imgyoung
```

</Tab>
<Tab value="Compose">

```bash title="Terminal"
docker compose stop        # if it has never been started, use docker compose create instead
docker run --rm --volumes-from "$(docker compose ps -a -q imgyoung)" -v "$PWD":/in:ro alpine:3.24 sh -c '
  cp /in/imgyoung-master.key /data/master.key &&
  cp /in/imgyoung-20261015-083000.123.db /data/imgyoung.db.restore &&
  chmod 600 /data/master.key &&
  chown 65532:65532 /data /data/master.key /data/imgyoung.db.restore'
docker compose up -d
```

</Tab>
<Tab value="systemd">

After `install.sh --service` the service has already started once, so systemd has created `/var/lib/imgyoung` and handed it to the service user. Give the new files the same owner as the existing database:

```bash title="Terminal"
sudo systemctl stop imgyoung
sudo cp imgyoung-master.key /var/lib/imgyoung/master.key
sudo cp imgyoung-20261015-083000.123.db /var/lib/imgyoung/imgyoung.db.restore
sudo chown --reference=/var/lib/imgyoung/imgyoung.db \
  /var/lib/imgyoung/master.key /var/lib/imgyoung/imgyoung.db.restore
sudo chmod 600 /var/lib/imgyoung/master.key
sudo systemctl start imgyoung
```

</Tab>
</Tabs>

If you provide the master key through `IMGYOUNG_MASTER_KEY`, set the variable instead of placing the file.

</Step>
<Step>

**Start and check**: for the binary, start `imgyoung` now. The log line `已用暂存快照换入元数据库,原库留存` confirms that the snapshot has been swapped in. Sign in with the credentials from snapshot time and check on **Storage channels** that the channels are healthy again.

If startup fails saying the master key does not match the database, or that no master key can be found, the key you put in place is not the original instance's key, or there is none. The snapshot has already been swapped in at that point: put the right master key in place and start again; there is no need to put the snapshot in place again.

</Step>
</Steps>

After recovery, images that existed only on the local channel are gone with the old host. Images with replicas on other channels load as usual, and the replicas missing from the local channel are copied back from the other channels during the daily reconciliation.

### Without fetching the snapshot file

If a snapshot is on an unencrypted channel, the new instance can read it from the channel directly:

1. Start a fresh instance with the original master key: put `master.key` in place or set `IMGYOUNG_MASTER_KEY` before the first start. Otherwise, when the service restarts after the restore, the key does not match the snapshot and the service refuses to start. If it has already started with a generated key, stop it, put the original `master.key` in place, delete `imgyoung.db` (along with `imgyoung.db-wal` and `imgyoung.db-shm`) from the data directory, and start it again.
2. In the admin console, add the channel holding the snapshots with its original parameters. Objects already in the channel are not deleted.
3. Pick a snapshot under **Metadata snapshots** and restore it.

<Callout type="warn" title="Restore soon after adding the channel">
Between adding the channel and restoring, do not click **Back up now** and do not restart the instance. Otherwise the fresh instance's empty database is written to the newly added channel as a snapshot and, by the retention count, pushes out the oldest snapshot there.
</Callout>

## Metadata export

**Settings → Backups & export → Data export → Export JSON** downloads `imgyoung-export.json`; each export writes an audit entry, and the file is saved only once fetched completely. Contents:

| Field | Contents |
|---|---|
| `users` | Users: ID, username, role, quota, default lifetime, disabled flag, usage and image count; no password hashes |
| `channels` | Channels: ID, name, driver, priority, health, latest failure `failure`, encrypted flag, direct-link flag, creation time, replica counts by state; no configuration parameters or credentials |
| `tokens` | Tokens: name, owner, plaintext prefix, scopes, revocation and issue times; no hashes |
| `images` | Every image reference: short ID, stored image, owner and token, original file name, object key alias, lifetime, access statistics, cleanup flags |
| `blobs` | Every stored image: SHA-256, perceptual hash, object key in the channels, MIME type, size, dimensions, reference count, deletion state |
| `blob_channels` | Which channel holds each replica, its state and attempt count, and the category `last_error_reason` and original error `last_error` of its latest failure |

The export is readable JSON: even if you stop using ImgYoung, it lets you match the objects in your channels back to the original images. It cannot be used to restore an instance; restores use snapshots. Runtime settings, hotlink rules, audit logs and alerts are not included.

## Reconciliation GC

Every 24 hours (first 24 hours after service start), each healthy channel is reconciled: the objects in the channel are compared with the records in the metadata database.

| Situation | Action |
|---|---|
| **Orphans**: objects ImgYoung wrote that have no replica record on this channel in the metadata database, in any state | Deleted once written more than 48 hours ago, so pay-per-use channels do not bill you for them |
| **Foreign objects**: objects ImgYoung did not write | Counted, never deleted |
| **Missing replicas**: replicas the metadata database records as completed but that are missing from the channel | Reset to pending and copied again from another channel |
| **Probe leftovers**: temporary `.imgyoung-probe-*` objects left by health checks | Deleted once written more than 48 hours ago, regardless of the binding time |

Apart from probe leftovers, an object counts as written by ImgYoung only if both hold: its key has the format `<short ID>_<first 8 hex digits of SHA-256>`, and it was written no earlier than the channel's **binding time**. The binding time is when the channel started using its current storage location, and it changes as follows:

| Situation | Binding time |
|---|---|
| A channel is created | Its creation time |
| The channel's backend or any configuration parameter is changed (re-entering the same password included) | The time of the change |
| Only the name, priority or direct-link setting changes; the provider refreshes a token | Unchanged |
| A snapshot is restored | The time of the start after the restore |

So files written to the same path by other programs, objects already in a bucket before it was added as a channel, and, after a restore, images uploaded after the snapshot was taken are only counted and never deleted. System objects under `_imgyoung/` in the channel (snapshots included) are not reconciled, and draining channels are not reconciled either.

Each channel's reconciliation logs a `渠道对账完成` line with the fields `objects` (object count), `bytes`, `foreign` (foreign objects), `orphans_deleted` (orphans deleted, probe leftovers included) and `phantoms_requeued` (missing replicas queued for replication).

<Callout type="error" title="Two instances must not share a channel path">
If two ImgYoung instances use the same storage path, objects written by the other instance are orphans to this one, and those written more than 48 hours earlier are deleted at reconciliation GC (every 24 hours, first 24 hours after the service starts). Give each instance its own bucket or path.
</Callout>

In addition, replica states are checked every 10 minutes (without listing channel objects): once a channel is healthy again, its failed replicas are replicated again, and unfinished replicas are queued again.

## Error codes

Backup and restore actions in the admin console return these status and error codes on failure.

| Action | Status | Error code | Meaning |
|---|---|---|---|
| Back up now | 500 | `backup_store_failed` | Some channels were not written; the message names them with the cause. Channels that were written keep the snapshot |
| Back up now | 500 | `backup_prune_failed` | The snapshot was written to every channel, but some channels could not prune old snapshots |
| Back up now | 500 | `backup_snapshot_failed` | The snapshot could not be taken |
| Restore | 422 | `snapshot_corrupt` | The snapshot is incomplete or is not an ImgYoung metadata database; the service keeps running, so pick another snapshot |
| Download, restore | 400 | `snapshot_name_invalid` | The snapshot name is not in the format ImgYoung generates |
| Download, restore | 404 | `snapshot_not_found` | No healthy channel has this snapshot |
| Any | 503 | `no_healthy_channel` | There is no healthy channel |
| List, download, restore | 500 | `internal` | List: listing a healthy channel failed. Download and restore: every channel holding the snapshot failed to read it, or a local disk or memory error occurred |
