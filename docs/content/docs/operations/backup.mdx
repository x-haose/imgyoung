## 需要备份什么

图片存放在各个渠道里，以内容哈希命名；哪个短链接对应哪张图、属于哪个用户，都记在元数据库里。因此：

- 元数据库丢失，渠道里的图片就无法再对应回原来的链接；
- 主密钥丢失，实例无法启动，渠道凭证和加密渠道里的数据也都无法解密。

| 内容 | 位置 | 备份方式 |
|---|---|---|
| 主密钥 | `<数据目录>/master.key`，或环境变量 `IMGYOUNG_MASTER_KEY` | 首次启动后复制一份离线保存，不要和快照放在一起。见[配置](../configuration.mdx#主密钥) |
| 元数据库 | `<数据目录>/imgyoung.db` | 自动快照会写到每个健康渠道；建议再定期下载一份存到别处 |
| 图片 | 各渠道 | 配置两个以上渠道，每张图就会有多份副本。内置 local 渠道的数据在 `<数据目录>/blobs/` |
| 加密渠道的 rclone 配置 | 「存储渠道」页的「导出 rclone 配置」 | 每个加密渠道导出一份，和主密钥一样离线保存。见[渠道存储加密](../channels/encryption.mdx) |
| 部署配置 | 环境变量、systemd drop-in、`compose.yaml`、反向代理配置 | 纳入你自己的配置管理 |

`<数据目录>/variants/` 是缩放与格式转换结果的缓存，丢失后会按需重新生成，不必备份。

服务运行时不要直接复制 `imgyoung.db`：最近的写入可能还在 `imgyoung.db-wal` 里，复制出来的文件不完整。需要一份完整的副本时，在后台下载快照，或先停止服务再复制。

## 元数据库自动快照

ImgYoung 定期为元数据库做快照，并把同一份快照写到每个健康的渠道上。

- **频率**：每隔「备份间隔」（`backup_interval_hours`，默认 1 小时）做一次，从服务启动时开始计时，修改间隔后重新计时。启动时，如果有健康渠道上没有最近一个间隔内的快照，会立即补做一次。
- **存放位置**：渠道路径下的 `_imgyoung/backup/`，文件名形如 `imgyoung-20261015-083000.123.db`（UTC 时间）。内置 local 渠道上即 `<数据目录>/blobs/_imgyoung/backup/`。加密渠道上的快照同样是加密的。
- **保留份数**：每个渠道只保留最新的「备份保留份数」（`backup_keep`，默认 24）份，更早的自动删除。
- **磁盘空间**：生成快照时先在数据目录写一个临时文件 `backup-snapshot.tmp`，需要约一个数据库大小的空闲空间。
- **失败**：生成快照失败、没有健康渠道、有渠道没写成，或有渠道没能按保留份数清理旧快照，这一次备份都算失败，会开启 `backup_failed` 告警，下一次成功后自动恢复。已经写成的渠道照常保留这份快照。见[监控与告警](./monitoring.mdx)。

删除渠道时选「删除并清理」，渠道上的快照会一起删除；选「仅移除」则原样保留。

<Callout type="warn" title="数据只存在这台主机上">
除了内置 local 渠道之外没有其他健康渠道时，图片和快照都只在这台主机的磁盘上，主机损坏就会全部丢失。总览页这时会提示「数据只存在这台主机上」。接入一个对象存储或网盘渠道后，快照会同时写到那里。
</Callout>

<Callout type="warn" title="加密渠道上的快照">
加密渠道上的快照，解密所需的密钥由主密钥和元数据库里记录的渠道信息共同派生。元数据库丢失后，要读出这些快照，只能用事先「导出 rclone 配置」保存下来的配置文件。因此，至少让一个未加密的渠道存放快照，或者为每个加密渠道导出并离线保存 rclone 配置。见[渠道存储加密](../channels/encryption.mdx)。
</Callout>

## 在后台管理快照

「设置 → 备份与导出 → 元数据库快照」列出所有健康渠道上的快照，最新的在前；「所在渠道」列显示每份快照存放在哪些渠道上。不健康或「清理中」的渠道上的快照不会列出。

- **立即备份**：马上做一次快照，写到每个健康渠道，并按保留份数清理旧快照。备份进行中再次点击，会在当前这次结束后再备份一次，多次点击也只多做一次，因此每次点击得到的快照都晚于点击时刻。
- **下载**：下载快照文件，它本身就是一个 SQLite 数据库。按优先级从存放它的渠道读取，一个渠道读不到就换下一个；文件完整取回后才保存到本地。
- **恢复**：用这份快照替换当前的元数据库，见下一节。

备份由服务端执行，关掉页面或反向代理超时都不会中断它。如果反向代理先超时（Nginx 返回 504，Cloudflare 返回 524），备份仍会在服务端完成：稍后刷新列表，出现新快照即已完成，没有出现再重新点击。

出错时的状态码与错误码见本页末尾的[错误码](#错误码)。

## 从快照恢复

恢复会把全部元数据退回到快照时刻。

<Steps>
<Step>

**发起恢复**：在快照所在行点「恢复」，确认「恢复并重启」。服务把快照下载为数据目录里的 `imgyoung.db.restore` 并检查是否完整，通过后自动停止。

</Step>
<Step>

**重新启动**：由进程管理器把服务重新拉起：Docker 用 `--restart unless-stopped`，Compose 用 `restart: unless-stopped`，systemd 用 `Restart=always`，`deploy/` 下的示例都已这样配置。在终端里直接运行的二进制会退出，下次手动启动时完成恢复。

</Step>
<Step>

**换入快照**：启动时，服务用快照替换当前的数据库，并升级到当前版本的表结构。原来的数据库改名为 `imgyoung.db.pre-restore-<UTC 时间>` 保留在数据目录里，确认恢复无误后可以手动删除。

</Step>
<Step>

**重新登录**：后台页面在服务恢复后自动刷新。账号和密码也回到了快照时刻，请用那时的密码登录。

</Step>
</Steps>

快照不完整，或者不是 ImgYoung 的元数据库时，恢复会被拒绝，服务照常运行，换一份快照再试即可。服务曾被强制终止（如 `kill -9`、断电）时，local 渠道上可能留下一份没写完的快照，它会出现在列表里，但无法用来恢复。

### 恢复之后

快照之后的变化都会丢失，渠道上的对象也会和元数据对不上：

- **快照之后上传的图片**：元数据里没有它们，链接返回 404。它们在渠道上的对象保留不动，不会被自动删除，可以用下一节的「找回图片记录」恢复链接。
- **快照之后删除的图片**：重新出现在元数据里，但渠道上的对象已经删除，访问会失败，并触发「副本补齐失败」告警。在后台删掉这些图片即可。
- **其他改动**：快照之后新建的渠道、用户、Token，修改过的运营配置和防盗链规则，都退回到快照时刻。

### 经反向代理恢复

恢复请求要一直等到快照下载并检查完毕。在此之前请求断开（关掉页面、反向代理超时），恢复就会取消，服务不会停止，数据也不会变化。因此，反向代理的读超时要长于从渠道下载快照所需的时间：

- **Nginx**：`proxy_read_timeout` 默认 60 秒，仓库里的 `deploy/nginx.conf` 示例设为 600 秒。超时返回 504 时，恢复已经取消，没有生效。
- **Cloudflare**：读超时固定为 125 秒，只有 Enterprise 套餐可以调整。超时返回 524 时，无法确定恢复是否完成：如果 Cloudflare 没有断开与源站的连接，恢复会在源站完成，服务随后自动重启。下载时间超过 125 秒的快照，请直接访问源站的后台恢复，或按下文[灾难恢复](#主机全损后的灾难恢复)的步骤手动放入。

见[反向代理与 HTTPS](./reverse-proxy.mdx)。

## 找回图片记录

元数据库退回到较早的状态后（从快照恢复，或最近的写入还没来得及复制出去），之后上传的图片仍在渠道里，库里却没有记录。「设置 → 备份与导出 → 找回图片记录」把这些对象重新登记为图片，原链接随之恢复。

找回按以下步骤进行：

1. 列举所有健康渠道，找出对象键形如 `<短 ID>_<SHA-256 前 8 位>`、库里没有记录的对象。
2. 按优先级从持有对象的渠道读取内容，核对格式、像素预算与哈希前缀。
3. 以对象键里的短 ID 登记图片。持有对象的渠道记为已就绪，其余渠道记为待补齐，由后台自动补齐。

执行结束后，页面列出渠道上的图片对象数、已有记录的数量、本次找回的数量，以及没有找回的对象和原因。

| 原因 | 含义 | 处理 |
|---|---|---|
| `read_failed` | 持有对象的渠道都读取失败 | 渠道恢复后重新执行 |
| `too_large` | 对象超过当前的单图大小上限 | 调大「单图上限」后重新执行 |
| `invalid_image` | 内容不是可解析的 jpeg、png、gif 或 webp，或超出像素预算 | 对象已损坏或不是图片，不会被登记 |
| `key_mismatch` | 内容的哈希与对象键里的哈希前缀不符 | 对象已损坏，不会被登记 |
| `id_taken` | 对象键里的短 ID 已属于另一条图片记录 | 不会被登记，按需手动清理该对象 |
| `register_failed` | 登记时落库失败 | 查看服务日志中的原因后重新执行 |

需要了解的限制：

- 找回的图片归当前登录的账号，永不过期。文件名、来源 Token 与有效期没有记在对象里，无法找回。
- 内容相同的图片经查重合并后共用同一份对象，对象键里只有第一张图的短 ID；其余几张图的链接无法找回。
- 恢复点之后删除、但对象还没有被物理删除（删除宽限期内）的图片，会随对象一起重新出现，在后台删除即可。
- 加密渠道由 ImgYoung 解密后读取，与未加密渠道的行为相同。

找回可以重复执行：已登记的对象下一次计为已有记录。同一时刻只进行一轮，页面关闭或请求断开时中止，已登记的保留。找回记入审计日志，动作为「找回图片记录」。

## 主机全损后的灾难恢复

开始之前，你需要：

- 原实例的主密钥：`master.key` 的备份，或 `IMGYOUNG_MASTER_KEY` 的值；
- 一份快照文件，可以来自：
  - 自己下载保存的快照；
  - 任一**未加密**渠道：用服务商的控制台或 rclone 下载渠道路径下 `_imgyoung/backup/` 里最新的 `imgyoung-*.db`；
  - 加密渠道：用事先导出的 rclone 配置读出，见[渠道存储加密](../channels/encryption.mdx)。

<Steps>
<Step>

**安装**：在新机器上安装相同或更新的版本，见[安装](../install/index.mdx)。安装后已经启动过也没关系，但它首次启动时生成的 `master.key` 必须在下一步换成原来那把。

</Step>
<Step>

**停止服务，放入主密钥与快照**：把原来的主密钥放到数据目录，命名为 `master.key`；把快照文件放到数据目录，命名为 `imgyoung.db.restore`。

不要直接用快照覆盖 `imgyoung.db`。以 `imgyoung.db.restore` 放入时，ImgYoung 会按恢复处理，保留快照之后写进渠道的对象；直接覆盖的话，这些对象会被当作无主对象：对账 GC 在服务启动 24 小时后第一次运行，此后每 24 小时一次，每次都删除写入已满 48 小时的无主对象。

手动放入的快照不经过后台恢复时的完整性检查，可以先自行检查：`sqlite3 imgyoung-20261015-083000.123.db 'PRAGMA quick_check;'` 应输出 `ok`，`sqlite3 imgyoung-20261015-083000.123.db '.tables'` 的结果里应有 `schema_revisions`。

<Tabs items={['二进制', 'Docker', 'Compose', 'systemd']}>
<Tab value="二进制">

```bash title="终端"
mkdir -p data
cp imgyoung-master.key data/master.key && chmod 600 data/master.key
cp imgyoung-20261015-083000.123.db data/imgyoung.db.restore
```

</Tab>
<Tab value="Docker">

镜像以 uid 65532 运行且没有 shell，借一个临时容器写入数据卷并修正属主：

```bash title="终端"
# 容器已在运行时先 docker stop imgyoung;还没有容器时按原来的参数先建出来(不启动)
docker create --name imgyoung --restart unless-stopped -p 8721:8721 \
  -v imgyoung-data:/data ghcr.io/x-haose/imgyoung:latest
docker run --rm --volumes-from imgyoung -v "$PWD":/in:ro alpine:3.24 sh -c '
  cp /in/imgyoung-master.key /data/master.key &&
  cp /in/imgyoung-20261015-083000.123.db /data/imgyoung.db.restore &&
  chmod 600 /data/master.key &&
  chown 65532:65532 /data /data/master.key /data/imgyoung.db.restore'
docker start imgyoung
```

</Tab>
<Tab value="Compose">

```bash title="终端"
docker compose stop        # 还没有启动过时改用 docker compose create
docker run --rm --volumes-from "$(docker compose ps -a -q imgyoung)" -v "$PWD":/in:ro alpine:3.24 sh -c '
  cp /in/imgyoung-master.key /data/master.key &&
  cp /in/imgyoung-20261015-083000.123.db /data/imgyoung.db.restore &&
  chmod 600 /data/master.key &&
  chown 65532:65532 /data /data/master.key /data/imgyoung.db.restore'
docker compose up -d
```

</Tab>
<Tab value="systemd">

`install.sh --service` 安装后服务已经启动过一次，`/var/lib/imgyoung` 已由 systemd 建好并归属运行用户。放入文件后把属主改成与现有数据库一致：

```bash title="终端"
sudo systemctl stop imgyoung
sudo cp imgyoung-master.key /var/lib/imgyoung/master.key
sudo cp imgyoung-20261015-083000.123.db /var/lib/imgyoung/imgyoung.db.restore
sudo chown --reference=/var/lib/imgyoung/imgyoung.db \
  /var/lib/imgyoung/master.key /var/lib/imgyoung/imgyoung.db.restore
sudo chmod 600 /var/lib/imgyoung/master.key
sudo systemctl start imgyoung
```

</Tab>
</Tabs>

用环境变量 `IMGYOUNG_MASTER_KEY` 提供主密钥的，改设环境变量即可，不必放文件。

</Step>
<Step>

**启动并检查**：二进制方式此时启动 `imgyoung`。日志里出现 `已用暂存快照换入元数据库,原库留存`，说明快照已经换入。用快照时刻的账号密码登录，在「存储渠道」页确认各渠道恢复健康。

如果启动时提示主密钥与数据库不符，或者找不到主密钥，说明放入的不是原实例的主密钥，或者没有放。此时快照已经换入，换上正确的主密钥再启动即可，不必重新放快照。

</Step>
</Steps>

恢复后，原来只存在 local 渠道上的图片已随旧主机丢失；在其他渠道上有副本的图片照常访问，local 渠道上缺少的副本会在每日对账时从其他渠道补回。

### 不手动取快照文件

快照在未加密渠道上时，也可以让新实例直接从渠道读取快照：

1. 用原来的主密钥启动一个全新实例：首次启动前就放好 `master.key`，或设置 `IMGYOUNG_MASTER_KEY`。否则恢复后重启时，主密钥与快照不符，服务会拒绝启动。如果已经用自动生成的主密钥启动过：停止服务，换上原来的 `master.key`，删除数据目录里的 `imgyoung.db`（连同 `imgyoung.db-wal` 和 `imgyoung.db-shm`），再启动。
2. 在后台按原来的参数接入存放快照的渠道。渠道里原有的对象不会被删除。
3. 在「元数据库快照」里选一份快照恢复。

<Callout type="warn" title="接入渠道后尽快恢复">
接入渠道之后、恢复之前，不要点「立即备份」，也不要重启实例。否则新实例的空数据库会作为快照写进刚接入的渠道，并按保留份数挤掉那里最早的一份快照。
</Callout>

## 元数据导出

「设置 → 备份与导出 → 数据导出 → 导出 JSON」下载 `imgyoung-export.json`，每次导出记一条审计日志。文件完整取回后才保存到本地。内容如下：

| 字段 | 内容 |
|---|---|
| `users` | 用户：ID、登录名、角色、配额、默认有效期、是否禁用、用量与图片数；不含密码哈希 |
| `channels` | 渠道：ID、名称、驱动、优先级、健康状态、最近一次失败结论 `failure`、是否加密、是否允许直链、创建时刻、各状态的副本数；不含任何配置参数与凭证 |
| `tokens` | Token：名称、归属用户、明文前缀、授权范围、吊销与签发时刻；不含哈希 |
| `images` | 每条图片引用：短 ID、物理图、归属用户与 Token、原始文件名、对象键别名、有效期、访问统计、清理标记 |
| `blobs` | 每个物理图：SHA-256、感知哈希、渠道内对象键、MIME、大小、宽高、引用计数、删除状态 |
| `blob_channels` | 每份副本所在的渠道、状态、尝试次数，以及最近一次失败的归类 `last_error_reason` 与原始错误 `last_error` |

导出文件是可读的 JSON：即使不再使用 ImgYoung，也能凭它把渠道里的对象对应回原来的图片。它不能用来恢复实例，恢复请用快照。导出不包含运营配置、防盗链规则、审计日志和告警。

## 对账 GC

每个健康渠道每 24 小时对账一次（服务启动 24 小时后第一次），比对渠道上的对象与元数据库的记录：

| 情况 | 处理 |
|---|---|
| **无主对象**：ImgYoung 写出、但元数据库里没有它在本渠道上的副本记录（不论状态）的对象 | 写入超过 48 小时后删除，免得按量计费的渠道为它付费 |
| **外来对象**：不是 ImgYoung 写出的对象 | 只计数，不删除 |
| **缺失副本**：元数据库记为已就绪、渠道上却没有的副本 | 改回待补齐，从其他渠道重新复制 |
| **探测残留**：健康探测留下的临时对象 `.imgyoung-probe-*` | 写入超过 48 小时后删除，不受绑定时刻限制 |

除探测残留外，一个对象同时满足以下两点，才算 ImgYoung 写出的：键名符合 `<短 ID>_<SHA-256 前 8 位>` 的格式，并且写入时间不早于渠道的**绑定时刻**。绑定时刻是渠道开始使用当前存储位置的时刻，在以下情况下更新：

| 情况 | 绑定时刻 |
|---|---|
| 新建渠道 | 创建时刻 |
| 修改渠道的后端或任一配置参数（包括重新输入相同的密码）| 修改时刻 |
| 只改名称、优先级或直链开关；服务商刷新令牌 | 不变 |
| 从快照恢复 | 恢复后启动的时刻 |

因此，别的程序写进同一路径的文件、接入渠道之前桶里已有的对象，以及从快照恢复时，快照时刻之后上传的图片，都只计数，不会删除。渠道上 `_imgyoung/` 下的系统对象（包括快照）不参与对账，「清理中」的渠道也不对账。

每个渠道对账完成后记一条 `渠道对账完成` 日志，字段为 `objects`（对象数）、`bytes`（字节数）、`foreign`（外来对象数）、`orphans_deleted`（删除的无主对象数，含探测残留）、`phantoms_requeued`（重新补齐的缺失副本数）。

<Callout type="error" title="两个实例不能共用同一渠道路径">
两个 ImgYoung 实例接入同一个存储路径时，对方写出的对象在本实例看来就是无主对象，写入已满 48 小时的会在对账 GC 时删除（每 24 小时一次，服务启动 24 小时后第一次）。每个实例要用各自的桶或路径。
</Callout>

此外，每 10 分钟检查一次副本状态（不列举渠道上的对象）：渠道恢复健康后，之前失败的副本重新补齐；未完成的副本重新排队。

## 错误码

后台的备份、恢复与找回操作出错时返回以下状态码与错误码。

| 操作 | 状态码 | 错误码 | 含义 |
|---|---|---|---|
| 立即备份 | 500 | `backup_store_failed` | 有渠道没写成，提示里列出失败的渠道与原因；写成的渠道保留这份快照 |
| 立即备份 | 500 | `backup_prune_failed` | 快照已写到所有渠道，但有渠道没能清理旧快照 |
| 立即备份 | 500 | `backup_snapshot_failed` | 生成快照失败 |
| 恢复 | 422 | `snapshot_corrupt` | 快照不完整，或不是 ImgYoung 的元数据库；服务照常运行，换一份快照再试 |
| 下载、恢复 | 400 | `snapshot_name_invalid` | 快照名不是 ImgYoung 生成的格式 |
| 下载、恢复 | 404 | `snapshot_not_found` | 健康渠道上都没有这份快照 |
| 找回图片记录 | 409 | `recovery_busy` | 已有一轮找回在进行，等它结束后再试 |
| 所有操作 | 503 | `no_healthy_channel` | 没有健康的渠道 |
| 列表、下载、恢复 | 500 | `internal` | 列表：有健康渠道列举失败；下载与恢复：存放快照的渠道都读取失败，或本机磁盘、内存出错 |
