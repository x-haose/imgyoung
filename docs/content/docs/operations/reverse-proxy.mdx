## 为什么需要反向代理

ImgYoung 只提供明文 HTTP，不处理 TLS。对公网提供服务时，请在它前面放一个反向代理：

- 由反向代理申请证书、提供 HTTPS；
- 会话 cookie 是否带 `Secure`，以及未配置 `base_url` 时返回的链接用哪个协议，都依据反向代理传来的 `X-Forwarded-Proto`；
- 在入口处拦截 `/metrics`，指标只供内网抓取；
- ImgYoung 本身只需监听回环地址，不直接暴露在公网上，见[只监听回环地址](#只监听回环地址)。

## Caddy

Caddy 自动申请并续期证书，默认就会设置 `X-Forwarded-For`、`X-Forwarded-Proto`、`X-Forwarded-Host`，并原样转发 `Host`。

<include cwd lang="text" meta='title="deploy/Caddyfile"'>../deploy/Caddyfile</include>

### Caddy 前面还有 CDN 时

Caddy 默认不信任任何上游代理：它会丢掉客户端带来的 `X-Forwarded-For`，只填入直接连接它的地址。Caddy 前面有 CDN 时，这个地址是 CDN 节点，ImgYoung 就拿不到访客的真实地址。

在 Caddyfile 的全局选项里把 CDN 的回源网段设为可信，Caddy 才会保留 CDN 传来的转发头，并在末尾追加自己看到的地址：

```text title="Caddyfile 全局选项"
{
	servers {
		trusted_proxies static <CDN 的回源网段>
	}
}
```

同时，`IMGYOUNG_TRUSTED_PROXIES` 也要加上 CDN 的回源网段，见下文[按部署方式取值](#按部署方式取值)。

Nginx 示例使用的 `$proxy_add_x_forwarded_for` 本身就是追加写法，没有这个问题。

## Nginx

<include cwd lang="nginx" meta='title="deploy/nginx.conf"'>../deploy/nginx.conf</include>

示例里的每一行 `proxy_set_header` 都不能省：

- `Host $host`：S3 兼容接口的签名校验包含 `Host` 头，反向代理改写它，S3 客户端就会签名不匹配。
- `X-Forwarded-For`：缺了它，所有请求都会被当作来自 Nginx 本机，见下一节。
- `X-Forwarded-Proto` 与 `X-Forwarded-Host`：ImgYoung 只取它们的第一个值，所以要用 `proxy_set_header` 覆盖，不能把自己的值追加在客户端传来的值后面。

## 信任的反向代理：IMGYOUNG_TRUSTED_PROXIES

ImgYoung 从每个请求里确定三项信息：

| 信息 | 用途 |
|---|---|
| 客户端地址 | 登录限速；`/metrics` 的访问控制 |
| 是否经 HTTPS 访问 | 会话 cookie 是否带 `Secure` |
| 对外域名 | 未配置 `base_url` 时，用来拼接返回的链接 |

只有直接连接 ImgYoung 的一方（TCP 连接的对端）在 `IMGYOUNG_TRUSTED_PROXIES` 网段内时，ImgYoung 才采信 `X-Forwarded-*` 头。

- 未设置时，默认值为 `127.0.0.0/8,::1/128`，只信任同一台主机上的反向代理。
- 设为空串（或只含空白）时，不信任任何代理，转发头一律忽略。后台「引导配置」卡片上会显示「空：不采信任何转发头」。

### 按部署方式取值

| 部署方式 | ImgYoung 看到的连接对端 | `IMGYOUNG_TRUSTED_PROXIES` |
|---|---|---|
| 反向代理与 ImgYoung（二进制或 systemd）在同一台主机 | `127.0.0.1` 或 `::1` | 默认值即可 |
| ImgYoung 在 Docker 里，反向代理在宿主机上 | Docker 网桥的网关地址，不是回环地址 | 网关所在的网段，如 `172.16.0.0/12`；用 `docker network inspect` 查看实际的网关 |
| 反向代理与 ImgYoung 是同一个 Compose 项目里的两个容器 | 反向代理容器在项目网络里的地址 | 项目网络的网段 |
| 反向代理在另一台主机上 | 反向代理主机的内网地址 | 该地址或它所在的网段 |
| 反向代理前面还有 CDN | 反向代理的地址；`X-Forwarded-For` 最右边一跳是 CDN 节点 | 反向代理的网段加上 CDN 的回源网段，客户端地址才会是真实访客。反向代理是 Caddy 时，Caddy 也要把 CDN 的回源网段设为 `trusted_proxies`，见上文 |

<Callout type="warn" title="信任配置错误的后果">
连接对端不在信任网段内时，所有经反向代理的请求都会被当作来自反向代理本身：全站访客共用一个登录限速额度。如果反向代理的地址恰好在 `IMGYOUNG_METRICS_ALLOW` 内（Docker 网段默认就在），而它又转发了 `/metrics`，任何人都能读到指标。反向代理没有设置 `X-Forwarded-For` 时，后果相同。
</Callout>

### 转发头的解析规则

对端受信任时：

1. 按顺序收集所有 `X-Forwarded-For` 头里以逗号分隔的地址，跳过无法解析的项。
2. **从右向左**逐个检查，跳过信任网段内的地址，遇到的第一个不在信任网段内的地址就是客户端地址。
3. 所有地址都在信任网段内（内网客户端）时，取最左边的一个；没有这个头或没有可用的地址时，取连接对端。
4. `X-Forwarded-Proto` 取第一个值，等于 `https`（不区分大小写）即视为经 HTTPS 访问。
5. `X-Forwarded-Host` 取第一个值，作为对外域名。

对端不受信任时，`X-Forwarded-*` 一律忽略：客户端地址就是连接对端；ImgYoung 不处理 TLS，所以总是视为没有经 HTTPS 访问。

**伪造的 `X-Forwarded-For` 不起作用**。每一级代理都把自己看到的对端追加到 `X-Forwarded-For` 末尾，客户端能控制的只有最左边的部分。例如，客户端 `203.0.113.7` 自带 `X-Forwarded-For: 1.2.3.4`，经过同一台主机上的 Nginx 后变成 `1.2.3.4, 203.0.113.7`。从右向左第一个不受信任的地址是 `203.0.113.7`，伪造的 `1.2.3.4` 被忽略。直接连接 ImgYoung 的请求，对端不在信任网段内，带什么转发头都不会被采信。

## 只监听回环地址

有了反向代理，就不要让 ImgYoung 的端口直接对外：

<Tabs items={['二进制 / systemd', 'Docker', 'Compose']}>
<Tab value="二进制 / systemd">

设置 `IMGYOUNG_LISTEN=127.0.0.1:8721`。systemd 部署用 drop-in 覆盖，见[配置](../configuration.mdx)：

```bash title="终端"
sudo systemctl edit imgyoung
```

```ini title="编辑器中填入"
[Service]
Environment=IMGYOUNG_LISTEN=127.0.0.1:8721
```

```bash title="终端"
sudo systemctl restart imgyoung
```

</Tab>
<Tab value="Docker">

容器内保持默认的监听地址，只把端口发布到宿主机的回环地址：

```bash title="终端"
docker run -d --name imgyoung --restart unless-stopped \
  -p 127.0.0.1:8721:8721 -v imgyoung-data:/data \
  -e IMGYOUNG_TRUSTED_PROXIES=172.16.0.0/12 \
  haose/imgyoung:latest
```

写成 `-p 8721:8721` 会发布到所有网卡，而且 Docker 自己管理的端口转发规则不受 ufw 等主机防火墙约束。

</Tab>
<Tab value="Compose">

```yaml title="compose.yaml"
services:
  imgyoung:
    ports:
      - "127.0.0.1:8721:8721"
    environment:
      IMGYOUNG_TRUSTED_PROXIES: 172.16.0.0/12
```

反向代理也在同一个 Compose 项目里时，可以去掉 `ports`，让反向代理直接访问 `imgyoung:8721`。

</Tab>
</Tabs>

## 什么时候必须设置 base_url

`base_url` 即后台「设置 → 运行配置 → 访问与链接 → 对外站点地址」。它为空时，ImgYoung 根据每个请求推导对外地址：协议按是否经 HTTPS 访问决定；对端受信任时域名取 `X-Forwarded-Host`，否则取 `Host`。

以下情况必须设置：

- **对外域名与 ImgYoung 收到的域名不同**：例如 CDN 用另一个域名回源、反向代理改写了 `Host` 又没有传 `X-Forwarded-Host`、反向代理不在信任网段内。这时上传接口返回的 `url`，以及「S3 客户端配置」弹窗里的端点与链接前缀都会出错。
- **启用 CDN 缓存清除**：清除在后台异步进行，没有请求可供推导，只使用 `base_url`。见 [CDN](./cdn.mdx)。
- **使用网盘渠道的「一键授权」**：授权回调地址必须与开放平台上登记的地址完全一致，只用 `base_url` 拼出。见[网盘渠道](../channels/cloud-drives.mdx)。

后台复制的分享链接不受上述情况影响：配置了 `base_url` 时用它，否则用浏览器地址栏里的站点地址。

## 上传体积上限要与反向代理一致

后台的「单图上限」（`max_upload_mb`，默认 50 MB）只限制文件本身，大小恰好等于上限的文件可以上传。整个请求体最多可以比单图上限多 64 KiB，留给 multipart 边界与 `exif_policy`、`ttl` 等字段。反向代理的请求体上限不能小于这个值：

- Nginx 默认只允许 1 MB，示例设为 `client_max_body_size 60m;`。
- Caddy 示例没有限制请求体。如果你用 `request_body` 设置了 `max_size`，不要小于单图上限加 64 KiB。

在后台调大单图上限后，要同步调大反向代理的限制。否则大图会在反向代理处被直接拒绝（413），请求到不了 ImgYoung。

## 从快照恢复要留够读超时

在后台「恢复」快照时，请求要等到快照从渠道下载并检查完毕才返回。请求在此之前断开，恢复就会取消，服务不会停止。因此，反向代理的读超时要长于下载快照所需的时间：

- **Nginx**：`proxy_read_timeout` 默认 60 秒，上面的示例在 `location /` 里设为 `600s`，可按快照大小与渠道速度调整。超时返回 504 时，恢复已经取消，没有生效。
- **Cloudflare**：等待源站响应最长 125 秒（超时返回 524），只有 Enterprise 套餐可以调大。超时时无法确定恢复是否完成：如果 Cloudflare 没有断开与源站的连接，恢复会在源站完成，服务随后自动重启。下载快照需要超过 125 秒时，无法经 Cloudflare 在后台恢复：请直接访问源站上的后台恢复，或按[灾难恢复](./backup.mdx#主机全损后的灾难恢复)的步骤手动放入快照。

见[备份与恢复](./backup.mdx#经反向代理恢复)。
