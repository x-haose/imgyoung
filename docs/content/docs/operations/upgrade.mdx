## 升级前

1. 读一遍目标版本的 [Release 说明](https://github.com/x-haose/imgyoung/releases)。
2. 留一份回滚用的元数据库副本：在后台「设置 → 备份与导出 → 元数据库快照」点「立即备份」，再「下载」这份快照，保存在服务器以外。也可以停服后复制 `<数据目录>/imgyoung.db`（停服后才是一致的）。
3. 确认 master.key 已有备份，见[配置](../configuration.mdx#主密钥)。
4. 看一眼后台「设置 → 运行配置 → 访问与链接 → 对外站点地址」：除了「`http://` 或 `https://` 加由字母、数字、点、连字符组成的主机名，再加可选的数字端口」这种形式，其余的值升级时都会被清空（见下文[数据库迁移](#数据库迁移)），例如不带协议的 `img.example.com`、带路径的 `https://example.com/img`、中文域名、IPv6 字面量。属于这些情况的先记下来，升级后重新填写；中文域名与 IPv6 字面量可以原样重填。

当前版本可用 `imgyoung -version` 查看，或看后台「设置 → 运行配置 → 引导配置」里的「服务端版本」。

## 升级命令

<Tabs items={['一行安装脚本', 'Docker', 'Compose', '二进制', '源码']}>
<Tab value="一行安装脚本">

重新执行安装脚本即升级到最新正式版；指定版本加 `--version X.Y.Z`。

```bash title="终端"
# 用 systemd 服务运行的(当初加了 --service):替换二进制、重写服务单元并重启服务
curl -fsSL https://raw.githubusercontent.com/x-haose/imgyoung/main/install.sh | sudo sh -s -- --service

# 自己管理进程的:只替换二进制,之后自行重启 imgyoung
curl -fsSL https://raw.githubusercontent.com/x-haose/imgyoung/main/install.sh | sh
```

`--service` 会用发布包里的 `deploy/imgyoung.service` 覆盖 `/etc/systemd/system/imgyoung.service`；自定义的环境变量请放在 `systemctl edit` 创建的 drop-in 里，不会被覆盖。

</Tab>
<Tab value="Docker">

拉取新镜像，删掉旧容器，用**同一个数据卷**和原来的参数重新创建。删除容器不会删除命名数据卷。原来用 `-e IMGYOUNG_MASTER_KEY=…` 传主密钥的，重建时不要漏掉它：数据库里已有依赖主密钥的数据（主密钥指纹、渠道配置等密文，或上传 Token、加密渠道这类由主密钥派生的数据）时，找不到主密钥进程就拒绝启动，不会生成新密钥。

```bash title="终端"
docker pull ghcr.io/x-haose/imgyoung:latest
docker stop imgyoung && docker rm imgyoung
docker run -d --name imgyoung --restart unless-stopped \
  -p 8721:8721 -v imgyoung-data:/data \
  ghcr.io/x-haose/imgyoung:latest
```

镜像标签：`latest` 跟随最新正式版；`1.0` 这样的「主.次」标签跟随该系列的最新补丁版；`1.0.3` 这样的完整版本号固定不变。预发布版只有完整版本号标签。

</Tab>
<Tab value="Compose">

```bash title="终端"
docker compose pull
docker compose up -d
```

`compose.yaml` 里钉的是「主.次」或完整版本号时，跨系列升级要先改 `image:` 的标签。

</Tab>
<Tab value="二进制">

从[发布页](https://github.com/x-haose/imgyoung/releases)下载对应平台的新压缩包，用同目录的 `checksums.txt` 校验后解压，替换旧的 `imgyoung` 二进制，然后重启进程。数据目录不动。

```bash title="终端"
sha256sum -c checksums.txt --ignore-missing
tar -xzf imgyoung_<版本号>_linux_amd64.tar.gz
```

</Tab>
<Tab value="源码">

```bash title="终端"
git fetch --tags
git checkout vX.Y.Z
task build
```

用新生成的 `./imgyoung` 替换正在运行的二进制并重启。

</Tab>
</Tabs>

停止旧进程时，ImgYoung 先停止接收新请求，在途请求最多等 6 秒（超时强制断开），再停后台循环与在途的补齐任务，最多等 2 秒，然后关库退出。被打断的补齐任务下次启动由对账重新入队。Docker 默认的 10 秒停止时限，以及 `deploy/` 示例里的 `stop_grace_period: 15s`（Compose）与 `TimeoutStopSec=15s`（systemd）都够用。

## 数据库迁移

数据库迁移打包在二进制里，每次启动、打开数据库之后自动执行：

- 先校验迁移文件与校验和清单一致，再按版本顺序应用所有尚未应用的迁移；跨多个版本升级时，中间版本的迁移会依次补齐。已应用的版本记录在数据库的 `schema_revisions` 表里。
- 补齐子系统的任务队列表也在启动时迁移到当前版本。
- 新增的运营配置项由迁移按出厂默认值补齐，已有配置保持不变。
- 迁移 `b20_failure_reasons` 给渠道与副本的失败原因加上结构化的归类：已有的失败原因一律记为 `unclassified`，原句留作根因原文，下一次探测或补齐即覆盖。
- 迁移 `b22_settings_constraints` 把存量运营配置改写到收紧后的取值范围：WebP 质量档为 0 的改为 75（编码库本就把 0 当作 75）；对外站点地址 `base_url` 只保留 `http` / `https` 加主机名（字母或数字开头，只含字母、数字、点、连字符）与可选数字端口的站点根地址，其余一律清空，例如不带协议，带路径、查询参数、片段或账号信息，主机名含空格或 `%`，端口不是数字，IPv6 字面量与中文域名。保留下来的值都能通过启动时的配置校验。清空后按请求推导对外地址，依赖它的 CDN 缓存清除与网盘一键授权也随之不可用，升级后到后台按 `https://img.example.com` 这样的格式重新填写。
- 库里记有本二进制不认识的迁移版本（被更新的版本迁移过）时拒绝启动，见下文[回滚](#回滚)。
- 迁移失败时进程以错误退出，日志给出失败的迁移文件名。此时用升级前的快照回滚（见下文）。

不需要也没有单独的迁移命令。

## 回滚

不支持降级：迁移只有升级方向，部分迁移会删除列或重建表。旧版本的二进制遇到被新版本迁移过的库会拒绝启动，错误信息写明库里的最新迁移版本与本二进制认识到的最新版本。

所以回滚只有一种做法：**旧版本的二进制 + 升级前的快照**。没有升级前的快照，就只能继续用新版本。

<Steps>
<Step>

停止服务。

</Step>
<Step>

换回旧版本的二进制或镜像标签。

</Step>
<Step>

把升级前的快照（或停服时复制的数据库）放为 `<数据目录>/imgyoung.db.restore`，不要直接覆盖 `imgyoung.db`：启动时它被换入，新版本迁移过的库改名为 `imgyoung.db.pre-restore-<UTC 时刻>` 留存，并且渠道的绑定时刻随之重置。Docker 部署的文件属主须为 `65532:65532`，写入方法参考[备份与恢复](./backup.mdx)里借临时容器的做法。

</Step>
<Step>

启动服务。

</Step>
</Steps>

升级之后产生的元数据随之丢失，影响与从快照恢复相同：这期间上传的图片在元数据里没有记录，它们在渠道上的对象只计数、不回收，但无法再通过 ImgYoung 访问，详见[备份与恢复](./backup.mdx)。
