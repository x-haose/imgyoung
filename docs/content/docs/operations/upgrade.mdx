## 升级前

1. 阅读目标版本的 [Release 说明](https://github.com/x-haose/imgyoung/releases)。
2. 留一份回滚用的元数据库副本：在后台「设置 → 备份与导出 → 元数据库快照」点「立即备份」，再「下载」这份快照，保存到服务器以外的地方。也可以停止服务后复制 `<数据目录>/imgyoung.db`；服务运行时复制的文件不完整。
3. 确认主密钥 `master.key` 已经备份，见[配置](../configuration.mdx#主密钥)。

查看当前版本：运行 `imgyoung -version`，或在后台「设置 → 运行配置 → 引导配置」里查看「服务端版本」。

## 升级命令

<Tabs items={['一行安装脚本', 'Docker', 'Compose', '二进制', '源码']}>
<Tab value="一行安装脚本">

重新运行安装脚本即可升级到最新正式版；要指定版本，加 `--version X.Y.Z`。

```bash title="终端"
# 用 systemd 服务运行的(当初加了 --service):替换二进制、重写服务单元并重启服务
curl -fsSL https://raw.githubusercontent.com/x-haose/imgyoung/main/install.sh | sudo sh -s -- --service

# 自己管理进程的:只替换二进制,之后自行重启 imgyoung
curl -fsSL https://raw.githubusercontent.com/x-haose/imgyoung/main/install.sh | sh
```

安装时用了 `--dir` 或 `sudo` 的，升级时要带同样的参数。否则新版本会装到默认目录（以 root 运行时为 `/usr/local/bin`，其他用户为 `~/.local/bin`），旧的二进制原样留在原处。

`--service` 会用发布包里的 `deploy/imgyoung.service` 覆盖 `/etc/systemd/system/imgyoung.service`。自定义的环境变量请放在 `systemctl edit` 创建的 drop-in 里，它不会被覆盖。

</Tab>
<Tab value="Docker">

拉取新镜像，删除旧容器，再用**同一个数据卷**和原来的参数重新创建。删除容器不会删除命名数据卷。

原来用 `-e IMGYOUNG_MASTER_KEY=…` 传入主密钥的，重建容器时不要漏掉。实例启动过一次之后，找不到主密钥就会拒绝启动，不会生成新的密钥。

```bash title="终端"
docker pull ghcr.io/x-haose/imgyoung:latest
docker stop imgyoung && docker rm imgyoung
docker run -d --name imgyoung --restart unless-stopped \
  -p 8721:8721 -v imgyoung-data:/data \
  ghcr.io/x-haose/imgyoung:latest
```

镜像标签：

- `latest`：最新正式版；
- `1.0` 这样的「主.次」标签：该系列的最新补丁版；
- `1.0.3` 这样的完整版本号：固定不变。

预发布版只有完整版本号标签。

</Tab>
<Tab value="Compose">

```bash title="终端"
docker compose pull
docker compose up -d
```

`compose.yaml` 里的 `image:` 固定为「主.次」标签时，升级到另一个系列要先修改这个标签；固定为完整版本号时，每次升级都要先修改。

</Tab>
<Tab value="二进制">

从[发布页](https://github.com/x-haose/imgyoung/releases)下载对应平台的新压缩包，用同一版本的 `checksums.txt` 校验后解压，替换旧的 `imgyoung` 二进制，然后重启进程。数据目录不用动。

```bash title="终端"
sha256sum -c checksums.txt --ignore-missing
tar -xzf imgyoung_<版本号>_linux_amd64.tar.gz
```

</Tab>
<Tab value="源码">

```bash title="终端"
git fetch --tags
git checkout vX.Y.Z
task build
```

用新生成的 `./imgyoung` 替换正在运行的二进制，然后重启。

</Tab>
</Tabs>

停止服务时，ImgYoung 先停止接收新请求，等正在处理的请求结束，再中止在途的补齐任务，总共最多约 8 秒，超时的请求会被强制断开，然后退出。Docker 默认的 10 秒停止时限，以及 `deploy/` 示例里的 `stop_grace_period: 15s`（Compose）和 `TimeoutStopSec=15s`（systemd）都足够。被打断的补齐任务会在下次启动后重新排队。

## 数据库迁移

数据库迁移打包在二进制里，每次启动、打开数据库之后自动执行，没有单独的迁移命令。

- 按版本顺序执行所有尚未执行的迁移。跨多个版本升级时，中间版本的迁移会依次执行。已执行的迁移记录在数据库的 `schema_revisions` 表里。
- 任务队列使用的表也在启动时一并迁移。
- 新版本新增的运营配置项取默认值，已有的配置保持不变。
- 数据库已被更新的版本迁移过时，拒绝启动，见下文[回滚](#回滚)。
- 迁移失败时，进程报错退出，日志里给出失败的迁移文件名。这时用升级前的快照回滚，见下文。

## 回滚

不支持降级：迁移只能向前执行，部分迁移会删除列或重建表。旧版本的二进制遇到新版本迁移过的数据库会拒绝启动，错误信息里写明数据库的最新迁移版本和这个二进制所知的最新版本。

因此，回滚只有一种办法：**旧版本的二进制，加上升级前的快照**。没有升级前的快照，就只能继续使用新版本。

<Steps>
<Step>

停止服务。

</Step>
<Step>

换回旧版本的二进制或镜像标签。

</Step>
<Step>

把升级前的快照（或停止服务时复制的数据库）放到数据目录，命名为 `imgyoung.db.restore`。不要直接覆盖 `imgyoung.db`：直接覆盖的话，升级之后写进渠道的对象会被当作无主对象：对账 GC 在服务启动 24 小时后第一次运行，此后每 24 小时一次，每次都删除写入已满 48 小时的无主对象。

Docker 部署时，文件属主必须是 `65532:65532`，写入方法参考[灾难恢复](./backup.mdx#主机全损后的灾难恢复)里借助临时容器的做法。

</Step>
<Step>

启动服务。启动时快照会被换入，新版本迁移过的数据库改名为 `imgyoung.db.pre-restore-<UTC 时间>`，保留在数据目录里。

</Step>
</Steps>

回滚会丢失升级之后的元数据，影响与从快照恢复相同：这期间上传的图片在元数据里没有记录，无法再通过 ImgYoung 访问；它们在渠道上的对象保留不动，不会被自动删除。见[恢复之后](./backup.mdx#恢复之后)。
