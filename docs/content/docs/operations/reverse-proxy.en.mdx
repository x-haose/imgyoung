## Why a reverse proxy

ImgYoung serves plain HTTP and does not handle TLS. When serving the public internet, put a reverse proxy in front of it:

- the proxy obtains certificates and serves HTTPS;
- whether the session cookie gets `Secure`, and which scheme returned links use when `base_url` is not set, both depend on the `X-Forwarded-Proto` the proxy sends;
- the proxy blocks `/metrics` at the entry point, so metrics are only scraped from the internal network;
- ImgYoung itself only needs to listen on loopback and is not exposed to the internet directly; see [Listen on loopback only](#listen-on-loopback-only).

## Caddy

Caddy obtains and renews certificates automatically, sets `X-Forwarded-For`, `X-Forwarded-Proto` and `X-Forwarded-Host` by default, and forwards `Host` unchanged.

### With a CDN in front of Caddy

By default Caddy trusts no upstream proxy: it drops any `X-Forwarded-For` the client sent and fills in only the address directly connected to it. With a CDN in front of Caddy, that address is a CDN node, so ImgYoung never sees the visitor's real address.

Declare the CDN's origin-pull ranges as trusted in the Caddyfile's global options. Caddy then keeps the forwarding headers the CDN sends and appends the address it sees:

```text title="Caddyfile global options"
{
	servers {
		trusted_proxies static <CDN origin-pull ranges>
	}
}
```

Add the CDN's origin-pull ranges to `IMGYOUNG_TRUSTED_PROXIES` as well; see [Values by deployment](#values-by-deployment) below.

The Nginx example's `$proxy_add_x_forwarded_for` already appends, so it does not have this problem.

## Nginx

None of the `proxy_set_header` lines in the example are optional:

- `Host $host`: signature verification on the S3-compatible API covers the `Host` header, so a proxy that rewrites it causes signature mismatches for S3 clients.
- `X-Forwarded-For`: without it, every request looks like it came from Nginx itself; see the next section.
- `X-Forwarded-Proto` and `X-Forwarded-Host`: ImgYoung reads only their first value, so overwrite them with `proxy_set_header` instead of appending your value after whatever the client sent.

## Trusted proxies: IMGYOUNG_TRUSTED_PROXIES

ImgYoung determines three things from each request:

| What | Used for |
|---|---|
| Client address | Login rate limiting; access control for `/metrics` |
| Whether it arrived over HTTPS | Whether the session cookie gets `Secure` |
| Public host | Building returned links when `base_url` is not set |

ImgYoung honors `X-Forwarded-*` headers only when whatever connects to it directly (the TCP peer) is inside `IMGYOUNG_TRUSTED_PROXIES`.

- When the variable is unset, the default `127.0.0.0/8,::1/128` trusts only a proxy on the same host.
- Setting it to an empty string (or only whitespace) trusts no proxy at all, so forwarding headers are always ignored. The **Bootstrap configuration** card in the admin console then shows **Empty: forwarded headers are never trusted**.

### Values by deployment

| Deployment | Peer address ImgYoung sees | `IMGYOUNG_TRUSTED_PROXIES` |
|---|---|---|
| Proxy and ImgYoung (binary or systemd) on the same host | `127.0.0.1` or `::1` | The default |
| ImgYoung in Docker, proxy on the host | The Docker bridge gateway, not loopback | The gateway's network, e.g. `172.16.0.0/12`; check the actual gateway with `docker network inspect` |
| Proxy and ImgYoung as two containers in one Compose project | The proxy container's address on the project network | The project network's subnet |
| Proxy on another host | The proxy host's internal address | That address or its network |
| A CDN in front of the proxy | The proxy's address; the rightmost `X-Forwarded-For` hop is a CDN node | The proxy's network plus the CDN's origin-pull ranges, so the client address resolves to the real visitor. If the proxy is Caddy, Caddy must also trust the CDN's origin-pull ranges via `trusted_proxies`; see above |

<Callout type="warn" title="What a wrong trust setting does">
If the peer is outside the trusted networks, every proxied request appears to come from the proxy itself, so all visitors share one login rate limit. If the proxy's address also happens to be in `IMGYOUNG_METRICS_ALLOW` (Docker networks are by default) and the proxy forwards `/metrics`, anyone can read the metrics. A proxy that does not set `X-Forwarded-For` has the same effect.
</Callout>

### How forwarding headers are resolved

When the peer is trusted:

1. All addresses from every `X-Forwarded-For` header are collected in order, split on commas; entries that do not parse are skipped.
2. They are checked **from right to left**, skipping addresses inside trusted networks. The first address outside them is the client address.
3. If every address is inside a trusted network (an internal client), the leftmost one is used; if the header is missing or has no usable address, the peer address is used.
4. The first value of `X-Forwarded-Proto` decides HTTPS: `https` (case-insensitive) means the request arrived over HTTPS.
5. The first value of `X-Forwarded-Host` is used as the public host.

When the peer is not trusted, all `X-Forwarded-*` headers are ignored: the client address is the peer, and since ImgYoung does not handle TLS, the request never counts as HTTPS.

**A forged `X-Forwarded-For` has no effect.** Each proxy appends the peer it saw to the end of `X-Forwarded-For`, so a client can only control the leftmost part. For example, a client at `203.0.113.7` sending `X-Forwarded-For: 1.2.3.4` arrives through Nginx on the same host as `1.2.3.4, 203.0.113.7`. Scanning from the right, the first untrusted address is `203.0.113.7`, and the forged `1.2.3.4` is ignored. A request that connects to ImgYoung directly has an untrusted peer, so none of its forwarding headers are believed.

## Listen on loopback only

With a proxy in front, do not expose ImgYoung's port directly:

<Tabs items={['Binary / systemd', 'Docker', 'Compose']}>
<Tab value="Binary / systemd">

Set `IMGYOUNG_LISTEN=127.0.0.1:8721`. For systemd, use a drop-in; see [Configuration](../configuration.mdx):

```bash title="Terminal"
sudo systemctl edit imgyoung
```

```ini title="In the editor"
[Service]
Environment=IMGYOUNG_LISTEN=127.0.0.1:8721
```

```bash title="Terminal"
sudo systemctl restart imgyoung
```

</Tab>
<Tab value="Docker">

Keep the default listen address inside the container and publish the port on the host's loopback address only:

```bash title="Terminal"
docker run -d --name imgyoung --restart unless-stopped \
  -p 127.0.0.1:8721:8721 -v imgyoung-data:/data \
  -e IMGYOUNG_TRUSTED_PROXIES=172.16.0.0/12 \
  ghcr.io/x-haose/imgyoung:latest
```

`-p 8721:8721` publishes on every interface, and Docker's own forwarding rules bypass host firewalls such as ufw.

</Tab>
<Tab value="Compose">

```yaml title="compose.yaml"
services:
  imgyoung:
    ports:
      - "127.0.0.1:8721:8721"
    environment:
      IMGYOUNG_TRUSTED_PROXIES: 172.16.0.0/12
```

If the proxy runs in the same Compose project, you can drop `ports` and let the proxy reach `imgyoung:8721` directly.

</Tab>
</Tabs>

## When base_url is required

`base_url` is **Settings → Runtime settings → Access & links → Public site address** in the admin console. When it is empty, ImgYoung derives the public address from each request: the scheme from whether the request arrived over HTTPS, and the host from `X-Forwarded-Host` when the peer is trusted, otherwise from `Host`.

You must set it when:

- **the public domain differs from what reaches ImgYoung**: for example a CDN pulls from a different hostname, the proxy rewrites `Host` without sending `X-Forwarded-Host`, or the proxy is not trusted. Otherwise the `url` returned by uploads and the endpoint and link prefix in the **S3 client settings** dialog are all wrong.
- **CDN cache purging is enabled**: purging runs in the background with no request to derive from, so it uses `base_url` only. See [CDN](./cdn.mdx).
- **one-click authorization for cloud drive channels is used**: the callback URL must match what is registered with the provider exactly, and it is built from `base_url` only. See [Cloud drives](../channels/cloud-drives.mdx).

Share links copied in the admin console are not affected by any of this: they use `base_url` when it is set, and otherwise the site address in the browser's address bar.

## Keep the upload size limit in step with the proxy

The **Max image size** setting (`max_upload_mb`, 50 MB by default) applies to the file itself, so a file exactly at the limit is accepted. The whole request body may be up to 64 KiB larger than the max image size, which leaves room for multipart boundaries and fields such as `exif_policy` and `ttl`. The proxy's body limit must be at least that:

- Nginx allows only 1 MB by default; the example sets `client_max_body_size 60m;`.
- The Caddy example sets no body limit. If you set `max_size` with `request_body`, keep it at or above the max image size plus 64 KiB.

When you raise the max image size in the admin console, raise the proxy's limit too. Otherwise large images are rejected by the proxy (413) and never reach ImgYoung.

## Leave enough read timeout for snapshot restores

When you **Restore** a snapshot in the admin console, the request returns only after the snapshot has been downloaded from the channel and checked. If the request is cut off before then, the restore is cancelled and the service keeps running. The proxy's read timeout must therefore be longer than it takes to download the snapshot:

- **Nginx**: `proxy_read_timeout` defaults to 60 seconds. The example above sets it to `600s` inside `location /`; adjust it to your snapshot size and channel speed. On a timeout (504), the restore has been cancelled and nothing changed.
- **Cloudflare**: the wait for the origin's response is limited to 125 seconds (a timeout returns 524), and only Enterprise plans can raise it. On a timeout it is unknown whether the restore completed: if Cloudflare kept its connection to the origin open, the restore completes there and the service restarts on its own. If downloading the snapshot takes longer than 125 seconds, you cannot restore through Cloudflare from the admin console: open the admin console on the origin directly and restore there, or put the snapshot in place by hand following [disaster recovery](./backup.mdx#disaster-recovery-after-losing-the-host).

See [Backup & restore](./backup.mdx#restoring-behind-a-reverse-proxy).
