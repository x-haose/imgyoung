## 健康检查：/healthz

`GET /healthz` 返回 200 和纯文本 `ok`，不需要认证。它只说明进程在运行、HTTP 服务能响应，**不检查**数据库、渠道或任务队列。

用它做进程存活检查和外部可用性探测；渠道是否健康，请看指标与告警。

## 指标：/metrics

`GET /metrics` 以 Prometheus 文本格式输出指标，与其他接口共用同一个端口。`/healthz` 与 `/metrics` 本身的请求不计入 HTTP 指标。

### 访问控制

指标里有路由、渠道名与用量，不要对公网开放。

- 只有客户端地址在 `IMGYOUNG_METRICS_ALLOW` 网段内的请求能访问，其余返回 403。未设置时允许回环地址与私网地址；设为空串（或只含空白）时，谁都不能访问。客户端地址如何确定，见[反向代理与 HTTPS](./reverse-proxy.mdx)。
- 公网入口（反向代理）不要转发 `/metrics`。`deploy/` 下的 Caddy 与 Nginx 示例都对它返回 404。
- 让 Prometheus 从内网直接访问 ImgYoung 的监听地址。
- 正确配置 `IMGYOUNG_TRUSTED_PROXIES`。配错时，经反向代理的请求都会被当作来自反向代理本身；如果反向代理的地址又在放行网段内，而它转发了 `/metrics`，所有人都能读到指标。

### Prometheus 抓取配置

```yaml title="prometheus.yml"
scrape_configs:
  - job_name: imgyoung
    static_configs:
      - targets: ["10.0.0.5:8721"]   # ImgYoung 的内网地址与端口
```

Prometheus 的地址不在默认放行的私网段内时，把它加进 `IMGYOUNG_METRICS_ALLOW`。设置这个变量会整体替换默认值，仍然需要的默认网段要一并写上，默认值见[配置](../configuration.mdx)。

### 指标清单

所有 ImgYoung 指标都以 `imgyoung_` 开头：

| 指标 | 类型 | 标签 | 含义 |
|---|---|---|---|
| `imgyoung_http_requests_total` | counter | `method`、`route`、`status` | HTTP 请求数。`route` 是路由模板（如 `/i/{id}`），不是原始路径 |
| `imgyoung_http_request_duration_seconds` | histogram | `method`、`route` | HTTP 请求的处理耗时（秒）|
| `imgyoung_upload_duration_seconds` | histogram | `outcome` | 上传耗时（秒）。`outcome` 为 `ok`（成功）、`rejected`（输入不合规或超出配额）或 `failed`（基础设施故障）|
| `imgyoung_channel_puts_total` | counter | `channel`、`result` | 向渠道写入对象的次数，包括上传时的同步写入与之后的补齐；`result` 为 `ok` 或 `error` |
| `imgyoung_channel_storage_bytes` | gauge | `channel` | 渠道用量（字节），按渠道上已就绪副本的图片大小累加，每隔「用量上报间隔」刷新 |
| `imgyoung_channels_total` | gauge | | 已装载的渠道数，包括不健康的，不包括「清理中」的和装载失败的 |
| `imgyoung_channels_healthy_total` | gauge | | 健康的渠道数 |
| `imgyoung_variant_lookups_total` | counter | `result` | 衍生图缓存的查找次数；`result` 为 `hit` 或 `miss` |
| `imgyoung_queue_jobs_waiting` | gauge | | 任务队列中等待执行的任务数，包括可立即执行、已排定时间与等待重试的；抓取时实时查询，查询失败时为 `NaN` |
| `imgyoung_queue_jobs_running` | gauge | | 任务队列中正在执行的任务数；查询方式同上 |

此外还有 Prometheus Go 客户端自带的 `go_*`（运行时）与 `process_*`（进程）指标。

### 常用告警表达式

```text title="PromQL"
# 有渠道不健康
imgyoung_channels_healthy_total < imgyoung_channels_total

# 渠道写入持续出错
sum by (channel) (rate(imgyoung_channel_puts_total{result="error"}[10m])) > 0

# 上传因基础设施失败
sum(rate(imgyoung_upload_duration_seconds_count{outcome="failed"}[10m])) > 0

# 任务队列积压
imgyoung_queue_jobs_waiting > 1000
```

## 告警

ImgYoung 定期检查一组告警条件：启动时检查一次，之后每隔「健康检查间隔」（`health_check_seconds`，默认 60 秒）检查一次。条件成立时开启告警，条件不再成立时告警自动恢复。

- 同一类型、同一对象同时最多只有一条未恢复的告警；
- 条件持续成立期间，告警详情随每次检查更新。

**查看告警**：后台「总览」页的「告警」卡片列出未恢复的告警；点「历史记录」进入「设置 → 告警历史」，可以查看包括已恢复在内的全部告警。告警开启与恢复时也会记日志（`告警开启`、`告警恢复`）。

### 告警类型

| 类型 | 界面名称 | 对象 | 开启条件 | 何时恢复 |
|---|---|---|---|---|
| `channel_unhealthy` | 渠道不健康 | 渠道名 | 渠道最近一次健康探测失败，或渠道装载失败。详情为失败原因（归类说明加原始错误）。「清理中」的渠道不产生这类告警 | 渠道恢复健康 |
| `replication_failed` | 副本补齐失败 | 渠道名 | 该渠道上有补齐失败的副本，详情里有份数。渠道恢复健康后，失败的副本会自动重试 | 渠道上没有补齐失败的副本 |
| `channel_quota_exceeded` | 渠道用量超阈值 | 渠道名 | 设置了「渠道用量告警阈值」，且渠道用量超过阈值 | 用量回到阈值以内，或阈值设为 0 |
| `drain_failed` | 渠道排空失败 | 渠道名 | 选「删除并清理」后，渠道上的对象删不掉，见下文[渠道排空失败](#渠道排空失败) | 渠道被移除；因装载失败开启的，渠道装载成功即恢复 |
| `backup_failed` | 备份失败 | 空 | 最近一次元数据库备份失败，详情为失败原因。失败的情形见[备份与恢复](./backup.mdx#元数据库自动快照) | 下一次备份成功 |

`backup_failed` 只看本次运行中最近一次备份的结果：服务重启后，要等下一次备份失败才会再次出现。

### 渠道排空失败

选「删除并清理」删除渠道后，ImgYoung 在后台删除渠道上的图片副本和它写入的系统对象（包括元数据库快照），这个过程叫排空。排空期间，渠道显示「清理中」。

以下两种情况会开启 `drain_failed`：

- **删除对象失败**：同一个排空任务第 4 次尝试仍然失败时开启，按默认的重试间隔，各次尝试都很快失败时约在首次失败 98 秒后。在此之前，渠道只显示「清理中」。
- **渠道装载失败**：立即开启，因为渠道装载不了就无法排空。渠道装载成功后，这条告警随即恢复，之后是否再次开启，由排空本身的结果决定。

排空会一直自动重试，告警保持开启，直到渠道清空。渠道清空后自动移除，告警随之恢复。

凭证已失效或存储桶已不存在、排空不可能成功时，在「存储渠道」页对该渠道选「直接移除」：渠道立即移除，远端剩下的对象保留不动。

### 告警参数

每条告警除了中文描述 `message`，还带一组参数 `params`，键和值都是字符串。后台按告警类型和参数，用当前的界面语言显示描述；遇到不认识的告警类型时，显示中文 `message`。

| 告警类型 | 键 | 含义 |
|---|---|---|
| `channel_unhealthy`、`drain_failed` | `stage` | 失败环节：`probe`（健康探测）、`load`（装载渠道）或 `drain`（删除渠道上的对象）|
| | `reason` | 失败归类，如 `s3_auth`、`grant_revoked`、`bucket_missing`、`dns`、`timeout`、`config_unreadable`；无法归类时为 `unclassified`。全部取值见[接口参考](../api/admin-channels.mdx)中的 FailureReason |
| | `detail` | 原始错误，多为服务商或网络库的英文报错；已去除凭证，最长 200 个字符 |
| `replication_failed` | `failed` | 补齐失败的副本数 |
| `channel_quota_exceeded` | `bytes` | 渠道用量，单位字节 |
| | `quota` | 告警阈值，单位字节 |
| `backup_failed` | `code` | 错误码：`no_healthy_channel`（没有健康渠道）、`backup_snapshot_failed`（生成快照失败）、`backup_store_failed`（有渠道没写成）或 `backup_prune_failed`（快照都已写入，但有渠道没能清理旧快照）|
| | `detail` | 失败详情；`code` 为 `no_healthy_channel` 时没有 |
| | `snapshot`、`failed`、`total` | 只在 `code` 为 `backup_store_failed` 或 `backup_prune_failed` 时出现：快照文件名、失败的渠道数、这次尝试写入的渠道数 |

渠道还没有探测过就被判为不健康时，`params` 为空对象 `{}`。

### Webhook

在「设置 → 运行配置 → 告警与审计 → 告警 Webhook 地址」填入一个 `http` 或 `https` 地址后，每条告警在**开启**和**恢复**时各发送一次 POST 请求，请求体为 JSON（`Content-Type: application/json`）：

```json title="开启"
{
  "kind": "channel_unhealthy",
  "target": "r2-main",
  "message": "连接超时:检查端点地址与网络连通性(i/o timeout)",
  "params": {
    "detail": "i/o timeout",
    "reason": "timeout",
    "stage": "probe"
  },
  "status": "open",
  "opened_at": "2026-10-15 08:30:00"
}
```

```json title="恢复"
{
  "kind": "channel_unhealthy",
  "target": "r2-main",
  "message": "连接超时:检查端点地址与网络连通性(i/o timeout)",
  "params": {
    "detail": "i/o timeout",
    "reason": "timeout",
    "stage": "probe"
  },
  "status": "resolved",
  "opened_at": "2026-10-15 08:30:00",
  "resolved_at": "2026-10-15 09:05:00"
}
```

| 字段 | 说明 |
|---|---|
| `kind` | 告警类型，见[告警类型](#告警类型) |
| `target` | 告警对象（渠道名）；`backup_failed` 为空串 |
| `message` | 最近一次检查得到的中文描述 |
| `params` | 告警参数，见[告警参数](#告警参数)；没有参数时为空对象 `{}` |
| `status` | `open`（开启）或 `resolved`（恢复）|
| `opened_at` | 开启时刻，UTC，格式 `YYYY-MM-DD HH:MM:SS` |
| `resolved_at` | 恢复时刻，格式同上；只在 `status` 为 `resolved` 时出现 |

投递规则：

- 接收方返回 2xx 即投递成功。连接失败、超时（10 秒）或返回非 2xx 时，在下一次检查时重试，直到成功。
- 同一对象（类型加对象）的状态变化按发生顺序投递：前一条没有投递成功时，后面的也暂缓，下一次检查时按顺序补投。因此，接收方不会先收到新告警的开启、再收到旧告警的恢复。不同对象的告警互不影响。
- 请求不带签名或认证头。需要校验来源时，把密钥放进 URL（如查询参数），并使用 `https`。
- 状态变化发生时没有配置 Webhook 的，这次变化视为已投递，之后再配置也不会补发。
- 请求体格式是固定的。要推送到即时通讯工具，需要一个转换格式的中转服务。

## 日志

- 日志写到标准错误，格式是 Go `log/slog` 的文本格式：每行以 `time=`、`level=`、`msg=` 开头，后面是 `key=value` 形式的字段，消息为中文。
- 日志级别固定为 INFO 及以上，不能调整。
- 查看方式：systemd 用 `journalctl -u imgyoung`，Docker 用 `docker logs imgyoung`，Compose 用 `docker compose logs imgyoung`。

日志里不会出现凭证：

- 渠道的配置参数不会出现在任何日志和错误信息里；
- Cloudflare API Token 只以明文存在于内存中；
- 修改配置的审计记录只写 `(已配置)` 或 `(空)`；
- 上传 Token 和会话只保存哈希。

日志里唯一会出现的密码是随机生成的初始密码：首次启动时，或[重置密码](./password-reset.mdx)后重启时，如果没有用 `IMGYOUNG_ADMIN_PASSWORD` 指定，服务随机生成初始密码并打印一次。在改掉初始密码之前，能读到日志的人都能用它登录。用环境变量指定的初始密码不会写进日志。

下面按场景列出排障时常见的日志。

### 启动、运行与告警

| 日志 | 含义 |
|---|---|
| `ImgYoung 已启动` | 启动完成，附带版本、提交、实际监听地址与数据目录 |
| `已生成主密钥文件,请立即备份……` | 数据目录里是全新的数据库且没有主密钥，本次启动生成了新的 `master.key`。如果不是首次部署，多半是数据目录指错了，或数据卷没有挂载 |
| `启动失败`，`err` 含 `主密钥与数据库不符` | 当前的主密钥不是这个数据库所用的那把。换回原来的主密钥再启动 |
| `启动失败`，`err` 含 `找不到主密钥` | 数据库已经在使用主密钥，但 `IMGYOUNG_MASTER_KEY` 未设置，数据目录里也没有 `master.key`。放回原来的主密钥再启动 |
| `运行失败` | 启动之后的运行错误，如端口被占用、监听地址非法、HTTP 服务异常退出、补齐子系统启动失败。`err` 为原因，进程随即以退出码 1 退出 |
| `CDN purge 已启用(Cloudflare)` / `CDN purge 未启用……` | 启动时 CDN 缓存清除是否已启用 |
| `告警开启` / `告警恢复` | 告警状态变化 |

### 渠道

| 日志 | 含义 |
|---|---|
| `渠道装载失败,本渠道跳过,健康检查时重试` | 渠道配置无法解密、驱动创建失败，或创建超过 30 秒。渠道显示为不健康，失败环节为装载（`stage` 为 `load`），每次健康检查时重试。各渠道并行装载，连不上的后端不会拖慢启动 |
| 同上，`err` 为 `构造后端未在时限内完成: context deadline exceeded` | 装载超过 30 秒。同一配置的上一次装载还没结束时，`err` 为 `构造后端未在时限内完成(同一配置上一次构造仍未结束): context deadline exceeded`。两者都归类为 `timeout`，渠道列表与告警只显示 `context deadline exceeded` |
| `渠道对账完成` | 每日对账 GC 的结果，字段 `objects`、`bytes`、`foreign`、`orphans_deleted`、`phantoms_requeued`，含义见[备份与恢复](./backup.mdx#对账-gc) |
| `渠道已清理完毕并删除` | 选「删除并清理」的渠道已清空并删除。字段 `objects` 为删除的图片副本数，`system_objects` 为删除的系统对象数（包括元数据库快照与探测残留）|
| `渠道已被直接移除,排空停止,剩余远端对象保留` | 排空途中选了「直接移除」，排空随即停止：除了正在删除的那一个对象，远端剩下的对象（包括快照）都保留不动。字段 `objects` 为停止前删除的图片副本数 |

### 备份与恢复

| 日志 | 含义 |
|---|---|
| `元数据库快照已备份` | 一份快照写进了一个渠道，每个渠道一行。字段 `channel`、`key`、`bytes` |
| `快照写入渠道失败` | 快照没能写进某个渠道，其他渠道照常写入。字段 `channel`、`key`、`err` |
| `清理渠道上的旧快照失败` | 快照已写进这个渠道，但清理超出保留份数的旧快照失败。字段 `channel`、`err` |
| `启动备份未完成` / `定时备份未完成` | 这一次备份失败，`err` 与 `backup_failed` 告警的详情相同 |
| `收到停机请求,优雅停机后由进程管理器拉起` | 后台发起了从快照恢复，服务即将停止，由进程管理器重新拉起 |
| `发起恢复的请求已断开,暂存已撤回,不停机` | 恢复请求在快照下载并检查完之前断开（关掉页面、反向代理读超时），恢复已取消，服务不停止，数据不变 |
| `已用暂存快照换入元数据库,原库留存` | 快照已换入，附带原数据库的保存路径 |
| `换入快照后已把渠道绑定时刻重置为当前时刻,快照之后写入渠道的对象不会被对账回收` | 换入快照后，各渠道的绑定时刻已重置，快照之后写入渠道的对象不会被删除。字段 `channels` 为重置的渠道数，见[备份与恢复](./backup.mdx#对账-gc) |
