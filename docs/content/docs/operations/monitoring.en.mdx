## Health check: /healthz

`GET /healthz` returns 200 with the plain-text body `ok` and needs no authentication. It only tells you that the process is running and its HTTP server responds; it does **not** check the database, channels or the job queue.

Use it for liveness checks and external uptime probes; for channel health, look at metrics and alerts.

## Metrics: /metrics

`GET /metrics` serves metrics in the Prometheus text format, on the same port as every other endpoint. Requests to `/healthz` and `/metrics` themselves are not counted in the HTTP metrics.

### Access control

Metrics expose routes, channel names and usage, so keep them off the public internet.

- Only clients whose address is inside `IMGYOUNG_METRICS_ALLOW` can read them; everyone else gets 403. When the variable is unset, loopback and private addresses are allowed; set it to an empty string (or only whitespace) to close `/metrics` to everyone. How the client address is determined is described in [Reverse proxy & HTTPS](./reverse-proxy.mdx).
- Do not forward `/metrics` from the public entry point (the reverse proxy). The Caddy and Nginx examples in `deploy/` answer it with 404.
- Let Prometheus reach ImgYoung's listen address directly over the internal network.
- Get `IMGYOUNG_TRUSTED_PROXIES` right. If it is wrong, every proxied request appears to come from the proxy itself, and if the proxy's address is in the allowed networks and it forwards `/metrics`, anyone can read the metrics.

### Prometheus scrape configuration

```yaml title="prometheus.yml"
scrape_configs:
  - job_name: imgyoung
    static_configs:
      - targets: ["10.0.0.5:8721"]   # ImgYoung's internal address and port
```

If Prometheus is outside the default private ranges, add its address to `IMGYOUNG_METRICS_ALLOW`. Setting the variable replaces the default list, so include any default ranges you still need; the defaults are listed in [Configuration](../configuration.mdx).

### Available metrics

All ImgYoung metrics are prefixed with `imgyoung_`:

| Metric | Type | Labels | Meaning |
|---|---|---|---|
| `imgyoung_http_requests_total` | counter | `method`, `route`, `status` | HTTP requests. `route` is the route template (such as `/i/{id}`), not the raw path |
| `imgyoung_http_request_duration_seconds` | histogram | `method`, `route` | HTTP request latency in seconds |
| `imgyoung_upload_duration_seconds` | histogram | `outcome` | Upload duration in seconds. `outcome` is `ok` (succeeded), `rejected` (invalid input or over quota) or `failed` (infrastructure failure) |
| `imgyoung_channel_puts_total` | counter | `channel`, `result` | Object writes to channels, both synchronous writes during upload and later replication; `result` is `ok` or `error` |
| `imgyoung_channel_storage_bytes` | gauge | `channel` | Channel usage in bytes: the sum of image sizes of the completed replicas on the channel, refreshed every **Usage report interval** |
| `imgyoung_channels_total` | gauge | | Loaded channels, including unhealthy ones, excluding draining channels and channels that failed to load |
| `imgyoung_channels_healthy_total` | gauge | | Healthy channels |
| `imgyoung_variant_lookups_total` | counter | `result` | Variant cache lookups; `result` is `hit` or `miss` |
| `imgyoung_queue_jobs_waiting` | gauge | | Jobs waiting in the job queue: available, scheduled and waiting to retry. Queried at scrape time; `NaN` if the query fails |
| `imgyoung_queue_jobs_running` | gauge | | Jobs currently running in the job queue; queried the same way |

The Prometheus Go client's own `go_*` (runtime) and `process_*` (process) metrics are exported as well.

### Useful alerting expressions

```text title="PromQL"
# A channel is unhealthy
imgyoung_channels_healthy_total < imgyoung_channels_total

# Writes to a channel keep failing
sum by (channel) (rate(imgyoung_channel_puts_total{result="error"}[10m])) > 0

# Uploads failing because of infrastructure
sum(rate(imgyoung_upload_duration_seconds_count{outcome="failed"}[10m])) > 0

# Job queue backlog
imgyoung_queue_jobs_waiting > 1000
```

## Alerts

ImgYoung checks a set of alert conditions on a schedule: once at startup, then every **Health check interval** (`health_check_seconds`, 60 seconds by default). An alert opens when its condition holds and resolves automatically once it no longer does.

- There is at most one open alert per kind and target at any time.
- While a condition persists, the alert's details are refreshed on every check.

**Viewing alerts**: the **Alerts** card on the **Dashboard** lists open alerts; **History** leads to **Settings → Alert history**, which lists every alert, resolved ones included. Opening and resolving are also logged (`告警开启`, `告警恢复`).

### Alert kinds

| Kind | UI label | Target | Opens when | Resolves when |
|---|---|---|---|---|
| `channel_unhealthy` | Channel unhealthy | Channel name | The channel's latest health check failed, or the channel failed to load. Details give the failure (category explanation plus the original error). Draining channels do not raise this alert | The channel is healthy again |
| `replication_failed` | Replication failed | Channel name | The channel has replicas whose replication failed; details give the count. Failed replicas are retried automatically once the channel is healthy again | No failed replicas remain on the channel |
| `channel_quota_exceeded` | Channel over quota | Channel name | A **Channel usage alert threshold** is set and the channel's usage exceeds it | Usage is back within the threshold, or the threshold is set to 0 |
| `drain_failed` | Channel drain failed | Channel name | After **Delete and purge**, the objects on the channel cannot be deleted; see [Channel drain failures](#channel-drain-failures) below | The channel is removed. An alert opened because of a load failure resolves as soon as the channel loads |
| `backup_failed` | Backup failed | Empty | The most recent metadata backup failed; details give the reason. For what counts as a failure, see [Backup & restore](./backup.mdx#automatic-metadata-snapshots) | The next backup succeeds |

`backup_failed` reflects only the most recent backup in the current run: after a restart it does not appear again until a backup fails again.

### Channel drain failures

When you delete a channel with **Delete and purge**, ImgYoung deletes the image replicas and the system objects it wrote on the channel (metadata snapshots included) in the background. This is called draining; while it runs, the channel shows as **Draining**.

`drain_failed` opens in two cases:

- **Deleting objects fails**: the alert opens when the same drain job is still failing on its 4th attempt, about 98 seconds after the first failure with the default retry intervals when each attempt fails quickly. Until then the channel only shows as **Draining**.
- **The channel fails to load**: the alert opens immediately, since a channel that cannot be loaded cannot be drained. Once the channel loads, this alert resolves; whether it opens again then depends on how the drain itself goes.

Draining keeps retrying automatically, and the alert stays open until the channel is empty. The channel is then removed automatically and the alert resolves.

If the credentials are revoked or the bucket is gone, so the drain can never succeed, use **Remove now** on the channel in **Storage channels**: the channel is removed immediately and the remaining remote objects are left in place.

### Alert parameters

Besides the Chinese description `message`, every alert carries `params`, with string keys and values. The admin console uses the kind and these parameters to show the description in the current UI language; for an alert kind it does not know, it shows the Chinese `message`.

| Alert kind | Key | Meaning |
|---|---|---|
| `channel_unhealthy`, `drain_failed` | `stage` | Where it failed: `probe` (health check), `load` (loading the channel) or `drain` (deleting objects from the channel) |
| | `reason` | Failure category, such as `s3_auth`, `grant_revoked`, `bucket_missing`, `dns`, `timeout` or `config_unreadable`; `unclassified` when it cannot be categorized. See FailureReason in the [API reference](../api/admin-channels.mdx) for every value |
| | `detail` | The original error, usually the provider's or network library's English error message, with credentials removed and at most 200 characters |
| `replication_failed` | `failed` | Number of replicas whose replication failed |
| `channel_quota_exceeded` | `bytes` | Channel usage in bytes |
| | `quota` | Alert threshold in bytes |
| `backup_failed` | `code` | Error code: `no_healthy_channel` (no healthy channel), `backup_snapshot_failed` (the snapshot could not be taken), `backup_store_failed` (some channels were not written) or `backup_prune_failed` (every channel was written, but some could not prune old snapshots) |
| | `detail` | Failure details; absent when `code` is `no_healthy_channel` |
| | `snapshot`, `failed`, `total` | Only when `code` is `backup_store_failed` or `backup_prune_failed`: the snapshot file name, the number of channels that failed, and the number of channels this backup tried to write |

If a channel is judged unhealthy before it has ever been checked, `params` is an empty object `{}`.

### Webhook

With an `http` or `https` URL in **Settings → Runtime settings → Alerts & audit → Alert webhook URL**, every alert sends one POST request when it **opens** and one when it **resolves**, with a JSON body (`Content-Type: application/json`):

```json title="Opened"
{
  "kind": "channel_unhealthy",
  "target": "r2-main",
  "message": "连接超时:检查端点地址与网络连通性(i/o timeout)",
  "params": {
    "detail": "i/o timeout",
    "reason": "timeout",
    "stage": "probe"
  },
  "status": "open",
  "opened_at": "2026-10-15 08:30:00"
}
```

```json title="Resolved"
{
  "kind": "channel_unhealthy",
  "target": "r2-main",
  "message": "连接超时:检查端点地址与网络连通性(i/o timeout)",
  "params": {
    "detail": "i/o timeout",
    "reason": "timeout",
    "stage": "probe"
  },
  "status": "resolved",
  "opened_at": "2026-10-15 08:30:00",
  "resolved_at": "2026-10-15 09:05:00"
}
```

| Field | Meaning |
|---|---|
| `kind` | Alert kind; see [Alert kinds](#alert-kinds) |
| `target` | Alert target (a channel name); an empty string for `backup_failed` |
| `message` | Chinese description from the latest check |
| `params` | Alert parameters; see [Alert parameters](#alert-parameters). An empty object `{}` when there are none |
| `status` | `open` or `resolved` |
| `opened_at` | When the alert opened, UTC, formatted `YYYY-MM-DD HH:MM:SS` |
| `resolved_at` | When it resolved, same format; present only when `status` is `resolved` |

Delivery rules:

- Any 2xx response counts as delivered. Connection errors, timeouts (10 seconds) and non-2xx responses are retried on the next check until they succeed.
- Transitions for the same kind and target are delivered in the order they happened: if an earlier one was not delivered, later ones wait and are delivered in order on the next check. The receiver therefore never gets a new alert's opening before an old alert's resolution. Alerts for other targets are not affected.
- Requests carry no signature or authentication header. If the receiver needs to verify the sender, put a secret in the URL (for example as a query parameter) and use `https`.
- A transition that happens while no webhook is configured counts as delivered and is not sent later, even if a webhook is configured afterwards.
- The body format is fixed. To post to a chat tool, put a relay in between that converts the format.

## Logs

- Logs go to standard error in Go's `log/slog` text format: each line starts with `time=`, `level=` and `msg=`, followed by `key=value` fields. Messages are in Chinese.
- The log level is fixed at INFO and above and cannot be changed.
- To read them: `journalctl -u imgyoung` for systemd, `docker logs imgyoung` for Docker, `docker compose logs imgyoung` for Compose.

Credentials never appear in the logs:

- channel configuration parameters never appear in any log line or error message;
- the Cloudflare API token exists in plaintext only in memory;
- audit entries for configuration changes record only `(已配置)` (set) or `(空)` (empty);
- upload tokens and sessions are stored only as hashes.

The only password that ever appears in the logs is a generated initial password: on the first start, or on the restart after a [password reset](./password-reset.mdx), the service generates one and prints it once, unless `IMGYOUNG_ADMIN_PASSWORD` sets it. Until it is changed, anyone who can read the logs can sign in with it. An initial password set through the environment variable is never written to the logs.

The tables below list the log lines most useful when troubleshooting, grouped by area.

### Startup, runtime and alerts

| Message | Meaning |
|---|---|
| `ImgYoung 已启动` | Startup finished; includes version, commit, actual listen address and data directory |
| `已生成主密钥文件,请立即备份……` | The data directory holds a brand-new database and no master key, so this start generated a new `master.key`. Outside a first deployment, this usually means the data directory path is wrong or the volume is not mounted |
| `启动失败` with `err` containing `主密钥与数据库不符` | The current master key is not the one this database uses. Put the original key back and start again |
| `启动失败` with `err` containing `找不到主密钥` | The database already uses a master key, but `IMGYOUNG_MASTER_KEY` is unset and there is no `master.key` in the data directory. Put the original key back and start again |
| `运行失败` | A runtime error after startup, such as the port already in use, an invalid listen address, the HTTP server exiting unexpectedly or the replication subsystem failing to start. `err` gives the cause, and the process then exits with status 1 |
| `CDN purge 已启用(Cloudflare)` / `CDN purge 未启用……` | Whether CDN cache purging was enabled at startup |
| `告警开启` / `告警恢复` | An alert opened or resolved |

### Channels

| Message | Meaning |
|---|---|
| `渠道装载失败,本渠道跳过,健康检查时重试` | A channel's configuration could not be decrypted, its driver could not be created, or creating it took more than 30 seconds. The channel shows as unhealthy with loading as the failed stage (`stage` is `load`), and loading is retried on every health check. Channels load in parallel, so an unreachable backend does not slow down startup |
| The same, with `err` reading `构造后端未在时限内完成: context deadline exceeded` | Loading took more than 30 seconds. If an earlier load of the same configuration is still running, `err` reads `构造后端未在时限内完成(同一配置上一次构造仍未结束): context deadline exceeded` instead. Both are categorized as `timeout`, and the channel list and alerts show only `context deadline exceeded` |
| `渠道对账完成` | Result of the daily reconciliation GC, with fields `objects`, `bytes`, `foreign`, `orphans_deleted` and `phantoms_requeued`; see [Backup & restore](./backup.mdx#reconciliation-gc) for what they mean |
| `渠道已清理完毕并删除` | A channel deleted with **Delete and purge** has been emptied and removed. `objects` is the number of image replicas deleted, `system_objects` the number of system objects deleted (metadata snapshots and probe leftovers included) |
| `渠道已被直接移除,排空停止,剩余远端对象保留` | **Remove now** was chosen while the channel was draining, so the drain stopped: apart from the object being deleted at that moment, the remaining remote objects (snapshots included) are left in place. `objects` is the number of image replicas deleted before it stopped |

### Backup and restore

| Message | Meaning |
|---|---|
| `元数据库快照已备份` | A snapshot was written to a channel; one line per channel, with fields `channel`, `key` and `bytes` |
| `快照写入渠道失败` | A snapshot could not be written to a channel; the other channels are written as usual. Fields `channel`, `key` and `err` |
| `清理渠道上的旧快照失败` | The snapshot was written to this channel, but pruning snapshots beyond the retention count failed. Fields `channel` and `err` |
| `启动备份未完成` / `定时备份未完成` | This backup failed; `err` matches the details of the `backup_failed` alert |
| `收到停机请求,优雅停机后由进程管理器拉起` | A restore from snapshot was started in the admin console; the service is about to stop and be restarted by the process manager |
| `发起恢复的请求已断开,暂存已撤回,不停机` | The restore request was cut off before the snapshot had been downloaded and checked (the page was closed, the reverse proxy's read timeout hit); the restore was cancelled, the service keeps running and nothing changed |
| `已用暂存快照换入元数据库,原库留存` | The snapshot was swapped in; includes where the previous database was kept |
| `换入快照后已把渠道绑定时刻重置为当前时刻,快照之后写入渠道的对象不会被对账回收` | After the snapshot was swapped in, every channel's binding time was reset, so objects written to the channels after the snapshot are not deleted. `channels` is the number of channels reset; see [Backup & restore](./backup.mdx#reconciliation-gc) |
