## /healthz

`GET /healthz` returns 200 with the plain-text body `ok` and needs no authentication. It only means the process is running and its HTTP server responds; it does **not** check the database, channels or the job queue. Use it for liveness checks and external uptime probes; for channel health, use metrics and alerts.

Requests to `/healthz` and `/metrics` themselves are not counted in the HTTP metrics.

## /metrics

`GET /metrics` serves metrics in the Prometheus text format on the same port as everything else.

**Access control**: only clients whose address is inside `IMGYOUNG_METRICS_ALLOW` (loopback and private ranges when the variable is unset) are allowed; everyone else gets 403. Setting the variable to an empty string (or only whitespace) closes `/metrics` to everyone. The client address is resolved by the rules in [Reverse proxy & HTTPS](./reverse-proxy.mdx). Metrics expose route templates, channel names and usage and should not be public:

- the public entry point (the reverse proxy) must never forward `/metrics`; the Caddy and Nginx examples in `deploy/` answer it with 404;
- let Prometheus reach ImgYoung's listen address directly over the internal network;
- get `IMGYOUNG_TRUSTED_PROXIES` right. If it is wrong, every proxied request appears to come from the proxy, and if the proxy's address is in the allowed networks, a proxy that forwards `/metrics` exposes the metrics to everyone.

### Metrics

All application metrics are prefixed with `imgyoung_`:

| Metric | Type | Labels | Meaning |
|---|---|---|---|
| `imgyoung_http_requests_total` | counter | `method`, `route`, `status` | HTTP requests. `route` is the route template (such as `/i/{id}`), not the raw path |
| `imgyoung_http_request_duration_seconds` | histogram | `method`, `route` | HTTP request latency in seconds |
| `imgyoung_upload_duration_seconds` | histogram | `outcome` | Upload pipeline duration in seconds. `ok` succeeded; `rejected` invalid input or over quota; `failed` infrastructure failure |
| `imgyoung_channel_puts_total` | counter | `channel`, `result` | Object writes to channels, both synchronous writes during upload and asynchronous replication; `result` is `ok` / `error` |
| `imgyoung_channel_storage_bytes` | gauge | `channel` | Logical channel usage in bytes: the sum of image sizes of completed replicas; refreshed every **Usage report interval** |
| `imgyoung_channels_total` | gauge | | Loaded channels, including unhealthy ones, excluding channels being deleted or that failed to load |
| `imgyoung_channels_healthy_total` | gauge | | Currently healthy channels |
| `imgyoung_variant_lookups_total` | counter | `result` | Variant cache lookups; `result` is `hit` / `miss` |
| `imgyoung_queue_jobs_waiting` | gauge | | Jobs waiting in the job queue (available, scheduled and retryable); queried at scrape time, `NaN` if the query fails |
| `imgyoung_queue_jobs_running` | gauge | | Jobs currently running; same as above |

The Prometheus Go client's own `go_*` (runtime) and `process_*` (process) metrics are exported as well.

### Prometheus scrape configuration

```yaml title="prometheus.yml"
scrape_configs:
  - job_name: imgyoung
    static_configs:
      - targets: ["10.0.0.5:8721"]   # ImgYoung's internal address and port
```

If Prometheus is outside the default private ranges, add its address to `IMGYOUNG_METRICS_ALLOW` (together with any default ranges you still need — setting the variable replaces the default list).

A few useful alerting expressions:

```text title="PromQL"
# A channel is unhealthy
imgyoung_channels_healthy_total < imgyoung_channels_total

# Writes to a channel keep failing
sum by (channel) (rate(imgyoung_channel_puts_total{result="error"}[10m])) > 0

# Uploads failing because of infrastructure
sum(rate(imgyoung_upload_duration_seconds_count{outcome="failed"}[10m])) > 0

# Job queue backlog
imgyoung_queue_jobs_waiting > 1000
```

## Alerts

Alerts come from an evaluation loop that runs once at startup and then every **Health check interval** (`health_check_seconds`, 60 seconds by default). Each round checks which conditions currently hold and reconciles them with the open alerts: new conditions open an alert, conditions that no longer hold resolve theirs automatically. There is at most one open alert per kind and target; while a condition persists, its details are refreshed every round.

| Kind | UI label | Target | Condition |
|---|---|---|---|
| `channel_unhealthy` | Channel unhealthy | Channel name | The latest health check of an in-service channel failed, or the channel failed to load; details give the failure (category explanation plus the root-cause text) |
| `replication_failed` | Replication failed | Channel name | The channel has replicas whose replication failed; details give the count. Failed replicas are retried once the channel is healthy again |
| `channel_quota_exceeded` | Channel over quota | Channel name | A **Channel usage alert threshold** is set and the channel's usage exceeds it |
| `drain_failed` | Channel drain failed | Channel name | A channel deleted with **Delete and purge** cannot be emptied, in one of two ways: deleting an image replica or a system object this service wrote (metadata snapshots included) fails and the same drain job is still failing on its 4th attempt (with the job queue's default backoff, about 98 seconds after the first failure) — before that the channel only shows as **Draining**, and the job's own timeout or a shutdown interruption does not count as a failure; or the draining channel fails to load, which opens the alert immediately, since a channel that cannot be loaded cannot be drained. Marking a channel as draining clears its earlier failure. Details give the failure. Draining keeps retrying: once the job runs out of attempts, reconciliation queues a new one that counts from its 1st attempt, and the open alert stays as it is until the channel is empty. The channel is then removed and the alert resolves. An alert opened because of a load failure resolves as soon as the channel loads, since the load failure is cleared then; from that point the drain's own failures decide whether it opens again. If the credentials are revoked or the bucket is gone, use **Remove now** on **Storage channels**; the remote objects are left as they are |
| `backup_failed` | Backup failed | Empty | The most recent metadata backup failed: no healthy channel, the snapshot could not be taken, some channels were not written, or every channel was written but pruning old snapshots failed on some (so the retention count did not take effect). A backup interrupted by shutdown does not count as failed. Details give the reason; when some channels failed it reads like `快照 imgyoung-20261016-083000.123.db 有 1/3 个渠道未写成(r2-main: i/o timeout)`, and the channels that were written keep the snapshot |

`backup_failed` reflects the most recent backup in the current process, so after a restart it does not reappear until a backup fails again.

Besides the Chinese description, every alert carries `params` (string keys and values); the admin console renders the description in the current UI language from the kind and these parameters:

| Kind | `params` |
|---|---|
| `channel_unhealthy`, `drain_failed` | `stage`: where it failed — `probe` (health check), `load` (building the driver from the configuration) or `drain` (deleting objects from a channel being deleted); `reason`: the failure category, such as `s3_auth`, `grant_revoked`, `bucket_missing`, `dns`, `timeout` or `config_unreadable`, and `unclassified` when it cannot be categorized — see FailureReason in the [API reference](../api/admin-channels.mdx) for every value; `detail`: the root-cause text, usually the provider's or network library's English error, with credentials removed and cut to at most 200 characters. An empty object `{}` when the channel is unhealthy without ever having been checked |
| `replication_failed` | `failed`: number of replicas whose replication failed |
| `channel_quota_exceeded` | `bytes`: the channel's usage; `quota`: the alert threshold; both in bytes |
| `backup_failed` | `code`: the error code — `no_healthy_channel` (no healthy channel), `backup_snapshot_failed` (the snapshot could not be taken; adds `detail`), `backup_store_failed` (some channels were not written) or `backup_prune_failed` (every channel was written but pruning old snapshots failed on some); the last two add `snapshot`, `failed`, `total` and `detail`, where `total` is the number of channels this round tried to write |

Alerts written before upgrading to a version with description parameters have none: `params` is `null` (if the condition still holds, the next evaluation fills them in), and the admin console shows their Chinese `message` as is. Alert kinds the admin console does not know are shown by their `message` as well.

**Where to see them**: the **Alerts** card on the **Dashboard** lists open alerts; **History** leads to **Settings → Alert history**, which pages through every alert including resolved ones. Opening and resolving are also logged (`告警开启`, `告警恢复`).

### Webhook

With an `http` / `https` URL in **Settings → Runtime settings → Alerts & audit → Alert webhook URL**, every alert is POSTed as JSON (`Content-Type: application/json`) once when it **opens** and once when it **resolves**:

```json title="Opened"
{
  "kind": "channel_unhealthy",
  "target": "r2-main",
  "message": "连接超时:检查端点地址与网络连通性(i/o timeout)",
  "params": {
    "detail": "i/o timeout",
    "reason": "timeout",
    "stage": "probe"
  },
  "status": "open",
  "opened_at": "2026-10-15 08:30:00"
}
```

```json title="Resolved"
{
  "kind": "channel_unhealthy",
  "target": "r2-main",
  "message": "连接超时:检查端点地址与网络连通性(i/o timeout)",
  "params": {
    "detail": "i/o timeout",
    "reason": "timeout",
    "stage": "probe"
  },
  "status": "resolved",
  "opened_at": "2026-10-15 08:30:00",
  "resolved_at": "2026-10-15 09:05:00"
}
```

| Field | Meaning |
|---|---|
| `kind` | Alert kind, see the table above |
| `target` | Alert target (a channel name); empty string for `backup_failed` |
| `message` | Description from the latest evaluation (in Chinese) |
| `params` | Description parameters with string keys and values, per kind as listed above; an empty object `{}` when there are none, `null` for older alerts that have no description parameters |
| `status` | `open` or `resolved` |
| `opened_at` | When the alert opened, UTC, formatted `YYYY-MM-DD HH:MM:SS` |
| `resolved_at` | When it resolved, same format; present only when `status` is `resolved` |

Delivery rules:

- any 2xx response counts as delivered; connection errors, timeouts (10 seconds) and non-2xx responses are retried on the next evaluation round until they succeed;
- for any one alert, the opening is always delivered before the resolution; if an earlier alert for the same kind and target was not delivered this round, later transitions for that kind and target are held back and delivered in order on the next round, so the receiver never gets a new alert's opening before an old alert's resolution; alerts for other targets are not affected;
- requests carry no signature or authentication header; if the receiver needs to verify the sender, put a secret in the URL (for example as a query parameter) and use `https`;
- a transition that happens while no webhook is configured is marked as delivered and is not sent later, even if a webhook is configured afterwards;
- the payload format is fixed; to post to a chat tool, put a small relay in between that converts the format.

## Logs

- Logs go to standard error in Go's `log/slog` text format: each line starts with `time=`, `level=` and `msg=`, followed by `key=value` fields; messages are in Chinese. The level is fixed at INFO and above; there is no setting to change it.
- To read them: `journalctl -u imgyoung` for systemd, `docker logs imgyoung` for Docker, `docker compose logs imgyoung` for Compose.
- Credentials stay out of the logs: channel configuration parameters never appear in logs or error messages, the Cloudflare API token exists in plaintext only in memory, and audit entries for configuration changes only record `(已配置)` (set) or `(空)` (empty). Upload tokens and sessions are stored as hashes only. The one password ever logged is the factory password seeded on first start (or after a [password reset](./password-reset.mdx)), which is public anyway.

Log lines worth knowing when troubleshooting:

| Message | Meaning |
|---|---|
| `ImgYoung 已启动` | Startup finished; includes version, commit, actual listen address and data directory |
| `库里没有可核对的加密数据,暂不记录主密钥指纹;上传 Token 的 S3 凭证若在客户端失效,说明主密钥不是原来那把` | The database has no master key fingerprint and no ciphertext to check against, only data derived from the master key such as upload tokens and encrypted channels: the current key is used without recording a fingerprint, and it is checked once the database holds ciphertext |
| `已生成主密钥文件,请立即备份……` | The data directory holds a brand-new database and no master key, so a new `master.key` was generated. Outside a first deployment this usually means the data directory path is wrong or the volume is not mounted |
| `启动失败` with `err` containing `主密钥与数据库不符` or `找不到主密钥` | The current master key does not match the fingerprint in the database (when there is no fingerprint yet, the key is checked by whether it can decrypt any one piece of encrypted data in the database, and only failing on all of it is a mismatch), or the database already holds data that depends on the master key (ciphertext, or derived data such as upload tokens' S3 credentials and encrypted channels) while `IMGYOUNG_MASTER_KEY` is unset and `master.key` does not exist. Put the original master key back and start again |
| `运行失败` | A runtime error after startup, such as the port already in use, an invalid listen address, the HTTP server exiting unexpectedly or the replication subsystem failing to start; `err` gives the cause, and the process then exits with status 1 |
| `CDN purge 已启用(Cloudflare)` / `CDN purge 未启用……` | Whether CDN cache purging was configured at startup |
| `渠道装载失败,本渠道跳过,健康检查时重试` | A channel's configuration could not be decrypted, its driver could not be built, or building it took more than 30 seconds (channels load in parallel, so an unreachable backend does not hold up startup; on a timeout `err` reads `构造后端未在时限内完成: context deadline exceeded`, or `构造后端未在时限内完成(同一配置上一次构造仍未结束): context deadline exceeded` when an earlier abandoned build of the same configuration is still running and this attempt fails as a timeout straight away. Both are categorized as `timeout`, and the channel list and alerts show only the innermost text `context deadline exceeded`); the channel shows as unhealthy with the load stage as where it failed (`stage` is `load`), and loading is retried on every health check |
| `告警开启` / `告警恢复` | An alert opened or resolved |
| `元数据库快照已备份` | A snapshot was written to a channel; one line per channel, with fields `channel`, `key` and `bytes` |
| `快照写入渠道失败` | A snapshot could not be written to a channel, with fields `channel`, `key` and `err`; the other channels are written as usual |
| `清理渠道上的旧快照失败` | The snapshot was written to this channel, but pruning snapshots beyond the retention count failed; fields `channel` and `err` |
| `启动备份未完成` / `定时备份未完成` | This backup round failed; `err` matches the details of the `backup_failed` alert |
| `渠道对账完成` | Result of the daily reconciliation GC, with fields `objects`, `bytes`, `foreign` (objects with no record whose key is in another format or that predate the channel's binding time; counted, never deleted), `orphans_deleted` and `phantoms_requeued`; see [Backup & restore](./backup.mdx) |
| `渠道已清理完毕并删除` | A channel deleted with **Delete and purge** has been emptied and its record removed; fields `objects` (image replicas deleted) and `system_objects` (system objects deleted, metadata snapshots and deep check leftovers included) |
| `渠道已被直接移除,排空停止,剩余远端对象保留` | An administrator chose **Remove now** while the channel was draining; the drain job stops, and apart from the object being deleted at that moment, the remaining remote objects (snapshots included) are left as they are; `objects` is the number of image replicas deleted before it stopped |
| `收到停机请求,优雅停机后由进程管理器拉起` | A restore from snapshot was triggered in the admin console |
| `发起恢复的请求已断开,暂存已撤回,不停机` | The request that started a restore went away before staging finished (the page was closed, the reverse proxy's read timeout hit); the restore stopped, and the service neither shuts down nor swaps the database |
| `已用暂存快照换入元数据库,原库留存` | The snapshot was swapped in; includes where the previous database was kept |
| `换入快照后已把渠道绑定时刻重置为当前时刻,快照之后写入渠道的对象不会被对账回收` | Follow-up after swapping in a snapshot; the `channels` field gives the number of channels reset; see [Backup & restore](./backup.mdx) |
