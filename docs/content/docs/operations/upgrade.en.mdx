## Before upgrading

1. Read the [release notes](https://github.com/x-haose/imgyoung/releases) of the target version.
2. Keep a copy of the metadata database to roll back to: in the admin console, go to **Settings → Backups & export → Metadata snapshots**, click **Back up now**, then **Download** that snapshot and store it off the server. Alternatively, stop the service and copy `<data dir>/imgyoung.db`; a copy taken while the service is running is incomplete.
3. Make sure the master key `master.key` is backed up; see [Configuration](../configuration.mdx#master-key).

To check the running version, run `imgyoung -version`, or look at **Server version** under **Settings → Runtime settings → Bootstrap configuration** in the admin console.

## Upgrade commands

<Tabs items={['Install script', 'Docker', 'Compose', 'Binary', 'Source']}>
<Tab value="Install script">

Rerunning the install script upgrades to the latest stable release; add `--version X.Y.Z` for a specific version.

```bash title="Terminal"
# Running as a systemd service (installed with --service): replaces the binary, rewrites the unit and restarts the service
curl -fsSL https://raw.githubusercontent.com/x-haose/imgyoung/main/install.sh | sudo sh -s -- --service

# Managing the process yourself: only replaces the binary; restart imgyoung afterwards
curl -fsSL https://raw.githubusercontent.com/x-haose/imgyoung/main/install.sh | sh
```

`--service` overwrites `/etc/systemd/system/imgyoung.service` with `deploy/imgyoung.service` from the release archive. Keep your own environment variables in a drop-in created with `systemctl edit`, which is not overwritten.

</Tab>
<Tab value="Docker">

Pull the new image, remove the old container, and create a new one with the **same volume** and your usual options. Removing a container does not remove its named volume.

If you pass the master key with `-e IMGYOUNG_MASTER_KEY=…`, do not leave it out when recreating the container. Once the instance has started for the first time, it refuses to start without its master key rather than generate a new one.

```bash title="Terminal"
docker pull ghcr.io/x-haose/imgyoung:latest
docker stop imgyoung && docker rm imgyoung
docker run -d --name imgyoung --restart unless-stopped \
  -p 8721:8721 -v imgyoung-data:/data \
  ghcr.io/x-haose/imgyoung:latest
```

Image tags:

- `latest`: the newest stable release;
- a major.minor tag such as `1.0`: the newest patch release of that series;
- a full version such as `1.0.3`: never moves.

Pre-releases only get the full version tag.

</Tab>
<Tab value="Compose">

```bash title="Terminal"
docker compose pull
docker compose up -d
```

If the `image:` in `compose.yaml` pins a major.minor tag, change the tag first to move to another series; if it pins a full version, change it for every upgrade.

</Tab>
<Tab value="Binary">

Download the new archive for your platform from the [releases page](https://github.com/x-haose/imgyoung/releases), verify it against `checksums.txt` from the same release, extract it, replace the old `imgyoung` binary and restart the process. Leave the data directory as it is.

```bash title="Terminal"
sha256sum -c checksums.txt --ignore-missing
tar -xzf imgyoung_<version>_linux_amd64.tar.gz
```

</Tab>
<Tab value="Source">

```bash title="Terminal"
git fetch --tags
git checkout vX.Y.Z
task build
```

Replace the running binary with the newly built `./imgyoung` and restart.

</Tab>
</Tabs>

When the service is stopped, ImgYoung stops accepting new requests, waits for requests in progress and replication jobs to finish — about 8 seconds at most in total, after which remaining requests are cut off — and then exits. Docker's default 10-second stop timeout and the `stop_grace_period: 15s` (Compose) and `TimeoutStopSec=15s` (systemd) in the `deploy/` examples are all enough. Interrupted replication jobs are queued again after the next start.

## Database migrations

Migrations are embedded in the binary and run automatically on every start, right after the database is opened. There is no separate migration command.

- Every migration not yet applied runs in version order. When you skip several versions, the migrations of every version in between are applied in turn. Applied migrations are recorded in the `schema_revisions` table.
- The tables used by the job queue are migrated at startup as well.
- Runtime settings added in a new version start at their default values; existing settings are left as they are.
- If the database has been migrated by a newer version, startup is refused; see [Rolling back](#rolling-back) below.
- If a migration fails, the process exits with an error, and the log names the failing migration file. Roll back using your pre-upgrade snapshot, as described below.

## Rolling back

Downgrades are not supported: migrations only go forward, and some of them drop columns or rebuild tables. An older binary refuses to start on a database migrated by a newer version; the error names the newest migration version in the database and the newest one the binary knows.

Rolling back therefore takes exactly one thing: **the older binary together with your pre-upgrade snapshot**. Without a pre-upgrade snapshot, you have to stay on the new version.

<Steps>
<Step>

Stop the service.

</Step>
<Step>

Switch back to the older binary or image tag.

</Step>
<Step>

Put the pre-upgrade snapshot (or the database copied while the service was stopped) in the data directory as `imgyoung.db.restore`. Do not overwrite `imgyoung.db` with it: if you do, objects written to the channels after the upgrade are treated as orphans and deleted after 48 hours.

For Docker, the file must be owned by `65532:65532`; use the throwaway-container approach shown in [disaster recovery](./backup.mdx#disaster-recovery-after-losing-the-host).

</Step>
<Step>

Start the service. At startup the snapshot is swapped in, and the database migrated by the newer version is renamed to `imgyoung.db.pre-restore-<UTC time>` and kept in the data directory.

</Step>
</Steps>

A rollback loses the metadata written since the upgrade, with the same effects as restoring a snapshot: images uploaded in the meantime have no record in the metadata and can no longer be reached through ImgYoung, while their objects stay on the channels and are never deleted automatically. See [After a restore](./backup.mdx#after-a-restore).
