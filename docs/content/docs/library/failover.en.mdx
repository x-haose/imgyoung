`store/failover` provides four stateless functions over a list of drivers. **The order of the driver slice is the
priority**: which drivers take part, which are healthy, and which ones hold a copy of an object are all decided by the
caller, who passes them in already sorted. The package itself keeps no state.

```go
func Write(ctx context.Context, ds []driver.Driver, key string, r io.ReaderAt, size int64,
	opts WriteOptions) ([]Attempt, error)
func Open(ctx context.Context, ds []driver.Driver, key string) (io.ReadCloser, []Attempt, error)
func Probe(ctx context.Context, d driver.Driver) error
func DeepProbe(ctx context.Context, d driver.Driver) error
```

`Write` and `Open` both return `[]Attempt`, recording every driver actually tried, in the order tried:

  type={{

  }}

## Write: write in order until N copies succeed

```go
attempts, err := failover.Write(ctx, ds, key, bytes.NewReader(data), int64(len(data)),
	failover.WriteOptions{Need: 2, AttemptTimeout: time.Minute})
```

<TypeTable
  type={{
    Need: { type: 'int', required: true, description: 'Minimum number of successful copies, must be >= 1. Writing stops as soon as it is reached; remaining drivers are not written' },
    AttemptTimeout: { type: 'time.Duration', description: 'Timeout for one write to one driver; 0 means only ctx applies', default: '0' },
  }}
/>

- **Drivers are written one at a time in slice order, never concurrently.** When a driver fails, the next one is tried;
  once `Need` copies succeed the call returns and later drivers are not touched.
- **Each attempt reads the data from the beginning.** The source is an `io.ReaderAt` plus `size`, and every attempt
  reads `[0, size)` independently, so a driver that fails halfway does not affect the next one. `*bytes.Reader` and
  `*os.File` both satisfy `io.ReaderAt`.
- **Cancelling `ctx` stops immediately**: `ctx` is checked before each attempt; once it is cancelled no further drivers
  are tried. If there are too few copies in the end and `ctx` has been cancelled or hit its deadline (including partway
  through the last attempt), `ctx.Err()` is returned, not `ErrInsufficient`. A failure caused by cancellation says
  nothing about the drivers.
- **Attempts with `Err == nil` are the drivers that now hold a copy.** Even on success, `attempts` may include failed attempts.
- **Failed writes are not cleaned up**: a failed driver may be left with a partial object. Delete it yourself if
  needed, or let reconciliation deal with it.
- A `Need` larger than the number of drivers is not rejected up front; all drivers are tried, then `ErrInsufficient` is returned.

| Error | Meaning |
|---|---|
| `ErrInvalidNeed` | `opts.Need` is less than 1; checked first |
| `ErrNoDrivers` | The driver slice is empty |
| `ErrInsufficient` | Every driver was tried and there are still too few copies; the same error also wraps the cause of each failure |
| The `ctx` error | Too few copies, and `ctx` was cancelled or hit its deadline (partway through any attempt, including the last) |

## Open: read from the first readable driver

```go
rc, attempts, err := failover.Open(ctx, ds, key)
if err != nil {
	return err
}
defer func() { _ = rc.Close() }()
```

- Drivers are opened in slice order and **the first successful open is returned immediately**; later drivers are not
  touched. The caller closes the reader.
- On success, the last element of `attempts` is the driver serving the reader; the earlier ones are failed attempts,
  useful for logs and metrics.
- **Fallback only happens while opening.** If the reader fails partway through reading, it does not switch to another driver.
- There is no per-attempt timeout, only `ctx`; `ctx` is checked before each attempt, and once it is cancelled
  `ctx.Err()` is returned. If every driver fails and `ctx` has been cancelled or hit its deadline (including partway
  through the last attempt), `ctx.Err()` is returned as well, instead of either error below. With rclone drivers, `ctx`
  usually also governs the returned reader (for HTTP-based backends, cancelling `ctx` aborts the response body), so do
  not cancel it before you finish reading.

When every driver fails, there are two kinds of error:

| Situation | Error returned | Meaning |
|---|---|---|
| Every driver reports the object does not exist | Wraps `driver.ErrNotFound` | The object really is missing |
| At least one driver failed for a reason other than "not found" | Wraps `ErrUnavailable`; each driver's failure appears only in the error text and is not wrapped | Some driver is broken; the object may still exist |

An empty driver slice returns `ErrNoDrivers`; a cancelled or expired `ctx` returns `ctx.Err()`.

The two kinds are mutually exclusive: `errors.Is(err, driver.ErrNotFound)` is true only when every driver confirmed
the object does not exist, and always false when some driver is broken. An `ErrUnavailable` error does not wrap the
drivers' original errors; to examine why a particular driver failed, look at the returned attempts:

```go
rc, attempts, err := failover.Open(ctx, ds, key)
switch {
case errors.Is(err, driver.ErrNotFound):
	// Every driver confirmed the object does not exist: e.g. HTTP 404
case errors.Is(err, failover.ErrUnavailable):
	// Some driver is broken and the object may still exist: treat as temporarily unavailable, e.g. HTTP 503
	for _, a := range attempts {
		log.Printf("driver %d: %v", a.Index, a.Err)
	}
case err != nil:
	// ErrNoDrivers, or ctx was cancelled
default:
	defer func() { _ = rc.Close() }()
	// read from rc
}
```

## Probe and DeepProbe: health checks

| | `Probe` (light check) | `DeepProbe` (deep check) |
|---|---|---|
| What it does | One `Stat` on the reserved key `ProbeKey` | Writes a small object under a random key, reads it back and compares byte for byte, then deletes it |
| Healthy when | `Stat` succeeds or returns `driver.ErrNotFound` | Write, read, and delete all succeed |
| Cost | One read-only request; no writes or deletes | A write and a delete every time |
| What it catches | Unreachable store, invalid credentials | Additionally catches "readable but not writable": read-only credentials, a full bucket, an exhausted quota |
| Good for | Periodic checks | Event-driven checks: creation, configuration changes, manual rechecks, confirming recovery |

`Probe`'s timeout is entirely up to `ctx`, so always call it with a deadline. `ProbeKey` is `.imgyoung-health-probe`; by
convention it is never written, so do not store data under that key.

Details of `DeepProbe`:

- The temporary object key is `.imgyoung-probe-` followed by 16 random hex characters, and the content is a fixed 19
  bytes; random keys keep concurrent deep checks from interfering with each other.
- The write and the read-back are bound by `ctx`. The delete uses its own 10-second timeout detached from `ctx`
  cancellation, so it still tries to clean up after a failed read-back or an expired `ctx`.
- A failure in the write, the read-back, or the content comparison returns the corresponding error. When the content
  read back differs from what was written, the error matches `errors.Is(err, failover.ErrProbeMismatch)`, which means
  the store is silently rewriting or truncating objects. If the read-back
  already failed, the delete result no longer affects the return value; if the read-back succeeded but the delete
  failed (with anything other than `driver.ErrNotFound`), the delete error is returned.
- A failed delete leaves a temporary object behind. `failover.IsDeepProbeKey(key)` reports whether a key is a deep check temporary object, so your cleanup logic can claim and reclaim it.

A successful read-only check does not mean the store accepts writes. A safe combination, and the one the application
uses, is "downgrade only": periodic light checks can only mark a healthy store unhealthy; an unhealthy store whose light
check passes must also pass a deep check (write, read, and delete all succeed) before it is marked healthy again. That
way a store with read-only credentials, which passes the light check but rejects writes, is not mistaken for recovered
on the next light check.

## Building your own replication [#replication]

A common pattern is "return once the primary write succeeds and fill in the other stores in the background": call
`Write` with `Need: 1`, remember the drivers that were not written, and copy to them later.

```go
// writePrimary returns once one copy is written, reporting which drivers hold it and which still need it.
func writePrimary(ctx context.Context, ds []driver.Driver, key string, data []byte) (holders, pending []int, err error) {
	attempts, err := failover.Write(ctx, ds, key, bytes.NewReader(data), int64(len(data)),
		failover.WriteOptions{Need: 1, AttemptTimeout: time.Minute})
	if err != nil {
		return nil, nil, err
	}
	done := map[int]bool{}
	for _, a := range attempts {
		if a.Err == nil {
			done[a.Index] = true
			holders = append(holders, a.Index)
		}
	}
	for i := range ds {
		if !done[i] {
			pending = append(pending, i)
		}
	}
	return holders, pending, nil
}
```

Replicating one copy means reading it from a driver that holds it and writing it to the target driver, and the read
step can use `Open`'s fallback directly:

```go
// Replicate copies key from holders (drivers that hold a copy, in priority order) to target.
// size is the object size in bytes, normally taken from your own metadata; without it, Stat a source driver first.
func Replicate(ctx context.Context, holders []driver.Driver, target driver.Driver, key string, size int64) error {
	rc, attempts, err := failover.Open(ctx, holders, key)
	if err != nil {
		return fmt.Errorf("no readable source copy: %w", err)
	}
	for _, a := range attempts[:len(attempts)-1] {
		log.Printf("source driver %d unreadable, moved on: %v", a.Index, a.Err)
	}
	err = target.Put(ctx, key, rc, size)
	if cerr := rc.Close(); err == nil {
		err = cerr
	}
	return err
}
```

These two functions only perform the work. To turn them into reliable replication you also need:

- **Persisted replica state**: store `holders` and `pending` in your own database so unfinished replication can resume after a restart.
- **Retries with backoff**: retry a failed `Replicate` later, mark it failed and alert after repeated failures, and try again once the store recovers.
- **Reconciliation**: periodically `List` every store and compare with your records in both directions. Objects in the
  store but not in your records are orphans (produced when the write succeeded but recording it failed); delete them
  after a grace period. Copies your records claim but the store lacks need to be replicated again, but beware of the
  race with new writes between listing and reading your records: list first, then read the records, and `Stat` each
  apparently missing object once more before resetting it, replicating only if it really is gone. Only reclaim
  objects you can tell you wrote yourself (by your own key format, for example), and leave files other programs put
  in the same store alone; claim deep check leftovers with `IsDeepProbeKey` and delete them once past the grace period.
- **Concurrency limits**: replication shares the stores' bandwidth and request quotas with regular traffic, so cap how many copies run at once.

The application records replica state in the `blob_channels` table and runs replication on the River task queue; see
[Architecture](../architecture.mdx).

## How the application uses these primitives

The application's channels are a set of rclone drivers, and upload, image access, and health checks all call this package directly:

| Scenario | Call | Arguments and handling |
|---|---|---|
| Upload | `Write` | Drivers are the healthy channels whose write lease could be taken, in priority order; `Need` is the runtime setting `min_success` (values below 1 count as 1); `AttemptTimeout` is 10 minutes. Channels that succeeded are recorded as holding a ready replica; the remaining active channels are recorded as pending and replication jobs are queued. Too few copies returns 503. Copies written to a channel that is marked for cleanup during the write do not count; if fewer than `min_success` copies remain on active channels when recording, the upload also returns 503 and the written objects are deleted |
| Image access | `Open` | Drivers are the channels that are healthy, not being cleaned up, and hold a ready replica of the image, in priority order; each failed attempt is logged; if all fail, 503 is returned |
| Periodic health check | `Probe` / `DeepProbe` | Every `health_check_seconds` seconds, channels that previously failed to load are retried, then all channels get a light check in parallel, with a 10-second timeout per channel; an unhealthy channel whose light check passes is confirmed with a deep check (20-second timeout) before it recovers |
| Event-driven deep check | `DeepProbe` | After a channel is created or edited, on manual recheck, and on connection test, with a 20-second timeout |

Replication jobs try the source channels one by one and write to the target channel, the same idea as `Replicate`
above. The daily reconciliation skips `ProbeKey` and the system directory `_imgyoung/`, and only reclaims orphans whose
keys have the application's object key format (criteria in [Architecture](../architecture.mdx)); leftovers from
deep checks are claimed with `IsDeepProbeKey` and deleted once written more than 48 hours ago, even if they predate the
channel's binding time. For runtime settings, see [Configuration](../configuration.mdx).
