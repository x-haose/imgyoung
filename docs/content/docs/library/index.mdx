ImgYoung 的多存储读写、渠道存储加密与容灾以三个公开 Go 包提供，应用本身也通过这几个包访问存储。
如果你的 Go 项目需要把同一份数据写进多个存储、读取时自动切换到可用的存储、探测存储是否可用，可以直接复用它们。

## 三个包

| 包 | 内容 | 依赖 |
|---|---|---|
| `store/driver` | `Driver` 接口（`Put` / `Open` / `Stat` / `Delete` / `List` / `ListShallow`）、`ObjectInfo`、哨兵错误 `ErrNotFound` | 仅标准库 |
| `store/rclone` | 用 rclone 的任一后端实现 `Driver`；可叠加 crypt 加密层；OAuth 令牌写回；密码类参数编码；导出与驱动等价的 rclone 配置文件 | `store/driver` 与 rclone |
| `store/failover` | 在一组 `Driver` 之上的无状态容灾原语：按序写够 N 份、按序读第一个可读的、轻探测与深探测 | 仅 `store/driver` |

```text
store/failover ──→ store/driver ←── store/rclone ──→ github.com/rclone/rclone
```

- `store/driver` 不导入 rclone，也不导入任何具体后端。你可以自己实现 `Driver`，完全不用 rclone。
- `store/rclone` 是可选的实现，导入它才会把 rclone 编译进来。它注册了 rclone 的全部后端，`Backend` 填任何 rclone 支持的后端名都能用。
- `store/failover` 只操作 `driver.Driver` 接口，rclone 驱动和你自己的驱动都能用。

三个包都不依赖应用的 `internal/` 代码，这条边界由 lint 规则（depguard）强制。

## 安装

```bash title="终端"
# 只用接口与容灾原语(搭配自己实现的驱动)
go get github.com/x-haose/imgyoung/store/failover@latest

# 同时使用 rclone 实现
go get github.com/x-haose/imgyoung/store/rclone@latest
```

本模块的 `go.mod` 声明 Go 1.26.9，你的工具链不能低于这个版本。

## 只编译用到的包

`store/` 与应用同属一个 module：`github.com/x-haose/imgyoung`。Go 只编译被导入的包，只导入 `store/driver` 与 `store/failover` 时，rclone 和应用代码都不会进入你的二进制。

两种导入方式的二进制体积差别很大。在 darwin/arm64 上构建一个只打印一行的最小程序（未 strip）：

| 导入的包 | 二进制大小 |
|---|---|
| `store/failover`（连带 `store/driver`）| 约 2.7 MB |
| `store/rclone` | 约 100 MB |

`store/rclone` 导入了 rclone 的 `backend/all`，一次注册全部后端，所以体积大。

<Callout type="info" title="依赖版本可能被抬高">
导入任一 `store` 包后，本模块进入你的依赖图，它的 `go.mod` 里列出的模块版本会参与 Go 的最小版本选择（MVS）。
如果你的项目也依赖其中某个模块（例如 AWS SDK、`golang.org/x/...`），这个模块的版本可能被抬到不低于本模块要求的版本。
这只影响版本选择。编译哪些代码、二进制多大，仍然只取决于你实际导入的包。
</Callout>

## 兼容承诺

本模块遵循语义化版本。v1.0.0 之前的版本可能包含不兼容的改动，升级前请看 Release 说明。从 v1.0.0 起，三个包的导出标识符在同一主版本内保持向后兼容：类型、函数、方法、字段与哨兵错误不会被删除，签名也不会改变。

- 错误消息是中文，内容不在兼容范围内，不要依赖它。判断错误类别一律用 `errors.Is` 匹配导出的哨兵错误，如 `driver.ErrNotFound`、`failover.ErrUnavailable`。
- `store/rclone` 的后端参数名与行为来自 rclone 本身，以本模块 `go.mod` 中固定的 rclone 版本为准。
- `internal/` 下的包按 Go 的规则无法从模块外导入，不在承诺范围内。

## 需要自己实现的部分

`store` 只负责对一组排好序的驱动执行一次操作。它不保存任何状态，也不在后台运行任何东西。下面这些能力由应用在同一组原语之上实现，你的项目需要的话，要自己搭：

| 能力 | 说明 |
|---|---|
| 副本状态持久化 | 记录哪个对象在哪几个驱动上有副本。`failover.Write` 只返回本次的尝试结果，记录由你负责 |
| 异步补齐 | 先写够 N 份就返回，其余驱动在后台补上。做法见[多存储容灾 · 自己做补齐](./failover.mdx#replication) |
| 对账 | 定期 `List` 存储内容，与你的记录双向比对，清理孤儿对象，重传缺失的副本 |
| 调度 | 健康探测的周期、失败重试与退避、任务队列 |
| 驱动实例管理 | 配置变更时重建驱动并 `Close` 旧实例；保存健康状态，决定切换策略 |
| 网盘授权 | 库只负责把刷新后的令牌写回；首次取得令牌用 `rclone authorize` |

应用里的对应实现在 `internal/core/replication`（补齐与对账）和 `internal/core/channel`（驱动管理、健康探测与网盘授权），可以作为参考。这些部分如何组合，见[架构](../architecture.mdx)。
