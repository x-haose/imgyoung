`store/failover` 在一组驱动之上提供四个无状态函数。**驱动切片的顺序就是优先级**。哪些驱动参与、哪些健康、对象在哪几个驱动上有副本，都由调用方决定，按优先级排好后传进来。包本身不保存任何状态。

```go
func Write(ctx context.Context, ds []driver.Driver, key string, r io.ReaderAt, size int64,
	opts WriteOptions) ([]Attempt, error)
func Open(ctx context.Context, ds []driver.Driver, key string) (io.ReadCloser, []Attempt, error)
func Probe(ctx context.Context, d driver.Driver) error
func DeepProbe(ctx context.Context, d driver.Driver) error
```

`Write` 与 `Open` 都返回 `[]Attempt`，按尝试顺序记录实际访问过的每个驱动：

<TypeTable
  type={{
    Index: { type: 'int', description: '驱动在传入切片中的下标' },
    Err: { type: 'error', description: '这次尝试的错误；nil 表示成功' },
  }}
/>

## Write：按序写够 N 份

```go
attempts, err := failover.Write(ctx, ds, key, bytes.NewReader(data), int64(len(data)),
	failover.WriteOptions{Need: 2, AttemptTimeout: time.Minute})
```

<TypeTable
  type={{
    Need: { type: 'int', required: true, description: '最少成功份数，须 >= 1；凑够即停，其余驱动不再写' },
    AttemptTimeout: { type: 'time.Duration', description: '单个驱动一次写入的超时；0 表示只受 ctx 约束', default: '0' },
  }}
/>

`Write` 按切片顺序逐个写入，不并发。某个驱动写失败，就接着写下一个。成功份数达到 `Need` 立即返回，排在后面的驱动不会被访问。

- **持有副本的驱动**：返回值里 `Err == nil` 的尝试，就是写成功的驱动。成功时 `attempts` 里也可能有失败的尝试。
- **数据源**：传入 `io.ReaderAt` 与 `size`，每次尝试都从头读取 `[0, size)`，上一个驱动写到一半失败不影响下一个。`*bytes.Reader`、`*os.File` 都满足 `io.ReaderAt`。
- **取消**：每次尝试前检查 `ctx`，已取消就不再尝试后续驱动。份数最终不足时，只要 `ctx` 已被取消或到期（包括在最后一次尝试中途），就返回 `ctx.Err()` 而不是 `ErrInsufficient`，便于把取消和驱动故障区分开。
- **失败的写入不清理**：写失败的驱动上可能残留半截对象。需要时自己删除，或交给对账处理。
- **`Need` 大于驱动数**：不会提前拒绝，而是试完全部驱动后返回 `ErrInsufficient`。

| 错误 | 含义 |
|---|---|
| `ErrInvalidNeed` | `opts.Need` 小于 1；最先检查 |
| `ErrNoDrivers` | 驱动切片为空 |
| `ErrInsufficient` | 全部驱动都试过，成功份数仍不足。这个错误同时包裹了每次失败的原因 |
| `ctx` 的错误 | 份数不足，且 `ctx` 已被取消或到期 |

## Open：按序读第一个可读的

```go
rc, attempts, err := failover.Open(ctx, ds, key)
if err != nil {
	return err
}
defer func() { _ = rc.Close() }()
```

`Open` 按切片顺序打开对象，**第一个打开成功的立即返回**，后续驱动不再访问。读取流由调用方 `Close`。成功时，`attempts` 的最后一项就是提供读取流的驱动，前面的都是失败的尝试，可以用来记日志或指标。

- **只在打开时切换**：读取流打开之后中途出错，不会自动换到下一个驱动。
- **超时**：没有单次尝试的超时，只受 `ctx` 约束。每次尝试前检查 `ctx`，已取消就返回 `ctx.Err()`。全部驱动失败时，只要 `ctx` 已被取消或到期（包括在最后一次尝试中途），同样返回 `ctx.Err()`。
- **rclone 驱动的读取流**：`ctx` 通常也约束返回的读取流，HTTP 类后端的响应体会随 `ctx` 取消而中断。读完之前不要取消它。

全部驱动都失败时，错误分两种，二者互斥：

| 情况 | 返回的错误 | 含义 |
|---|---|---|
| 每个驱动都报告对象不存在 | 包裹 `driver.ErrNotFound` | 对象确实缺失 |
| 至少一个驱动的失败不是「不存在」 | 包裹 `ErrUnavailable` | 有驱动故障，对象可能还在 |

`errors.Is(err, driver.ErrNotFound)` 为 true，说明每个驱动都确认对象不存在；只要有驱动故障，它就是 false。`ErrUnavailable` 的错误不包裹各驱动的原始错误，失败原因只写在错误文本里。要逐个判断某个驱动为什么失败，看返回的尝试记录：

```go
rc, attempts, err := failover.Open(ctx, ds, key)
switch {
case errors.Is(err, driver.ErrNotFound):
	// 所有驱动都确认对象不存在:例如 HTTP 404
case errors.Is(err, failover.ErrUnavailable):
	// 有驱动故障,对象可能还在:按「暂时不可用」处理,例如 HTTP 503
	for _, a := range attempts {
		log.Printf("驱动 %d: %v", a.Index, a.Err)
	}
case err != nil:
	// ErrNoDrivers,或 ctx 被取消
default:
	defer func() { _ = rc.Close() }()
	// 读取 rc
}
```

此外，驱动切片为空时返回 `ErrNoDrivers`；`ctx` 已被取消或到期时返回 `ctx.Err()`。

## Probe 与 DeepProbe：健康探测

| | `Probe`（轻探测）| `DeepProbe`（深探测）|
|---|---|---|
| 做什么 | 对约定键 `ProbeKey` 执行一次 `Stat` | 写入一个随机键的小对象 → 读回逐字节核对 → 删除 |
| 判为健康 | `Stat` 成功，或返回 `driver.ErrNotFound` | 写、读、删全部通过 |
| 成本 | 一次只读请求，不写不删 | 每次都有写入与删除请求 |
| 能发现 | 存储不可达、凭证无效 | 还能发现「可读不可写」：只读凭证、桶满、配额耗尽 |
| 适合 | 周期执行 | 事件触发：新建、改配置、手动复查、恢复健康前确认 |

`Probe` 的超时完全由 `ctx` 决定，调用时要带超时。`ProbeKey` 的值是 `.imgyoung-health-probe`，约定从不写入，不要用这个键存数据。

`DeepProbe` 的行为：

- **临时对象**：键为 `.imgyoung-probe-` 加 16 位十六进制随机串，内容是固定的 19 字节。随机键让并发的深探测互不干扰。
- **超时**：写入与读回受 `ctx` 约束。删除使用独立的 10 秒超时，不随 `ctx` 取消，所以读回失败或 `ctx` 到期后仍会尝试删除。
- **返回值**：写入、读回、内容核对任一环节失败，都返回对应的错误。读回的内容与写入的不一致时，返回的错误能被 `errors.Is(err, failover.ErrProbeMismatch)` 判断，说明存储在静默改写或截断对象。
- **删除失败**：读回已经失败时，删除的结果不影响返回值。读回成功而删除失败（且不是 `driver.ErrNotFound`）时，返回删除的错误。
- **残留**：删除失败会留下临时对象。`failover.IsDeepProbeKey(key)` 判断一个键是不是深探测的临时对象，清理逻辑可据此识别并回收。

只读探测成功不代表能写。应用采用的组合是轻探测只降不升：

- 周期轻探测只能把健康的存储判为不健康。
- 不健康的存储即使轻探测通过，也要再经深探测确认写、读、删全部通过，才恢复为健康。

这样，用只读凭证这类能通过轻探测、却写不进去的存储，不会在下一轮轻探测时被误判为已恢复。

## 自己做补齐 [#replication]

常见的用法是主存储写成功就返回，其余存储在后台补上：`Write` 用 `Need: 1`，记下没写到的驱动，稍后再复制。

```go
// writePrimary 写够 1 份就返回,同时给出持有副本与待补齐的驱动下标。
func writePrimary(ctx context.Context, ds []driver.Driver, key string, data []byte) (holders, pending []int, err error) {
	attempts, err := failover.Write(ctx, ds, key, bytes.NewReader(data), int64(len(data)),
		failover.WriteOptions{Need: 1, AttemptTimeout: time.Minute})
	if err != nil {
		return nil, nil, err
	}
	done := map[int]bool{}
	for _, a := range attempts {
		if a.Err == nil {
			done[a.Index] = true
			holders = append(holders, a.Index)
		}
	}
	for i := range ds {
		if !done[i] {
			pending = append(pending, i)
		}
	}
	return holders, pending, nil
}
```

补齐一份副本，就是从持有副本的驱动里读出来，写进目标驱动。读取这一步可以直接用 `Open` 的容灾：

```go
// Replicate 把 key 从 holders(持有副本的驱动,按优先级排好)复制到 target。
// size 是对象字节数,通常取自你自己记录的元数据;没有记录时可以先对源驱动 Stat。
func Replicate(ctx context.Context, holders []driver.Driver, target driver.Driver, key string, size int64) error {
	rc, attempts, err := failover.Open(ctx, holders, key)
	if err != nil {
		return fmt.Errorf("没有可读的源副本: %w", err)
	}
	for _, a := range attempts[:len(attempts)-1] {
		log.Printf("源驱动 %d 读取失败,已切换: %v", a.Index, a.Err)
	}
	err = target.Put(ctx, key, rc, size)
	if cerr := rc.Close(); err == nil {
		err = cerr
	}
	return err
}
```

这两段只负责执行复制。要成为可靠的补齐机制，还需要你自己实现：

- **持久化副本状态**：把 `holders` 与 `pending` 存进你的数据库，进程重启后能继续未完成的补齐。
- **重试与退避**：`Replicate` 失败时稍后重试；多次失败后标记为失败并告警，存储恢复后再重新尝试。
- **对账**：定期对每个存储执行 `List`，与你的记录双向比对。
  - 存储里有、记录里没有的是孤儿对象，写入成功但记录失败时会产生。过了宽限期再删除。只回收能确认是自己写出的对象（例如按你自己的键名格式判断），别的程序写进同一存储的文件不要动。深探测残留用 `IsDeepProbeKey` 识别，过了宽限期即可删除。
  - 记录里有、存储里没有的副本，要重新补齐。列举与查记录之间可能有新的写入，所以要先列举、后查记录；把记录改回待补齐之前，对疑似缺失的对象再 `Stat` 一次，确实不存在才补齐。
- **并发控制**：补齐任务与正常读写共用存储的带宽与请求配额，要限制同时运行的补齐数量。

应用在元数据库里记录每份副本的状态，用 River 任务队列执行补齐，见[架构](../architecture.mdx)。

## 应用中的用法

应用的每个渠道就是一个 rclone 驱动，上传、访问与健康探测都直接调用本包：

| 场景 | 调用 | 参数与处理 |
|---|---|---|
| 上传 | `Write` | 驱动为健康的渠道，按优先级排序。`Need` 取运营配置 `min_success`，小于 1 时按 1。`AttemptTimeout` 为 10 分钟。写成的渠道记为副本就绪，其余渠道记为待补齐，由补齐任务复制。份数不足返回 503。上传没有记入元数据库时（写够份数之前失败、记录失败，或同一幂等键的另一个请求先完成），删掉本次已经写进渠道的对象。对象键带本次上传的短 ID，不会删到别的上传写的对象 |
| 访问图片 | `Open` | 驱动为健康、不在清理中、且这张图的副本已就绪的渠道，按优先级排序。失败的尝试逐条记日志。全部失败返回 503 |
| 周期健康探测 | `Probe` / `DeepProbe` | 每隔 `health_check_seconds` 秒一轮：先重试装载此前装载失败的渠道，再对各渠道并行轻探测，每个渠道超时 10 秒。不健康的渠道轻探测通过后，再做一次深探测（超时 20 秒），通过才恢复健康 |
| 事件深探测 | `DeepProbe` | 创建渠道后、编辑渠道后、手动重检、测试连接时执行，超时 20 秒 |

补齐任务从持有副本的渠道逐个尝试读出，写入目标渠道，做法与上面的 `Replicate` 相同。

每日对账跳过 `ProbeKey` 与系统目录 `_imgyoung/`，只回收键名符合应用对象键格式的孤儿，判定规则见[对账 GC](../operations/backup.mdx#对账-gc)。深探测残留由 `IsDeepProbeKey` 识别，写入超过 48 小时即删除，不论是否早于渠道的绑定时刻。

运营配置项见[配置](../configuration.mdx)。
