## 单实例设计

ImgYoung 按单实例设计：一个进程，一个数据目录。

- **元数据库**：数据目录下的一个 SQLite 文件 `imgyoung.db`，WAL 模式。写操作经单个连接排队执行，读操作使用连接池。驱动是纯 Go 的 `modernc.org/sqlite`。
- **任务队列**：异步任务由 River 执行。River 的任务表与 ImgYoung 自己的表在同一个 SQLite 文件里，不需要单独的队列服务。
- **进程内状态**：上传并发上限、按用户的上传频控、登录限速和访问活跃度的聚合都在进程内存里，衍生图缓存在本地磁盘上。不使用 Redis。
- **单个静态二进制**：全程以 `CGO_ENABLED=0` 构建，管理后台的前端产物与 OpenAPI 文档都编译进二进制。

因此，多个进程不能共用同一个数据目录，ImgYoung 也不支持水平扩展。ImgYoung 只实现了 SQLite；要部署多个实例，需要换用 PostgreSQL（River 也支持 PostgreSQL），并把上面这些进程内状态移到进程外。

## 分层与依赖方向 [#layers]

```text
http ──→ core ──→ infra
  │        └────→ store
  └─────────────→ infra
```

| 层 | 目录 | 职责 |
|---|---|---|
| store | `store/` | 公开的存储引擎：`driver` 接口、`rclone` 实现、`failover` 容灾原语。见[作为 Go 库使用](./library/index.mdx) |
| infra | `internal/infra/` | 基础设施与出站适配：`config`（引导配置与运营配置）、`db`（schema、查询、迁移、sqlc 生成代码）、`secret`（主密钥与加密）、`errcode`（错误码与中文文案目录）、`id`（短 ID）、`imaging`（图像处理）、`cdn`、`urlfetch`（URL 转存的抓取）、`observability`（指标）、`version` |
| core | `internal/core/` | 业务核心：`channel`（渠道与健康探测）、`replication`（补齐、对账、排空、CDN 缓存清理）、`upload`、`variants`（按需处理）、`dedup`、`lifecycle`、`reliability`（备份与恢复）、`auth`、`audit`、`referer`、`usage`、`alert` |
| http | `internal/http/` | HTTP 入站：`publicapi`（上传与图片访问）、`s3api`（S3 兼容接口）、`adminapi`（管理后台）、`middleware`、`httpx`、`router` |
| 装配根 | `cmd/imgyoung/` | `build.go` 按「基础设施 → 业务服务 → HTTP」的顺序手工构造对象图，`serve.go` 用 oklog/run 编排启停，`loops.go` 放周期循环 |

`store` 与 `infra` 是两个并列的底层包：`store` 不依赖任何 `internal/` 包，`infra` 不依赖 core、store 与 http，`core` 同时依赖二者。依赖方向由 golangci-lint 的 depguard 规则在 CI 中强制检查：

| 规则 | 禁止导入 | 原因 |
|---|---|---|
| `store/**` | `internal/` 下的任何包 | store 是公开的可复用存储引擎，不能依赖应用代码 |
| `internal/infra/**` | `internal/core`、`store`、`internal/http` | infra 处在依赖关系的最底层 |
| `internal/core/**` | `internal/http` | 业务核心不知道传输层，可以脱离 HTTP 测试 |
| `internal/http/**` | `store` | 选路与容灾属于 core，传输层只使用 core 给出的结果 |

另外两条约定：

- **接口由使用方定义**：各包在自己内部声明只含所需方法的小接口（如 `upload.ChannelSelector`、`publicapi.BlobChannels`），由具体类型隐式实现。只有 `store/driver.Driver` 由提供方预先定义。
- **身份显式传参**：中间件把认证主体放进请求上下文，handler 取出后作为参数传给 core。core 不从 context 读取身份，按用户隔离的检查在 core 中执行。

HTTP handler 与 River worker 都是薄适配层，只把外部触发翻译成服务调用。周期任务是各服务自带的 `Run(ctx, wait)` 循环，由装配根统一启停，没有单独的调度层。

## 数据模型 [#data-model]

数据模型分为两层：物理图（blob）与上传引用（image）。

```text
images(上传引用)──→ blobs(物理图)──→ blob_channels(各渠道的副本)──→ channels
       N : 1                  1 : N                          N : 1
```

- **`blobs`**：一份实际存储的字节。每次上传都新建一个 blob；后台查重把字节完全相同的 blob 合并后，一个 blob 可以被多条引用指向。blob 记录净化后字节的 `sha256`、感知哈希 `phash`、渠道内对象键 `storage_key`（形如 `<短 ID>_<SHA-256 前 8 位>`）、MIME、大小、尺寸、引用计数 `ref_count` 与待删标记。
- **`images`**：一次上传产生的引用，主键就是对外的 10 位短 ID。归属用户、来源 Token、S3 对象键别名、到期时刻、访问活跃度、冷图标签与清理豁免都记在引用上，不记在 blob 上。
- **`blob_channels`**：一个 blob 在一个渠道上的副本，同时记录补齐状态 `pending → uploading → done / failed`，以及尝试次数、最近一次失败的归类与原始错误。

分成两层后，查重合并只需把引用改指到保留的 blob；TTL、冷图与配额按引用计算；副本、补齐与物理删除按 blob 进行。

### 引用计数与物理删除

`ref_count` 的增减都是原子的 `UPDATE … SET ref_count = ref_count ± 1`，删除引用与递减计数在同一个事务里。计数归零的 blob 标记为待删，物理删除时刻按运营配置 `delete_grace_minutes` 计算。到点后，清理任务依次：

1. 删除它的衍生图缓存；
2. 在一个事务里删除数据库记录，同时复查删除条件，期间又被引用就放弃这次删除；
3. 为每个持有副本的渠道入队对象删除任务。

### 其余的表

| 表 | 内容 |
|---|---|
| `channels` | 渠道：rclone 后端名、用主密钥 AES-GCM 加密的参数 JSON、优先级、健康标记、最近一次失败结论（环节、归类、原始错误，见[错误码与失败结论](#errors)）、是否加密、是否允许直链、清理中标记、创建时刻 `created_at` 与绑定时刻 `bound_at`（见[对账 GC](#reconcile-gc)）。主键自增且删除后不复用（`AUTOINCREMENT`），补齐、删除与排空任务只按主键找渠道。`created_at` 与渠道 ID 一起参与加密渠道的密钥派生，创建后不变 |
| `variants` | 衍生图缓存的索引：每个 blob 的每组处理参数一行，字节存在本地磁盘，按最近访问时间做 LRU 淘汰 |
| `settings` | 运营配置，单行宽表，每列的 DEFAULT 就是出厂值。见[配置](./configuration.mdx) |
| `users`、`tokens`、`sessions` | 用户与配额；上传 Token（只存哈希）；后台会话（只存 session id 的哈希与绑定的 CSRF 令牌）|
| `idempotency_keys` | 上传幂等键，按用户隔离 |
| `dedup_candidates` | 相似重复的候选对，等待管理员裁决 |
| `referer_whitelist`、`audit_log`、`alerts` | 防盗链白名单；管理操作审计；告警记录（类型、对象、中文描述与描述参数）|
| `master_key_fingerprint` | 单行，由主密钥派生的指纹，不能反推出主密钥。全新实例首次启动时记下，之后每次启动据此核对主密钥，主密钥缺失或不符即拒绝启动。见[主密钥](./configuration.mdx#主密钥) |

表结构以 `internal/infra/db/schema/` 下的声明式 SQL 为准，每表一个文件，每张表与每一列都有注释。版本化迁移由 Atlas 据此生成并内嵌进二进制，进程启动时按顺序自动应用。已应用的版本记在 `schema_revisions` 表里，跨多个版本升级时，中间的迁移会依次补上。

迁移不支持降级。库里记有本二进制不认识的迁移版本时（即库已被更新版本的二进制迁移过），进程拒绝启动，错误信息写明库里与本二进制各自的最新迁移版本。回滚只能用「旧二进制 + 升级前的快照」，见[升级](./operations/upgrade.mdx)。

## 上传数据流

数据面上传（`/api/upload`）、后台上传、URL 转存与 S3 PutObject 只是字节的来源不同，拿到字节之后走同一条流程。上传时不查重：每次上传都新建 blob，查重在后台进行，上传流程因此没有分支。

<Steps>
<Step>

**认证与限流**：校验身份（上传 Token、后台会话或 S3 签名），并检查按用户的上传频控（`upload_rate_per_min`）与全局的上传并发上限（`max_concurrent_uploads`，已满时直接返回 429）。S3 入口先检查并发上限，再验签。通过后，把图片字节完整读进内存，任何大小都不写临时文件。请求大小的限制见本节末尾。

</Step>
<Step>

**幂等**：请求带 `Idempotency-Key`，且同一用户已用过这个键时，直接返回已有的图。

</Step>
<Step>

**格式与像素预算**：按文件头的 magic bytes 判定真实格式，只接受 JPEG、PNG、GIF、WebP。只读图片头取得尺寸，并与嗅探出的格式交叉核对；宽 × 高超过 `max_pixels_mp`（像素预算）直接拒绝，不做完整解码。解码所需的内存取决于分辨率，与文件大小无关，所以这一步必须在解码之前。

</Step>
<Step>

**配额预检**：按引用计全额，超出用户配额返回 403，不写渠道。

</Step>
<Step>

**净化**：EXIF 档位为 `strip` 时剥离元数据（JPEG、PNG、WebP；GIF 没有标准元数据段，原样保留）。JPEG 剥离后补回一个只含方向（Orientation）的最小 Exif 段，靠方向标记摆正的照片不会显示成错误的方向；GPS、机型、时间等字段照样删除。方向为默认值时不补。

</Step>
<Step>

**哈希**：完整解码一次，计算感知哈希 pHash；再对将要存储的字节计算 SHA-256。净化在哈希之前，所以 `sha256` 总是对应渠道里实际存储的字节。

</Step>
<Step>

**写渠道**：对象键为 `<短 ID>_<SHA-256 前 8 位>`。元数据库全部丢失时，键里的短 ID 是从存储端反查的最后手段。候选渠道是取得了[写入租约](#write-lease)的健康渠道，`failover.Write` 按优先级逐个写入，写够 `min_success` 份即止。单次写入超时 10 分钟，失败顺延到下一个渠道。

</Step>
<Step>

**落库**：在一个事务里写入 blob、引用、每个在役渠道（不在清理中的渠道）的副本记录与幂等键，写成功的副本为 `done`，其余为 `pending`；之后才释放写入租约。写入期间被标为清理中的渠道，副本记录照样写下，供排空据此删除对象，但不算有效副本。落库时在役渠道上的同步副本不足 `min_success` 份，上传失败，返回 503。

</Step>
<Step>

**入队补齐**：为 `pending` 的渠道入队补齐任务，然后返回。入队失败只记日志，由对账补上。

</Step>
</Steps>

请求大小的限制：

- 单图上限 `max_upload_mb` 只约束图片本身。恰好等于上限可以上传，超出返回 413。
- multipart 请求体整体不超过「单图上限 + 64 KiB」。
- multipart 请求只读取 `file`、`exif_policy`、`ttl` 三个段。`exif_policy` 与 `ttl` 只从表单字段读取，不读 URL 查询参数，每个最多 1 KiB，超出返回 400。

整个上传在内存中完成。峰值内存约为「并发数 × max（单图上限，像素预算对应的解码内存）」，调低这几项即可适配小内存机器。

上传没有落库时，本次已写进渠道的对象会被删除。这包括：写够份数之前失败、落库失败（包括同步副本不足）、幂等键竞争输给另一个请求。对象键带本次的短 ID，不会误删别的上传。删除失败或进程中途退出时留下的对象：

- 在役渠道上的，由对账 GC 当作无主对象回收（48 小时后）；
- 上传期间被标为清理中的渠道上的，会留在存储商处：对账不扫描清理中的渠道，排空也只删除有记录的对象。

## 访问数据流

`GET` / `HEAD /i/{id}` 与 S3 对象键别名 `/o/{user_id}/{key}` 按以下顺序处理。后台预览图 `/api/admin/images/{id}/thumb` 走同一条流程，但不经过防盗链，也不计访问。

1. **防盗链**：中间件按 Referer 白名单放行，或返回 403。
2. **查引用**：查不到返回 404。到期时刻已过的引用立即按不存在处理，不等清理任务回收，也不会因访问而续期。
3. **校验处理参数**：`w` 不在宽度档位，或显式的 `format` 不在允许的格式里，返回 400。这一步与原图格式无关：GIF 这类不做处理的原图，带档位外的参数同样返回 400，带合法参数时输出原图。
4. **计访问**：只有对外入口的 GET 请求在内存中累计活跃度，按 `activity_flush_seconds` 批量落库。HEAD 请求、参数非法的请求与后台预览图都不计访问。
5. **按需处理**：带 `w`、带与原图格式不同的显式 `format`，或未指定格式而浏览器接受 WebP、允许的格式里有 WebP 且原图不是 WebP 时，需要缩放或转格式。GIF 一律输出原图。命中衍生图缓存直接返回；未命中时在 `process_workers` 并发上限内处理并写入缓存，相同参数的并发请求合并为一次处理。处理繁忙或失败时输出原图，并带 `Cache-Control: no-store`。HEAD 请求同样会取得或生成衍生图，只是不返回正文。
6. **输出原图**：候选渠道是健康、不在清理中、且该图副本为 `done` 的渠道，按优先级排序。访问模式为 `redirect`，且候选中有允许直链、未加密并配置了公开地址的渠道时，返回 302 跳到该渠道；重定向带 `Cache-Control: no-store`，因为目标随渠道健康与配置变化，不能被缓存。HEAD 请求只返回响应头，不读取渠道对象。其余情况用 `failover.Open` 代理读取，一个渠道读不到就立即换下一个。

缓存方式按入口区分：

| 入口 | Cache-Control | 原因 |
|---|---|---|
| `/i/{id}` | `public, max-age=31536000, immutable` | 短 ID 指向的内容不可变，URL 即版本 |
| `/o/{user_id}/{key}` | `public, no-cache` | 同键重传会让别名改指新图；允许缓存，但每次使用前要带 ETag 向源站确认，未变则返回 304 |

两个入口的原图与衍生图都带强 ETag：原图为内容哈希，衍生图为哈希加处理参数。请求的 `If-None-Match` 与之相同时返回 304，304 带有 200 响应会带的 `ETag`、`Cache-Control` 与 `Vary`，缓存据此继续使用已存的副本。格式经 `Accept` 协商的响应带 `Vary: Accept`。处理繁忙或失败时输出的原图为 `no-store`，不返回 304。数据库查询失败时返回纯文本 500，可以重试。

## outbox 模式：副本状态以 `blob_channels` 为准 [#outbox]

异步补齐由 River 执行，但 River 任务只是幂等的触发器。副本状态以 `blob_channels` 表为准：即使 River 的任务表丢失或损坏，也能从这张表完整重建队列。

- **补齐任务**：含义是「确保 blob X 在渠道 Y 上有副本」。worker 先读 `blob_channels`：已是 `done` 直接返回；开始复制前置为 `uploading`；失败退回 `pending`，由 River 重试；最后一次尝试仍失败置为 `failed`；成功置为 `done`。
- **入队去重**：按（blob，渠道）去重，只对尚未结束的任务去重，同一副本不会在队列里出现两份。
- **对账**：启动时执行一次，之后每 10 分钟一次。它为清理中的渠道补入排空任务，为每个渠道补写缺失的副本行，把健康渠道上 `failed` 的副本改回 `pending`，再按主键游标分页扫描全部 `pending` / `uploading` 副本并重新入队。扫描期间有副本变成 `done`，也不会让后面的页漏行。
- **新建渠道**：为已有的每个 blob 写入一行 `pending` 副本，由同一套补齐与对账完成复制，不需要额外的回填逻辑。
- **进程被强制终止**：正在执行的任务停在运行状态。River 在它停留超过 16 分钟、且超过该任务自身的超时之后重新排程：排空任务（`drain_channel`）自身超时 1 小时，约 1 小时后才重新排程；其余任务在 16 分钟后。

### 写入租约 [#write-lease]

上传、补齐、元数据库快照与深探测（包括测试连接时对已有渠道的探测）都在渠道的写入租约内写对象并写下记录。渠道一旦标为清理中，新的写入立即被拒绝，不会排在排空后面等待。排空任务开工前，先等在途的写入全部结束，再列举对象与记录。这样，本服务在租约内写下、且已有副本记录的全部对象，排空都能看到。例外是上传没有落库、删除已写对象又失败或进程中途退出时留下的对象，见[上传数据流](#上传数据流)。

### 其他异步任务

| 任务 | 内容 | 最终失败时 |
|---|---|---|
| `delete_object` | 删除渠道上的一个对象 | 留下的对象由对账 GC 当作无主对象回收 |
| `drain_channel` | 排空清理中的渠道，见下文 | 见下文 |
| `cdn_purge` | 清理 CDN 缓存 | 边缘缓存在 CDN 自身的缓存期满后过期 |

这些任务都是幂等的，失败由 River 退避重试。

排空任务按顺序：

1. 等渠道上在途的写入全部结束；
2. 按剩余的副本行逐个删除副本对象，进度就是剩余的副本行数；
3. 删除该渠道上 `_imgyoung/` 下的系统对象（包括元数据库快照）与深探测残留，别的程序写的对象不动；
4. 删除渠道记录。

每删一个对象之前，都按渠道表确认渠道仍在清理中。管理员中途选「直接移除」，排空即停止：除了正在删除的那一个，剩下的远端对象原样保留。

排空失败时：

- 同一个排空任务第 4 次尝试仍失败（按 River 的默认退避，约在首次失败 98 秒后），才把失败结论写进渠道，并开启 `drain_failed` 告警。超时与停机打断时任务立即重排，不计入尝试次数。在此之前，渠道只显示「清理中」，一次网络抖动不会产生一开一关两条告警。
- 清理中的渠道装载失败时，立即写下失败结论并开启告警，因为装载不了就无法排空。
- 之后任务一直退避重试。尝试次数用尽后由对账重新入队，新任务从第 1 次算起；已写下的结论与告警保持不变，直到清完。任务自身超时与停机取消不写失败结论，也不开启告警。
- 重试不会停止。要结束排空，在后台对该渠道选「直接移除」，远端对象保留。

## 错误码与失败结论 [#errors]

服务端交给调用方的失败信息只有稳定的标识与参数，面向人的文案在管理后台的词典里。

- **接口错误**：响应体为 `{code, error, params}`。错误码统一登记在 `internal/infra/errcode`，每个错误码带一份中文文案模板，`error` 就是用 `params` 填好的中文文案。端到端测试核对登记的错误码与接口契约的 `ErrorCode` 枚举一一对应。见[接口参考](./api/index.mdx)。
- **渠道与副本的失败结论**：渠道的 `failure` 为 `{stage, reason, detail}`，副本的为 `{reason, detail}`；最近一次成功或从未失败时为 null。字段含义见下表。
- **告警**：`message` 是中文描述，另带 `params`（键与值都是字符串），Webhook 请求体同样带上。Webhook 按对象（类型加对象）保序投递：前一条没投递出去时，同一对象后续的状态变化留到下一轮按顺序补投。

| 字段 | 含义 |
|---|---|
| `stage` | 失败环节：`probe` 健康探测；`load` 按配置装载驱动；`drain` 删除清理中渠道上的对象 |
| `reason` | 归类，取自契约的 `FailureReason` 枚举，按整条错误链的文本特征判定；判不出时为 `unclassified` |
| `detail` | 原始错误：错误链最内层的错误，多为服务商或网络库的英文原文。凭证已抹除，最多 200 个字符，超长时截到 199 个再加「…」 |

探测结论只写进在役渠道。清理中渠道的结论只来自排空失败与装载失败；渠道标为清理中时，此前的结论一并清空，两类结论不会互相覆盖。

服务端不按请求的语言渲染文案：接口错误、失败结论与告警都只给错误码与参数，渠道模板也只下发结构。各语言的文案集中在前端词典（`web/src/i18n/*/server.ts`），词典的键由 TypeScript 类型检查保证与契约的 `ErrorCode`、`FailureReason` 等枚举一一对应，缺一项即构建失败。中文的 `error` 与告警 `message` 供不经管理后台的调用方和 Webhook 接收方直接展示。

有两处由浏览器直接打开、不经前端渲染，由服务端选择语言：

- 网盘授权回调的提示页，按 `Accept-Language` 选择中文或英文；
- 导出的 rclone 配置文件的头部注释，按查询参数 `lang` 选择，未提供时按 `Accept-Language`。

## 周期任务

周期任务都是服务自带的循环，由装配根统一启停。间隔来自运营配置的任务，在后台修改间隔后立即按新值重新计时，不等旧的周期走完。

| 任务 | 间隔 | 内容 |
|---|---|---|
| 健康探测 | `health_check_seconds`（默认 60 秒）| 先重试装载此前装载失败的渠道：各渠道并行，构造驱动最多 30 秒，不可达的后端到时即记为装载失败。再对各渠道并行做轻探测；不健康的渠道轻探测通过后，还要经深探测确认才恢复健康。见[多存储容灾](./library/failover.mdx) |
| 告警评估 | 同健康探测 | 渠道不健康、补齐失败、渠道用量超阈值、排空失败、备份失败；可推送到 Webhook |
| 生命周期清理 | `cleanup_sweep_seconds`（默认 60 秒）| 回收到期引用 → 物理删除过了宽限期的 blob → 冷图打标 → 回收过期幂等键 → 回收超期审计日志 |
| 活跃度落库 | `activity_flush_seconds`（默认 60 秒）| 把公开访问时刻与计数批量写库；衍生图的最近访问时间按同一间隔落库 |
| 查重 | `dedup_scan_seconds`（默认 300 秒）| 精确重复（SHA-256 相同）自动合并，再做 pHash 相似扫描，结果进入人工裁决队列 |
| 用量上报 | `usage_report_seconds`（默认 300 秒）| 统计各渠道的存储用量并更新指标 |
| 元数据库备份 | `backup_interval_hours`（默认 24 小时）| 用 `VACUUM INTO` 生成一份一致性快照，写到每个健康且不在清理中的渠道的 `_imgyoung/backup/`，各渠道各自保留 `backup_keep` 份。有渠道没写成，或快照都写成但有渠道清理旧快照失败，即本轮失败（`backup_failed` 告警），写成的渠道保留这份快照；被停机打断的一轮不算失败。启动时，任一健康渠道上没有备份间隔内的快照，就先备份一次。见[备份与恢复](./operations/backup.mdx) |
| 认证维护 | 1 分钟 / 1 小时（固定）| 批量写回 Token 最近使用时刻 / 回收过期会话 |
| 补齐对账 | 10 分钟（固定）| 见 [outbox 模式](#outbox) |
| 对账 GC | 24 小时（固定）| 列举每个健康渠道（不扫描清理中的渠道），与副本记录双向比对：回收无主对象，把缺失的副本改回 `pending` 重新补齐。规则见下 |

### 对账 GC 的规则 [#reconcile-gc]

对账 GC 比对渠道上的对象与库里的副本记录，系统目录 `_imgyoung/` 与轻探测键不参与比对。

| 情况 | 判定 | 处理 |
|---|---|---|
| **无主对象** | 键名是本服务的对象键格式 `<短 ID>_<SHA-256 前 8 位>`；库里没有它在该渠道上任何状态的副本记录；修改时间不早于该渠道的绑定时刻 | 写入超过 48 小时后删除。宽限期覆盖已写入渠道、尚未落库的上传 |
| **外来对象** | 库里没有记录，但键名不是本服务的格式，或修改时间早于绑定时刻。例如：别的程序写进来的文件；灾备时新实例接入的旧桶里原有的对象；快照之后、恢复之前写进渠道的对象（恢复后的库里没有它们的记录）| 只计数，不删除；对账日志里记为 `foreign` |
| **探测残留** | 深探测删除失败时留下的 `.imgyoung-probe-` 临时对象 | 写入超过 48 小时后删除，不看绑定时刻（测试连接时留下的残留会早于绑定时刻）；不计入对账统计的对象数与字节数 |
| **缺失副本** | 库里记为 `done`、渠道上实际没有的副本 | 改回 `pending`，重新入队补齐 |

修改时间是对象在存储商处的写入时刻。S3 类后端在列举时直接取服务端记录的修改时间，不逐个读取对象的元数据。

**绑定时刻**（`channels.bound_at`）是这条渠道记录开始对应当前存储位置的时刻，本服务只会在它之后往这个位置写对象。

| 情况 | 绑定时刻 |
|---|---|
| 新建渠道 | 创建时刻。新实例接入旧桶时，桶里原有的对象都早于它，只计数，不删除 |
| 在后台编辑渠道，后端名或任一配置参数有改动 | 编辑时刻。重新输入同一个密码也算改动，因为 rclone 编码密码时带随机 IV |
| 只改名称、优先级或直链开关；令牌刷新写回 | 不变 |
| 从快照恢复 | 全部渠道设为恢复后启动的时刻 |

从快照恢复时，服务在启动时换入暂存文件 `<数据目录>/imgyoung.db.restore`，换入之前先在数据目录写下标记文件 `imgyoung.db.restored`。完成迁移后、加载主密钥之前，见到标记即重置绑定时刻，成功后删除标记，日志为 `换入快照后已把渠道绑定时刻重置为当前时刻,快照之后写入渠道的对象不会被对账回收`。这样，快照之后上传、恢复后的库里没有记录的对象，不会被当作无主对象删除。后台恢复会自动暂存这个文件；手动恢复也要把快照放成这个文件再启动，不要直接覆盖 `imgyoung.db`，否则不会写标记，也不会重置绑定时刻。见[备份与恢复](./operations/backup.mdx)。

`created_at` 不随绑定时刻变化，它与渠道 ID 一起参与加密渠道的密钥派生。

<Callout type="warn" title="两个实例不能共用同一个渠道路径">
对账只认本库的副本记录。另一个实例写进同一路径的对象，键名格式正确却没有记录，过了宽限期就会被当作无主对象删除。
</Callout>

## 停机

收到 SIGINT / SIGTERM，或在后台恢复快照后请求重启时，服务按以下顺序停机：

1. 停止接收新请求，等在途请求结束，超时强制断开；
2. 取消后台循环与在途的补齐任务，各循环退出前把内存中待落库的数据写完；
3. 中止进行中的备份（定时或手动）与恢复时的快照取回：写了一半的快照由存储后端删除，暂存的临时文件删除；
4. 关闭渠道驱动与数据库。

停机最多约 8 秒，在 Docker 默认 10 秒的强制终止时限之内。`deploy/` 下的示例配置另留了余量：compose 的 `stop_grace_period: 15s`，systemd 的 `TimeoutStopSec=15s`。被取消的补齐任务状态留在 `blob_channels` 里，下次启动由对账重新入队。

## 技术选型 [#tech-stack]

选型都服务于同一个前提：单实例、单个静态二进制，除了存储渠道，部署时不需要任何外部服务。依赖的具体版本以仓库的 `go.mod` 为准。

### 语言与构建

- **Go**：静态编译成单个二进制，Docker 镜像小；多渠道写入、异步补齐、健康探测、任务队列这类 I/O 编排，用 goroutine 写起来直接；对象存储、HTTP、指标监控的生态成熟；语法简单、编译快，参与贡献的门槛低。决定性的一条是 rclone 本身用 Go 编写，只有 Go 能在进程内直接调用它的后端，见[为什么在进程内集成 rclone](#rclone)。
- **全程 `CGO_ENABLED=0`**：不依赖 C 工具链与系统库，因此能交叉编译出 Linux、macOS、Windows 各两种架构的发布包，并放进只含一个二进制的 distroless 镜像。下面每一项依赖都是纯 Go，或者不需要 cgo。构建一律带 `-tags nodynamic`：WebP 库默认会在运行时尝试加载系统的 libwebp，关掉这条路径后，Linux 二进制才不依赖动态链接器。

### 依赖

| 领域 | 选择 | 理由 |
|---|---|---|
| HTTP 路由 | chi | handler 就是标准库的 `http.Handler`，没有私有概念；上传（流式读请求体）与图片代理（流式写响应）都直接面对 `io.Reader` / `io.Writer`，适合用薄路由 |
| SQLite 驱动 | `modernc.org/sqlite` | 纯 Go 实现，不需要 cgo |
| 数据库访问 | sqlc | 查询写成 SQL，生成类型安全的 Go 代码。不用 ORM：图床的查询都是简单的精确查询，用不上 ORM 的抽象 |
| 迁移 | Atlas | 以声明式 schema 为准，开发时由 Atlas 计算差异、生成版本化迁移；运行时用它的纯 Go 执行器在启动时应用，部署方不需要安装迁移工具 |
| 任务队列 | River | 持久化任务队列，重试、退避与并发控制现成可用；用 SQLite 驱动时，任务表与 ImgYoung 的表在同一个库里，不多一个服务。任务只是幂等触发器，状态以 `blob_channels` 为准，见 [outbox 模式](#outbox) |
| 周期任务 | 各服务自带的 `Run(ctx, wait)` 循环 | 周期任务只需要「每隔多久执行一次」，间隔取自运营配置、修改后立即重新计时；不引入 cron 库 |
| 依赖装配 | 在 `cmd/imgyoung/build.go` 里手工装配 | 组件集合固定、依赖关系静态，按顺序调用构造函数即可；能搜索、能跳转，没有反射与运行时容器。不用 DI 框架 |
| 生命周期编排 | oklog/run | HTTP、River 与各后台循环各是一个 actor，任何一个退出即触发整组按序停机；比手写 `WaitGroup` 加通道更不容易出错 |
| systemd 就绪通知 | coreos/go-systemd 的 `daemon` 包 | systemd 服务单元为 `Type=notify`，服务打开数据库、监听端口后发送 `READY=1`；rclone 本身已依赖这个模块，不多引入新的依赖 |
| 架构守卫 | depguard（golangci-lint 内置）| 层间依赖方向写成 lint 规则，由 CI 强制检查，见[分层与依赖方向](#layers) |
| 感知哈希 | goimagehash | 纯 Go，输入是解码后的 `image.Image`，直接接在上传的解码步骤后面 |
| 图像编解码 | 标准库、`golang.org/x/image`、gen2brain/webp | 都不需要 cgo；WebP 编码由 gen2brain/webp 在纯 Go 的 WebAssembly 运行时里执行 libwebp |
| 加密 | 标准库的 AES-256-GCM 与 HKDF；`golang.org/x/crypto` 的 argon2id | 分别用于加密渠道配置与凭证、派生渠道密钥与 S3 secret、哈希登录密码。渠道数据本身的加密交给 rclone crypt |
| 限流 | `golang.org/x/time/rate` | 上传频控与登录限速都是进程内的令牌桶 |
| 日志与指标 | `log/slog`、Prometheus 的 client_golang | 各自领域的事实标准 |
| 短 ID | jaevor/go-nanoid | 对外短 ID 用成熟实现；内部主键用 SQLite 自增 rowid，不对外暴露 |

项目以 MIT 许可发布，与 rclone 相同。

### 不引入的东西

- **Redis**：单实例下用不到。幂等键、引用计数这类需要原子性的地方交给 SQLite 的约束与原子更新，限流用进程内令牌桶，衍生图缓存在本地磁盘。进程内实现没有网络往返与序列化，也少运维一个服务。
- **配置文件与配置库**：环境变量只负责把进程启动起来，其余运营配置都存在数据库的 `settings` 表里、在后台修改，每个值只有一个来源。见[配置](./configuration.mdx)。
- **ORM、DI 框架、cron 库**：理由见上表。

### SQLite 与版本化迁移

SQLite 是单个文件，没有外部依赖，一致性快照也只是一个文件，适合自部署，也与单实例设计相配。表结构的每次变更都以版本化迁移发布：长期运行的自部署实例会跨很多个版本升级，按版本顺序应用迁移，才能让表结构保持一致。迁移只能升级，不能降级，见[数据模型](#data-model)。

### 预期会替换的组件

图像处理引擎与数据库是预期会被替换的两个组件。其余依赖不预留替换手段：Go 生态的薄库都贴近标准库的接口形状，需要替换时，改写是机械的工作。

- **图像处理引擎**：按需处理的唯一入口是 `internal/infra/imaging` 的 `Processor.Process(src, params)`。处理器是纯 Go 实现：标准库解码 JPEG / PNG / GIF，WebP 编码用 gen2brain/webp，只输出 WebP、JPEG、PNG，GIF 只原样收发、不处理。不支持 AVIF、HEIF：它们使用率低，编码器（如 libaom）又重。需要更多格式或更快的处理时（例如基于 libvips 的实现），替换的是这个处理器。
- **数据库**：表结构以声明式 SQL 为准，迁移由 Atlas 生成，查询代码由 sqlc 生成。换用 PostgreSQL 时，按目标方言重新生成查询代码与迁移，并换上 River 的 PostgreSQL 驱动。

两者都只有一个实现，没有预先定义接口类型。

## 为什么在进程内集成 rclone [#rclone]

存储层的分工是：rclone 只负责把字节存到某个后端，以及取回、查询、列举、删除；主备切换、补齐、引用计数、查重、TTL、健康判断都由 ImgYoung 实现。两者之间隔着 `store/driver.Driver` 接口。

集成方式是直接 import rclone 的 `fs` 与后端包，在进程内用参数映射构造 `fs.Fs`，不调用 rclone 命令行或 librclone 的 RPC 接口，也不使用 rclone 配置文件。这样做的好处：

- **流式、不落盘**：上传用 `fs.Fs.Put` 直接写内存里的字节，读取时直接把对象流转给 HTTP 响应。
- **配置在 ImgYoung 自己的库里**：渠道参数用主密钥加密后存在 `channels` 表，运行时解密成参数映射交给后端。参数含凭证，不写日志，错误链里也不带参数。
- **OAuth 令牌只有一个刷新者**：rclone 自己刷新 OAuth 令牌，经参数写回钩子交给 ImgYoung，ImgYoung 立即加密落库，不另起刷新循环。写回的规则：
  - 落库前只核对被写回的那个参数：它在库里仍是这个驱动上次确认的值，才写入。
  - 这个参数期间被编辑过，就丢弃这次写回，旧驱动的写回不会覆盖刚保存的新令牌。编辑只改了别的参数（如优先级、路径）时，写回照常并入编辑后的配置。
  - 写回落库失败时，驱动继续使用手里的新令牌，下一次写回时再落库，不重建驱动。
- **一个句柄完成全部操作**：读、写、探测、列举、删除都经同一个 `fs.Fs`，错误映射只维护一套，对象缺失统一映射为 `driver.ErrNotFound`。
- **渠道加密不需要额外代码**：加密渠道在后端之上叠加 rclone 的 crypt 层，上传与访问流程不用改。crypt 是公开格式，持有密码就可以用标准 rclone 独立解密。见[渠道存储加密](./channels/encryption.mdx)。
- **配置可以原样导出**：后台能为每个渠道导出一份 rclone 配置文件，参数与驱动实际交给后端的完全一致，加密渠道另带 crypt 远端。配置文件由 `store/rclone` 的 `ConfigFile` 生成，与构造驱动共用同一套参数整理，标准 rclone 凭它就能脱离 ImgYoung 读写渠道数据。见[驱动接口与 rclone 实现](./library/driver.mdx#config-file)。
- **测试不需要云账号**：rclone 的 `local` 与 `memory` 后端让整条存储链路可以在本机做集成测试。

注册全部 rclone 后端（`backend/all`）后，rclone 支持的任何存储都能直接作为渠道使用，升级 rclone 即带来新后端；代价是二进制体积达到百 MB 量级。这里用的是 rclone 的内部 API，它不承诺稳定，所以 `go.mod` 固定了 rclone 版本，升级由人工进行，并跑完整测试。

`Driver` 接口不依赖 rclone：rclone 的内部 API 变动时，可以换一个 `Driver` 实现，业务代码不用改。接口与 rclone 实现拆成两个包，应用之外的 Go 项目也可以单独复用这套存储引擎，见[作为 Go 库使用](./library/index.mdx)。
