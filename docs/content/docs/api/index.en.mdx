## Where the API document comes from

`api/openapi.yaml` in the repository (OpenAPI 3.1) is the single source of truth for ImgYoung's HTTP API. The group
pages in this section are generated from it, and the end-to-end tests check the status code and body of every
`/api/`, `/healthz`, and `/i/` response against it.

The summaries and descriptions in that document are written in Chinese, so the generated group pages are in Chinese as well.

The document is compiled into the binary, and a running instance serves a copy matching its own version at
`GET /api/openapi.yaml`. You can import it directly into Swagger UI, Scalar, or a code generator:

```bash title="Terminal"
curl -o openapi.yaml https://img.example.com/api/openapi.yaml
```

The S3-compatible API (`/s3/…`) follows the AWS S3 specification and is not part of this reference; see
[Upload clients](../guides/clients.mdx) for how to use it. All of its errors are S3 XML error bodies, including 429
`SlowDown` from upload throttling and 501 `NotImplemented` for unsupported operations.

## Authentication

There are two authentication methods, and their credentials are not interchangeable:

| | Data plane | Admin console |
|---|---|---|
| Paths | `POST /api/upload`, `POST /api/upload/url` | `/api/admin/…` |
| Credential | An upload token in the `Authorization: Bearer <token>` header | The session cookie `imgyoung_session`; state-changing requests also send an `X-CSRF-Token` header |
| How to obtain | Issue one on the admin console's **Upload tokens** page; the plaintext is shown only once | `POST /api/admin/auth/login` |
| Not authenticated | 401: the token is invalid, expired, or revoked, or its owner is disabled | 401: not logged in, or the session expired |
| Not permitted | 403: the token lacks upload permission | 403: CSRF token missing or wrong; still on the initial password; administrator required |

A 401 only ever means a credential problem. If reading the database fails while checking a token or session, the
response is 500 (error code `internal`) and can be retried later; it is never reported as an invalid credential.

Upload tokens look like `imgy_…`. They only authorize the data plane; no admin console endpoint accepts them. The image
access endpoints (`/i/…`, `/o/…`), `/healthz`, and `/api/openapi.yaml` need no authentication.

### Sessions and the CSRF token

<Steps>
<Step>

**Log in**: `POST /api/admin/auth/login` with the body `{"name": "<login name>", "password": "<password>"}`. On success
the response sets the session cookie, and the body is `{"user": {…}, "csrf_token": "…"}`.

</Step>
<Step>

**Call endpoints**: send the cookie with every request. `GET`, `HEAD`, and `OPTIONS` need only the cookie; every other
method must also echo the `csrf_token` from login in the `X-CSRF-Token` header, or it gets a 403 with the error code `csrf_rejected`.

</Step>
<Step>

**Restore the session state**: if you lose the `csrf_token` (after a page reload, say), `GET /api/admin/me` returns the
current user and the same `csrf_token`.

</Step>
</Steps>

```bash title="Terminal"
# Log in, saving the cookie to jar.txt; note csrf_token in the response body
curl -c jar.txt -H 'Content-Type: application/json' \
  -d '{"name":"admin","password":"<password>"}' \
  https://img.example.com/api/admin/auth/login

# Read-only endpoints need only the cookie
curl -b jar.txt https://img.example.com/api/admin/me

# State-changing endpoints also need the CSRF token
curl -b jar.txt -X POST -H 'X-CSRF-Token: <csrf_token>' \
  https://img.example.com/api/admin/auth/logout
```

Session details:

- The cookie is `HttpOnly` and `SameSite=Lax`. It is also `Secure` when the request arrives over HTTPS, whether TLS is
  terminated by the server itself or a trusted reverse proxy reports HTTPS via `X-Forwarded-Proto`.
- A session lasts 30 days from login and is not extended by use; after that you must log in again.
- Changing a user's password invalidates all of that user's sessions.
- Too many login attempts return 429.
- While an account still has the initial password, its session can use only three endpoints: log out
  (`POST /api/admin/auth/logout`), view itself (`GET /api/admin/me`, where `must_change_password` is true), and change
  the password (`PUT /api/admin/me/password`). Every other admin endpoint, including admin console uploads and issuing
  tokens, returns 403 with the error code `must_change_password`. Everything works normally once the password is
  changed and you log in again.

Channels, users, hotlink protection, audit log, alerts, backups, export, and moderation endpoints, as well as reading
the full runtime settings and changing them, are for administrators only; a regular user gets 403.

## Error format

Error responses use a single JSON envelope, except on the image access endpoints (see below). This is the response to
a file too large for the default per-image limit of 50 MB:

```json
{
  "code": "upload_too_large",
  "error": "文件超过大小上限(50 MB)",
  "params": { "max": "50" }
}
```

| Field | Meaning |
|---|---|
| `code` | The error code, a stable machine-readable identifier. The same kind of failure always has the same code, regardless of changes to the wording; programs should branch on it rather than parse the text in `error` |
| `error` | Message text in Chinese, with the parameters already filled in and no internal details or credentials. Callers that do not go through the admin console (PicGo, ShareX, curl, and so on) can show it to users directly |
| `params` | Values for the placeholders in the message, keyed by placeholder name, all strings; omitted for error codes without parameters |

There are about 100 error codes; the complete list is the `ErrorCode` enum in the API contract. Expand the `Error`
schema in any endpoint's error responses in this reference to see it, or look it up in `/api/openapi.yaml`. The admin
console renders the message in the current interface language from `code` and `params`, so the English interface never
shows Chinese error messages.

- When a runtime setting fails validation, the code tells which kind of failure it is: `setting_unknown`,
  `setting_type`, `setting_positive`, `setting_non_negative`, `setting_too_large`, `setting_range`, `setting_option`,
  `setting_url`, `setting_site_root`, or `setting_empty`. `params.key` is the offending setting key.
- In the result of a batch image deletion, each item in `failed` has the same `code` / `error` / `params` plus the
  image `id`. A failed cloud drive authorization result (`GET /api/admin/channel-oauth/result`) carries the same three fields.

### Errors from the image access endpoints

The image access endpoints are `/i/{id}`, `/o/{user_id}/{object_key}`, and the admin console preview
`/api/admin/images/{id}/thumb`. Apart from 400 for invalid processing parameters, which is still a JSON envelope,
their error responses are plain text:

| Status | Meaning |
|---|---|
| 403 | Rejected by hotlink protection (`/i/` and `/o/` only) |
| 404 | The image does not exist, has expired, or was deleted |
| 500 | Looking up the image metadata failed (database error); retry later |
| 503 | No healthy channel can currently read the image |

The admin console preview checks the session first. Authentication errors such as not being logged in, and a 500 from
a database failure while checking the session, are JSON envelopes; a 500 from looking up the image metadata afterwards
is plain text.

In `redirect` access mode, the 302 redirect from an image access endpoint carries `Cache-Control: no-store`. The
redirect target changes with channel health and configuration, so it stays out of CDN and browser caches.

### Common status codes

| Status | Meaning |
|---|---|
| 400 | Invalid request body or parameters |
| 401 | Not authenticated: invalid token, or not logged in / session expired; only ever a credential problem |
| 403 | Not permitted: CSRF check failed, still on the initial password, administrator required, or the token lacks upload permission; for uploads it also means the storage quota is full |
| 404 | The target does not exist or is not visible to the current user |
| 409 | Conflicts with existing state, such as a duplicate name, a channel that holds the only copy of some images, a channel that is draining, a channel configuration that changed while saving, or a recovery of image records already running (`recovery_busy`) |
| 413 | Larger than the per-image size limit (runtime setting `max_upload_mb`) |
| 415 | Not a supported image format (judged by file content) |
| 422 | Resolution exceeds the pixel budget (runtime setting `max_pixels_mp`), or the side length or aspect ratio exceeds the limit (`max_side_px`, `max_aspect_ratio`, error code `upload_bad_dimensions`); a parameter value cannot be written to the exported rclone config file (`channel_unrepresentable`); the snapshot to restore is not a complete database file or not an ImgYoung metadata database (`snapshot_corrupt`) |
| 429 | The upload concurrency limit is reached, the user is uploading too often, or there are too many login attempts; wait as indicated by `Retry-After` when present |
| 500 | Internal server error, including database faults; error code `internal`, retry later. Any endpoint that touches the database can return 500 |
| 503 | On upload, no healthy channel can be written or too few synchronous replicas succeeded; on image access, no channel can currently read the image |

The group pages list the status codes each endpoint can actually return.

## Shared conventions

- **Timestamps**: unless stated otherwise, UTC text in the form `YYYY-MM-DD HH:MM:SS` (for example
  `2026-10-15 08:30:00`), with no time zone suffix. The exceptions are `built_at` in build info and `taken_at` on
  backup snapshots, which are RFC 3339, with `taken_at` at millisecond precision.
- **Lists**: list endpoints return `{"items": […], "total": N}`, where `total` counts all items after filtering.
- **Pagination**: the image, upload token, duplicate, cleanup, and audit log lists, as well as the alert list with
  `status=all`, accept `page` and `page_size`. `page` starts at 1 and defaults to 1; `page_size` ranges from 1 to 100
  and defaults to 20. An invalid pagination, time range or filter parameter gets 400 with error code
  `query_param_invalid`, and `params.name` names the parameter.
- **Time ranges**: the image list and the audit log accept `since` (inclusive) and `until` (exclusive), in the same format.
- **IDs**: images use a 10-character short ID string; user IDs are strings, and the built-in administrator is
  `default`; tokens, channels, duplicate candidates, and similar records use integers; backup snapshots are identified by file name.
- **Idempotent uploads**: uploads may send an `Idempotency-Key` header. Within the retention period, retries with the
  same key by the same user return the same image. The retention period is the runtime setting
  `idempotency_key_ttl_hours`, 24 hours by default. Keys are scoped per user.
- **Request bodies**: JSON endpoints use `application/json`. File uploads use `multipart/form-data` with the file in
  the `file` field; the optional `exif_policy` and `ttl` are read only from form fields (never from URL query
  parameters), at most 1 KiB each.
- **Base URL**: the API shares the site's origin, with the path prefixes shown above and no version segment.
