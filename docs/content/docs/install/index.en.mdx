title: Installation
description: Five ways to install, compared - the install script, the Docker image, Docker Compose, release archives and building from source.

ImgYoung is a single pure-Go binary with the admin console's front end compiled in. It needs no database server, cache or other process at runtime.

All five methods install the same program. They differ only in how you get it and what supervises it.

## Comparison

| Method | Suits | Needs root | Upgrading | Data directory |
|---|---|---|---|---|
| [Install script](./script.mdx) | Running directly on a Linux or macOS host; on Linux, optionally under systemd | To install into `/usr/local/bin` or with `--service`; not for `~/.local/bin` | Run the same command again | `/var/lib/imgyoung` with `--service`; otherwise `data/` under the directory it is started from |
| [Docker image](./docker.mdx) | Hosts that already run Docker | Depends on how Docker permissions are set up on the host | Pull the new image and recreate the container | The volume mounted at `/data` in the container |
| [Docker Compose](./compose.mdx) | Keeping the deployment in a file, or running it alongside a reverse proxy | Same as above | `docker compose pull`, then `docker compose up -d` | The `imgyoung-data` volume, prefixed with the Compose project name |
| [Release archive](./binary.mdx) | Windows; hosts where running the script is inconvenient; full manual control | No | Download the new archive, replace the binary, restart | `data/` under the directory it is started from, or `IMGYOUNG_DATA_DIR` |
| [Build from source](./source.mdx) | Developers who change the code or build it themselves | No | Pull the new code and rebuild | Same as the release archive |

Not sure? If you have Docker, use [Docker Compose](./compose.mdx). On a Linux host without Docker, use the [install script](./script.mdx) with `--service`. On a system with a graphical interface such as Synology, 1Panel, BT Panel, CasaOS or Unraid, see [NAS and server panels](./nas-panel.mdx).

## Environments that do not fit

ImgYoung is a long-running process that keeps its data on a local disk. Two kinds of environment cannot run it or do not suit it:

- **Platforms that only host static pages or run functions per request**, such as Cloudflare Workers and Pages: they cannot run this Go binary.
- **Platforms with no persistent disk, or that put idle apps to sleep**, which is the case on the free tier of many hosting platforms: data is lost on restart, and the first request after a sleep waits for a cold start, so image links tend to time out.


## What all methods share

- **Listening address**: `:8721` by default, which is port 8721 on every interface. Change it with the `IMGYOUNG_LISTEN` environment variable.
- **First sign-in**: open `http://<host>:8721/` and sign in with `admin` and the initial password printed in the log of the first start. The console asks you to change the password right away. You can also set the initial password with the `IMGYOUNG_ADMIN_PASSWORD` environment variable.
- **Data directory**: holds the metadata database `imgyoung.db`, the master key `master.key`, the built-in local channel's `blobs/` and the variant cache `variants/`. Back up the whole directory, and keep a separate backup of `master.key`.
- **Configuration**: a handful of bootstrap settings come from `IMGYOUNG_*` environment variables; all runtime settings are edited in the console and apply on save. There is no config file. See [Configuration](../configuration.mdx).
- **Process supervisor**: for long-running use, run it under something that restarts the process after it exits, such as systemd (`Restart=always`) or Docker (`--restart unless-stopped`). **Restore** under **Settings → Backups & export** makes the service exit cleanly, and the snapshot is swapped in when the supervisor starts it again. The samples under `deploy/` in the repository are already set up this way.

<Callout type="info" title="Why there is no go install">
  `go install` compiles straight from the repository source. The admin console's front end is a build artifact that is not committed, so a binary installed that way has the API but no console. To install on a machine, use the install script or a release archive; no Go toolchain is needed.

  What Go developers usually want to reuse is the storage engine, which is a public package you can `go get`. See [Go library](../library/index.mdx).
</Callout>
