## Running it

```bash title="Terminal"
docker run -d --name imgyoung --restart unless-stopped \
  -p 8721:8721 \
  -v imgyoung-data:/data \
  ghcr.io/x-haose/imgyoung:latest
```

Open `http://<host>:8721/` and sign in with `admin` and the initial password; the first sign-in asks you to change the password right away. The initial password is printed in the log of the first start (`docker logs imgyoung 2>&1 | grep 初始密码`), or you can set it with `IMGYOUNG_ADMIN_PASSWORD`.

| Flag | Purpose |
|---|---|
| `-d --name imgyoung` | Run in the background as a container named `imgyoung`, which later commands refer to |
| `--restart unless-stopped` | Start the process again after it exits; see "Restart policy" below |
| `-p 8721:8721` | Publish the service port. If a reverse proxy on the same host is the only entry point, use `-p 127.0.0.1:8721:8721` so 8721 is not exposed directly |
| `-v imgyoung-data:/data` | A named volume holding all data |

The image is published for `linux/amd64` and `linux/arm64`, and Docker picks the right one for the host. To see the version inside an image:

```bash title="Terminal"
docker run --rm ghcr.io/x-haose/imgyoung:latest -version
```

## Image tags

The image is `ghcr.io/x-haose/imgyoung`. Tags have no `v` prefix:

| Tag | Points to | Good for |
|---|---|---|
| `1.2.3` | One specific version; never changes after release | Production, where you decide exactly when to upgrade |
| `1.2` | The latest stable release in the 1.2 series; moves when a patch release ships | Getting fixes automatically without crossing a minor version |
| `latest` | The latest stable release | Trying it out and personal instances |

Pre-releases get only their exact version tag and never move the major.minor tags or `latest`, so instances pinned to those never pull a pre-release.

## The data volume

The data directory inside the container is `/data`; the image sets `IMGYOUNG_DATA_DIR=/data`. It contains:

| Path | Contents |
|---|---|
| `imgyoung.db` | The metadata database (SQLite): users, image records, channel configuration, runtime settings and the job queue |
| `master.key` | The master key, mode 0600 |
| `blobs/` | Objects of the built-in local channel |
| `variants/` | The cache of variants produced by on-demand processing, capped at 10240 MB by default |

- The database runs in WAL mode, so `imgyoung.db-wal` and `imgyoung.db-shm` sit next to it while running. Channel credentials in it are encrypted with the master key.
- `master.key` is generated when a brand-new instance first starts without `IMGYOUNG_MASTER_KEY`. When `IMGYOUNG_MASTER_KEY` is set, the file is neither created nor read.
- While the local channel is healthy, metadata snapshots are also written to `blobs/_imgyoung/backup/`.
- When the variant cache exceeds its cap, the least recently accessed variants are evicted first.
- During a restore from a snapshot you may also see the staged file `imgyoung.db.restore`, and afterwards the previous database kept as `imgyoung.db.pre-restore-<time>`.

<Callout type="warn" title="Back up master.key separately">
  Channel credentials and the data on encrypted channels can only be decrypted with the master key, and the S3 credentials of upload tokens are derived from it. The key is not included in metadata snapshots or data exports, and once it is lost none of that can be recovered.

  The database records a fingerprint of the master key. If the key is missing or wrong, the service refuses to start and says why, instead of carrying on with a new key.

  Copy it somewhere safe right after the first start:

  ```bash
  docker cp imgyoung:/data/master.key ./imgyoung-master.key
  ```
</Callout>

### Using a host directory instead

To keep the data in a directory on the host, first give that directory to the user the image runs as (uid 65532):

```bash title="Terminal"
sudo mkdir -p /srv/imgyoung
sudo chown 65532:65532 /srv/imgyoung
docker run -d --name imgyoung --restart unless-stopped \
  -p 8721:8721 \
  -v /srv/imgyoung:/data \
  ghcr.io/x-haose/imgyoung:latest
```

A named volume inherits the ownership of `/data` from the image the first time it is mounted; a host directory does not. With the wrong owner, the process cannot create the database and fails at startup.

## Environment variables

These are all bootstrap settings. Pass them with `-e`; changes take effect only after the container is recreated. See [Configuration](../configuration.mdx) for the full reference.

| Variable | Default | Description |
|---|---|---|
| `IMGYOUNG_DATA_DIR` | `/data` (set by the image) | Leave it alone |
| `IMGYOUNG_LISTEN` | `:8721` | Listening address inside the container; rarely needs changing |
| `IMGYOUNG_MASTER_KEY` | Empty, meaning `/data/master.key` is used | A 64-character hex master key |
| `IMGYOUNG_ADMIN_PASSWORD` | Empty, meaning one is generated at the first start | The built-in administrator's initial password, at least 8 characters |
| `IMGYOUNG_TRUSTED_PROXIES` | `127.0.0.0/8,::1/128` | Reverse proxy networks whose forwarding headers are trusted; see "Behind a reverse proxy" below |
| `IMGYOUNG_METRICS_ALLOW` | Loopback and private ranges | Networks allowed to read `/metrics` |

You can generate a master key with `openssl rand -hex 32`. When switching an existing instance to `IMGYOUNG_MASTER_KEY`, use the exact value from its current `master.key`; a wrong value makes startup fail.

A variable that is not set takes its default. Setting it to an empty string (or only whitespace) empties it explicitly instead of falling back to the default:

| Variable | When set to an empty string |
|---|---|
| `IMGYOUNG_DATA_DIR`, `IMGYOUNG_LISTEN` | Startup fails, and the error names the variable |
| `IMGYOUNG_MASTER_KEY` | Same as not set |
| `IMGYOUNG_ADMIN_PASSWORD` | Same as not set; one is generated |
| `IMGYOUNG_TRUSTED_PROXIES` | Forwarding headers are never trusted |
| `IMGYOUNG_METRICS_ALLOW` | `/metrics` is closed to every address |

<Callout type="warn" title="Referencing host variables in Compose">
  With a reference such as `IMGYOUNG_TRUSTED_PROXIES: ${TRUSTED_PROXIES}` in `compose.yaml`, if the host does not set that variable, Compose only prints a warning and substitutes an empty string, which is the empty-string case in the table above.

  When `IMGYOUNG_MASTER_KEY` becomes an empty string, the service reads `/data/master.key`. An instance whose master key comes only from that variable, with no `master.key` in the data directory, refuses to start and reports that the master key is missing; it does not generate a new one.

  When the host must provide a variable, write `${TRUSTED_PROXIES:?TRUSTED_PROXIES must be set}`, and Compose refuses to start when the variable is missing or empty. If you want the default, leave the entry out.
</Callout>

## Running as nonroot

The image is based on `gcr.io/distroless/static-debian13:nonroot` and runs as the nonroot user (uid 65532). It contains no shell and no package manager, so `docker exec -it imgyoung sh` does not work.

When you need to work on the data directly (for example editing the database to [reset a forgotten password](../operations/password-reset.mdx)), stop the container and mount the same volume into another container that has the tools.

## Behind a reverse proxy

ImgYoung trusts `X-Forwarded-For`, `X-Forwarded-Proto` and `X-Forwarded-Host` only when the connecting peer is inside `IMGYOUNG_TRUSTED_PROXIES`. The default trusts loopback only, but inside a container the peer is almost never a loopback address:

- The proxy runs in another container on the same Docker network: the peer is the proxy container's address.
- The proxy runs on the host and reaches the container through a port published with `-p`: the peer is usually the Docker bridge gateway (such as `172.17.0.1`), not `127.0.0.1`.

In both cases, mark the proxy's network as trusted:

```bash title="Terminal"
docker run -d --name imgyoung --restart unless-stopped \
  -p 127.0.0.1:8721:8721 \
  -v imgyoung-data:/data \
  -e IMGYOUNG_TRUSTED_PROXIES=172.16.0.0/12 \
  ghcr.io/x-haose/imgyoung:latest
```

`172.16.0.0/12` covers most networks Docker allocates by default; check the actual subnet with `docker network inspect <network>`.

If you leave it unset:

- **Login rate limiting** is keyed on the proxy's address, so every visitor shares one allowance (a burst of 5, then 1 more every 12 seconds). When someone keeps mistyping a password, everyone else is temporarily locked out too.
- **Links and cookies**: without `base_url`, links returned by uploads start with `http://` even though the site is served over HTTPS, and the session cookie is not marked `Secure`.
- **Metrics**: the `/metrics` network check also sees the proxy's private address, so anyone going through the proxy can read the metrics unless the proxy blocks `/metrics`. The Caddy and Nginx samples under `deploy/` in the repository already block it.

For the proxy itself, see [Reverse proxy](../operations/reverse-proxy.mdx); for running it together with Caddy, see [Docker Compose](./compose.mdx).

## Restart policy

**Restore** under **Settings → Backups & export** first stages the snapshot in the data directory, then makes the service exit cleanly (exit code 0); the snapshot is swapped in when the process starts again. Therefore:

- Use `unless-stopped` or `always`. `on-failure` does not restart a container that exited cleanly, and the default `no` never restarts it.
- Without a suitable policy, the container stays exited after a restore, and the snapshot is swapped in only when you run `docker start imgyoung`.

The restart policy also brings ImgYoung back after the host or the Docker daemon restarts.

## Upgrading

Before upgrading, consider clicking **Back up now** under **Settings → Backups & export**.

Then pull the new image and recreate the container with the same flags. All data lives in the volume and is untouched; the database schema is migrated automatically when the new version starts:

```bash title="Terminal"
docker pull ghcr.io/x-haose/imgyoung:latest
docker stop imgyoung && docker rm imgyoung
docker run -d --name imgyoung --restart unless-stopped \
  -p 8721:8721 \
  -v imgyoung-data:/data \
  ghcr.io/x-haose/imgyoung:latest
```

`docker stop` waits 10 seconds by default before killing the container. ImgYoung finishes shutting down within about 8 seconds, so the default is enough.

Downgrading is not supported: if you switch back to an older tag, the older version refuses to start on a database migrated by a newer one. Rolling back takes the older image plus a snapshot taken before the upgrade; see [Upgrading](../operations/upgrade.mdx) for the steps and more.
